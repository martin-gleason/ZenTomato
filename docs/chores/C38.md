# C38 — the device installer chose a simulator over the phone

**Status:** closed 2026-09-24. **Owner:** agent. No user-visible change.
**Found by running it**, when the owner asked for the current build on their phone.

## The defect

`scripts/install-device.sh` picked the first device whose `marketingName` contained `iPhone` and
stopped looking. **`xcrun devicectl list devices` lists simulators alongside physical devices**, and
this Mac has an iPhone simulator called `HN-Test`, so the script chose the simulator, built
`Debug-iphonesimulator`, and then died with:

```
install-device.sh: HN-Test — iOS 26.5
install-device.sh: the build succeeded but produced no .app bundle.
```

**That message names the symptom and not the cause**, which is the failure this file's own header says
it exists to prevent: *"every one of those failures has a specific fix the person running it needs to be
told, and a Makefile recipe that can only say 'Error 1' is how a five-second problem becomes a
twenty-minute one."* It had become the thing it was written against.

## The discriminator, and the one that looks right and is not

`connectionProperties.transportType == "sameMachine"` is a simulator. Read off the real output:

| name | marketingName | transportType |
|---|---|---|
| `HN-Test` | iPhone 17 | `sameMachine` |
| `iPhone 17` | iPhone 17 | `sameMachine` |
| `iPhone` | iPhone 15 Pro Max | `localNetwork` |

**`hardwareProperties.isSimulated` is the obvious field and it is useless here: it is ABSENT on every
entry**, simulator and phone alike. A truthiness test on it selects nothing and a falsiness test selects
everything — either way the check passes review and does not work.

## What else changed

- **The two failures read differently now**, because *no iPhone is paired* and *only simulators are
  paired* have different fixes. The old script could report neither, because it never knew the
  difference.
- **A reachable phone is preferred but not required.** A paired-but-unreachable phone still builds, and
  the install step gives its own specific error.

## Mutations

| ID | mutation | result |
|---|---|---|
| `C38-M1` | every device made to look like a simulator | caught — *no PHYSICAL iPhone … only 2 simulator(s)*, with the right remedy |
| `C38-M2` | the no-candidates branch prints three empty fields before its note | caught on the first run of the fix |

**`C38-M2` was my own bug, not a planned mutation, and it is the more interesting one.** The
no-candidates branch printed `"" "" "" "simulators=2"`, and `read -r udid name os note` **strips leading
whitespace** — so the note landed in `udid`, the empty-udid check passed, and the build ran with
`-destination id=simulators=2`. A sentinel (`NONE`) cannot collapse; three empty fields can.

It is recorded because the shape recurs: a guard that reads the right value in the happy case and a
shifted one in the failure case, which is the same class as the malformed register rows `C33` left and
`C36` found.

## What this cost

One device check. The owner asked for the build on their phone; the first `make device` failed with a
message about a missing `.app` bundle, which points at the build rather than at the device choice.
