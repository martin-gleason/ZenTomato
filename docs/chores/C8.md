# C8 — Turn on Developer Mode on the watch, and provision it

**Owner: the human.** It needs the watch in hand and the Apple Developer account,
neither of which the agent has. Blocks F7's device check and nothing else.

## Developer Mode was off, was turned on, and was not the whole story

**2026-08-24.** The owner identified that the new Watch Ultra 3 had never had
Developer Mode turned on, and turned it on. `devicectl` now reports
`developerModeStatus: enabled` for both devices — and the watch app still does
not install.

**The two things are separate, and conflating them cost a round trip.** Developer
Mode makes a watch *willing* to run development builds. **Registering** it as a
development device is what lets a provisioning profile *name* it. A watch can be
willing and unnamed, which is exactly where this is now.

What follows was written when Developer Mode was believed to be the whole cause.
It is kept because the chain is still true — it simply starts one link later:

- A watch without Developer Mode is not a usable development device, so Xcode
  never registers it.
- An unregistered device cannot appear in a provisioning profile.
- Automatic signing therefore never creates a watchOS profile, and falls back to
  the iOS one — which is exactly what the evidence showed.

It also explains the two things that looked odd while diagnosing: `devicectl`
reported the watch as `available (paired)` rather than `connected`, and
`xcodebuild` answered *"Unable to find a destination matching the provided
destination specifier"* when asked to build for it.

**The agent under-weighted this**, having previously called Developer Mode as the
cause on the phone when it was already on — an idle Wi-Fi tunnel presents the
same way. Being wrong once in one direction is not a reason to stop suspecting it
in the other.

## What the profile actually says, which is the symptom

The watch app builds, embeds and signs correctly. It is inside
`ZenTomato.app/Watch/`, signed by team `KH6NBQRZBY`, with `WKApplication` true,
`WKCompanionAppBundleIdentifier` naming the phone app, and a real `arm64_32`
watchOS binary. **None of that is the problem.**

The problem is one level up. The watch app is signed with
**`iOS Team Provisioning Profile: *`**, whose platform list is `iOS, xrOS,
visionOS` — **no watchOS** — and whose device list contains one device, the
iPhone. The paired Apple Watch Ultra 3, `00008310-00037C462640E01E`, is not in
it. No watchOS provisioning profile exists on this machine at all.

So iOS installs the container app and **silently declines the watch app**. There
is no error, no prompt, and nothing in any log: the phone app simply arrives and
the wrist stays empty.

**This is why it took four checks to find.** Every inspection of the bundle came
back healthy, because the bundle was healthy. `scripts/check-watch-provisioning.sh`
now looks where the fault actually is.

## What the agent tried, so it is not tried again

- `-allowProvisioningUpdates` — already in `install-device.sh`. It updates
  profiles but did not create a watchOS one.
- `-allowProvisioningUpdates -allowProvisioningDeviceRegistration` together —
  built fine and still chose the iOS profile for all three targets.
- Building with the watch as the destination — *"Unable to find a destination
  matching the provided destination specifier"*. A watch is not directly
  addressable; it is reachable only through the iPhone it is paired to, and this
  one is `available (paired)` rather than `connected`.

`project.yml` says no Xcode GUI is ever required, and that stands for **building
and testing**. Registering a new device against a developer account is neither,
and `C4` already exists as the equivalent chore for the phone.

## Steps

**1. ~~Turn on Developer Mode on the watch.~~ DONE 2026-08-24** — both devices
report `enabled`.

**2. Register the watch in the developer portal.** This is what is actually
missing, and `xcodebuild` cannot do it from here: a watch is never a build
destination, so automatic signing never sees it to register it.

> developer.apple.com → Certificates, Identifiers & Profiles → **Devices** → **+**
> Platform: **watchOS** · Device ID: **`00008310-00037C462640E01E`**

Doing it by hand rather than hoping Xcode notices the watch is deliberate: three
CLI attempts with `-allowProvisioningUpdates` and
`-allowProvisioningDeviceRegistration` all registered the phone and ignored the
watch.

**Then the rest:**

3. `make generate && open ZenTomato.xcodeproj`, **iPhone connected by cable**,
   Watch on the wrist and unlocked. Xcode → Settings → Accounts → **Download
   Manual Profiles**.
3. **Xcode → Window → Devices and Simulators.** The watch appears beneath the
   iPhone, and should no longer be marked as unavailable. If it does not appear,
   unlock both and wait — it is only reachable through its paired phone, and a
   first pairing to a development machine can take a few minutes.
4. Select the **ZenTomatoWatch** target → **Signing & Capabilities** → confirm the
   Team. Xcode registers the watch and creates a watchOS profile at that moment.
   Accept any prompt to register the device.
5. `make device`
6. `scripts/check-watch-provisioning.sh`

If the watch app still does not appear after that: **iPhone → Watch app → scroll
to Available Apps → ZenTomato → Install.** A development build often needs that
nudge rather than arriving on its own.

## The order matters

Developer Mode → Xcode sees the watch → Xcode registers it → a watchOS profile is
created → `make device` embeds an app that can install. Skipping to `make device`
before the first step just reproduces the silent failure.

## Part two, found while diagnosing part one: the app has no MusicKit entitlement

**The same wildcard profile explains the music log.** The installed app's
entitlements are exactly three:

```
application-identifier      KH6NBQRZBY.com.martingleason.ZenTomato
com.apple.developer.team-identifier  KH6NBQRZBY
get-task-allow              true
```

and the profile's App ID is **`KH6NBQRZBY.*`** — a wildcard. **A wildcard App ID
cannot carry a capability**, so there is no MusicKit entitlement, which is why
every launch fills the console with:

```
ICError Code=-7013 "Client is not entitled to access account store"
applicationQueuePlayer _establishConnectionIfNeeded timeout [ping did not pong]
Aborted fetching subscription status because privacy link needs to be displayed first
```

`-7013` is not noise. It says, literally, that the app is not entitled.

**What it actually costs today: less than it looks.** `AppleMusicAvailability`
already treats a failed read as `.couldNotBeChecked` rather than as "no
subscription" — one quiet line, the timer untouched. Playback from the local
library does not need the entitlement, which is why F4's device checks passed
with music playing. What the app cannot do is ever *know* whether there is a
subscription, so that one row is permanently uncertain.

**`C2` asked for this and it appears never to have landed:** *"Confirm the Apple
developer account is active; create the App ID with the MusicKit capability."*
Automatic signing is falling back to the team wildcard instead.

### The fix, in the same Xcode sitting

1. developer.apple.com → Certificates, Identifiers & Profiles → **Identifiers** →
   an explicit App ID for `com.martingleason.ZenTomato`, with **MusicKit** enabled.
2. A second explicit App ID for `com.martingleason.ZenTomato.watchkitapp`.
3. Back in Xcode, both targets → Signing & Capabilities. It should now pick the
   explicit App IDs rather than the wildcard.
4. `make device`, then check with:
   `codesign -d --entitlements - --xml DerivedData/Build/Products/Debug-iphoneos/ZenTomato.app`
   — a MusicKit entitlement should appear alongside the three above.

**Both halves of this chore are the same underlying fault**: the project is being
signed with a generic team wildcard rather than explicit App IDs carrying the
capabilities it needs. Fixing that fixes the watch and the music row together.

## Done when

`scripts/check-watch-provisioning.sh` exits 0 — the embedded profile covers
watchOS and lists `00008310-00037C462640E01E` — and ZenTomato is on the wrist.

Then F7's device check becomes possible: three wrist taps during a pomodoro with
the phone in another room, and the harder half, taps made genuinely out of range
arriving later with their original timestamps.
