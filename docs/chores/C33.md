## Why a documentation chore needs a code change first

`scripts/gen_status.py` is the generator behind `docs/plans/00-status.md`, and CI keeps that page
current. Three of its mechanics govern every table this chore writes, and two of them would have
destroyed the backfill in silence.

1. **A section is found by the parenthesis in its heading.** `gen_status.py:134` searches
   `\(([A-Z]{1,2})\)\s*$`. The four new headings are therefore exactly `## Agent items (A)`,
   `## Mutations (M)`, `## Hooks (H)` and `## Risks (RR)`. A trailing period or a backtick round the
   symbol and the section is skipped without a word.
2. **Column headers are the field names, lowercased** (`gen_status.py:117`). The generator reads
   `id`, `title`, `status` and `p`. Every new table carries columns headed literally `ID`, `Title`,
   `P` and `Status`; any other column is free and ignored. This is load-bearing for `H`: the status
   page's `## Hooks` block prints `| ID | Hook | Status |` out of `h.get('title')`, so an `H` table
   whose second column were headed `Mechanism` — the natural choice, and the one `conventions.md`'s
   own wording suggests — would render thirty-two blank hook names and no gate would catch it.
3. **Row IDs are filtered by `re.fullmatch(r"[A-Z]{1,2}\d+", …)`** (`gen_status.py:138`), and **a
   scoped mutation id such as `F8-M1` or `C32-M7` fails that regex.** 81 of this project's 103 mutation
   IDs are scoped. Backfilling `M` and leaving the generator alone would have printed
   `Mutations (M) | 22` on a page CI keeps current — precisely the failure `D38` opens the register to
   prevent.

### The ruling on (3), and the two alternatives named so they are not re-proposed

**The regex is widened, by this chore, to `[A-Z]{1,2}\d+|[A-Z]{1,2}\d+[a-z]?-M\d+[a-z]?` and to nothing
else.** `sort_key` is untouched: it already degrades to `(unit_id, 0, "")` for a scoped id, which
sorts scoped rows lexically after bare ones. That is acceptable and the `M` section's preamble says so
rather than leaving a reader to discover it.

- **Renumbering the 81 scoped IDs into a bare global sequence** breaks citations in shipped Swift —
  `ShapeSeamTests`, `ShapeScreenTests`, `ShapeScreenFenceTests`, `ShapeSettingsFenceTests`,
  `PolishFenceTests`, `ShapeStore.swift` and `ShapeSheetActions.swift` all cite `F8-M<n>` — and
  `conventions.md` forbids it outright: *an identifier, not an index.*
- **Putting the scoped id in a non-`ID` column and a synthetic bare id in `ID`** invents identifiers
  nothing cites.

**Proved by mutation before a single row was written** — see *Mutations* below.

## The mechanism count: it is thirty-one, and it is not fifteen (and it was thirty)

`D38` refused to inherit the handoff's *"fifteen real enforcement mechanisms"* because no command had
been shown to reproduce it, and made establishing the real count the first work of this chore.

**A mechanism is a check that (a) is invoked by a named command, (b) can fail and thereby stop a
commit, a CI run or a test run, and (c) defends a stated spec invariant or a ratified decision rather
than a formatting preference. It is counted once at its definition site, never once per surface that
invokes it** — `scripts/check-secrets.sh` runs at pre-commit and in CI and is one mechanism with two
values in its `Runs at` field. Counting invocations instead of definitions is how a count inflates
without anything being built.

### The first version of this count reproduced its own answer, and that is why it was wrong

**The shell/Python and SwiftLint halves derive themselves. The Swift half did not, and it shipped
thirty when the answer is thirty-one.** The command below listed seventeen Swift files **by name** —
`ls ZenTomatoTests/*Fence*.swift ZenTomatoTests/NoCaptureSurfaceTests.swift …` — so it printed the set
it was handed rather than selecting from the population. A hand-written `ls` is a fixture that
satisfies both the right and the wrong answer, which is the tautology-with-a-green-tick
`docs/conventions.md` names, and it hid
`ZenTomatoTests/TodoistEndpointTests.swift` — a suite whose own first line is *"the rule the whole
project cares most about: **the only write to Todoist is completing a task**"*. That is `H32`, added
after review. **What a re-deriver needs is the criterion, not the `ls` line**, so the criterion is
below and the command derives the candidate set instead of the answer.

**The two halves that do derive themselves**, run at `bc4e0f2`:

```
{ ls scripts/check-*.sh | grep -v install; echo scripts/gen_status.py;
  echo scripts/tests/run-script-tests.sh;
  awk '/^  [a-z_]+:/&&f{print ".swiftlint.yml:"$1} /custom_rules/{f=1}' .swiftlint.yml; } \
  | sort -u | wc -l
→ 13
```

Twelve shell/Python checks and one SwiftLint custom rule.

**The Swift half is a judgement over a derived candidate set, and the criterion is the same three-part
one, applied to a suite.** A Swift suite is a mechanism when, and only when:

- **(a) it is invoked by a named command** — every suite under `ZenTomatoTests/` is, by `make test`, so
  this part selects nothing and is stated only so the count is not read as excluding it;
- **(b) it can fail and thereby stop the test run** — again true of all of them; and
- **(c) its stated purpose is to stop a change, not to describe a behaviour.** *This* is the whole of
  the selection. The test is the suite's own `///` docblock, not its filename: does it name an
  invariant sourced from `CLAUDE.md`'s non-negotiables, a ratified `D<n>`, or a fence a plan declared —
  and would the suite go red because somebody **added** something the contract forbids, rather than
  because a feature computes the wrong answer? A behaviour suite answers *does this work*; a mechanism
  answers *has the fence moved*.

The candidate set is every suite, and it derives itself:

```
for f in ZenTomatoTests/*.swift; do

    "$(sed -n '1,30p' "$f" | grep -m1 '^/// ' | sed 's|^/// ||')"
done
→ 96 suites, each with the first line of its own docblock
```

Applying (c) to those 96 returns **eighteen**: the nine `*Fence*` suites, plus
`NoCaptureSurfaceTests`, `MusicNoCaptureTests`, `PrivacyManifestTests`, `WatchLinkTests`,
`DeltaIntegrityTests`, `AmendmentRatchetTests`, `AmendmentDeclarationTests`,
`DeltaCitationSurfaceTests` and — added after review — `TodoistEndpointTests`. 13 + 18 = **31**.

exists to stop a Todoist write being added, and its docblock states the gap it fills — *"the script

**What was excluded, because the exclusions are the argument.** `scripts/install-device.sh` installs

section preamble states both numbers.** `H32` is allocated after `H31` and therefore out of the
allocation order below; the table is not renumbered to tidy it, because an ID is an identifier and not
an index (`D17`).

**Where fifteen came from.** `docs/handoffs/blockersfor1_5.md:71` — *"15 real enforcement
mechanisms"* — restated at :85, with no command beside either sentence. Fifteen was not reproducible
under any defensible rule: the near misses are ten `scripts/check-*.sh` excluding `install-device`,
twelve shell/Python checks, sixteen CI steps including setup, and seven hook invocations. It matches
none of them and is most likely a recollection rather than a count. **The tree was not touched to
reach any number.**

**The same paragraph carries a second unverified claim, and it is already wrong.**

### `run` versus `proposed`, which is the only column that matters

`Run` is a pinned enum of three values and it is the only thing separating the 60 mutations that have

one that **escaped** (`F8-M9`, which is `F8`'s thirteenth scoped row and the sixty-first application)
and the 42 that have never touched code. **THE SCOPED BREAKDOWN READ `F8` 13 AND `C33` 3 UNTIL
2026-09-23,** two errors that cancelled to the right total of 38 — the *fixture that satisfies both the
right and the wrong implementation* pattern `conventions.md` names, committed as a sentence rather than
as a test, and caught by `C33`'s second review pass rather than by the total. `F8` has 13 scoped rows
but only 12 are `run`, the thirteenth being the `escaped` one; `C33` has 4 since `C33-M4` was
allocated. **`docs/plans/00-register.md`'s figure of 61 is the `Status` column and not this one** — its
preamble now says so — and until this pass the two documents this chore ships disagreed by one.
Neither number is asserted; both come out of the register, by the command in its `M` preamble grouped
on the id's unit prefix. **A mutation is `run` only where a source records
it failing.** *"Named now and run before this task is called done"* (`F8.md:468`) is a promise, and a
promise filed as a run is exactly the false-assurance instrument `conventions.md` describes at length.

| Value | Means |
|---|---|
| `run` | applied to shipped code, the named test was seen to go red, and it was restored |
| `escaped` | applied, and the named test did **not** catch it. The project has one: `F8-M9` |
| `proposed` | named in a plan for work that has not been built. Never seen to fail anything |

The rule for telling them apart is **the source document's kind, not the wording.** A chore file, a

## What C34's validator must handle, found here and not fixed here

The register validator is `C34`. These are the **fifteen** row shapes that would defeat one, written
down so it is designed for them rather than patched round them. **Fourteen of them were written before
`C33`'s second review pass, and that pass rewrote one and added another** — finding 14's mechanism was
wrong, so a validator built to it would have fired on none of the eight rows it was for, and finding 15
did not exist. Both corrections point the same way: **a validator checks a declared shape field by
field, with a pinned vocabulary per field**, because every shape here is a required field carrying
something that is not a value of it.

1. **A scoped ID fails the bare-ID regex.** Fixed for the generator here; a validator written on the
   same assumption inherits the same hole.
2. **Five `Source` cells are a commit SHA and nothing else.** No file-reading validator can resolve
   them. It must either accept a SHA as a terminal citation or report them as an enumerated
   exemption — and **an exemption list is how a validator quietly stops validating**, so whichever it
   is should be visible in the output rather than in the code.
3. **Bare `M<n>` is also used as local shorthand, and a naive grep cannot tell it from a global ID.**
   `docs/plans/F7b.md:309,348` write `M1`–`M4` meaning `F7b-M1`–`F7b-M4`; this register's own `C32`
   row writes *"with `M1`-`M6`"* meaning `C32-M1`–`C32-M6`. These are **not** the `F4`-series
   `M1`–`M6`. Merging them by string match reproduces the `C29` defect in a new register. A validator
   must require the scoped spelling in register cells and treat a bare token in prose as unresolvable.
4. **Substring bleed.** The same bare-token regex matches inside `C32-M10` depending on the preceding
   character, which is how `00-register.md` appears in the bare-token file list at all.
5. **`H1` has false positives in prose.** `docs/chores/C6.md:91` and `docs/reviews/F6.md:158` carry
   markdown heading-1 text that a bare `H\d+` grep reads as a hook citation.
6. **A retrofit letter on a mutation number.** `C32-M4b` is a real ID and the obvious scoped-ID regex
   reports it as `C32-M4`, merging two mutations into one. A validator must allow the letter.
7. **A grep cannot tell a name from a denial of a name.** `M34`, `F8-M7a` and the fifteen-mechanisms
   figure are all tokens whose only appearances are statements that they are not real.
8. **Two `Owning unit` cells record a scope that is wrong rather than one that should have been right.**
   `ZenTomatoTests/DeltaCitationSurfaceTests.swift` arrived as `fix(C1)` — `C1` is the repo-setup
   chore — and `ZenTomatoTests/PrivacyManifestTests.swift` arrived as `chore(O18)`, a **register ID in a
   commit scope**, which Axis 2 forbids outright. Both are recorded as git states them. A validator that
   requires `Owning unit` to be a defined `F`/`C` unit will fire on the second, correctly.
9. **`F8-M7` and `F8-M8` each name two different mutations** — already `O43`. This chore writes **one
   row per ID** with the collision stated in `Why` and the row cross-referencing `O43`. It does not
   allocate a disambiguating suffix, because `F8-M7a` would be an identifier nothing cites and `O43`
   is the owner's to rule on.
10. **`Status: closed` beside a `Proved by` cell containing `never`.** **This register committed that
   contradiction four times** — `H5`, `H7`, `H15`, `H30` — under a paragraph stating the rule, and the
   generated page published *"17 of 31 built"* off the back of it. It is the single most valuable check
   `C34` can carry, because the two cells are in the same row and a validator needs no other file to
   see it. Note the shape it has to survive: `H15` and `H30` do not read the bare word `never`, they
   read *"`F15-M1` proposes the sibling typography rule's mutation; this rule itself: never"* and
   *"`F15-M3` proposes one; today: never"* — **a cell naming a `proposed` mutation is not a proof**, so
   the check is on the presence of `never`, not on the absence of an ID. A stricter and better version
   pins each cited mutation ID to its `M` row and requires `Run: run` there.
11. **A section whose rows are not in ID order.** The `M` section shipped with `M23` immediately before
   `C28-M1` and `F19-M4` before `F7b-M1`, because its preamble had ordered the **source** to match
   `gen_status.py`'s output — the inverse of `docs/conventions.md`'s *"re-sorting for reading is the
   generated status page's job, not the source's."* Corrected after review. A validator needs a stated
   key, because the IDs are two shapes: parse as
   `(prefix, number, retrofit letter, scoped prefix, scoped number, scoped letter)` and the 103 rows
   have exactly one order. The check also catches the duplicate-ID half of the Axis 2 rule for free.
12. **A defining field left empty on every row of a register.** `RR`'s `Likelihood` shipped `—` on 4 of
   4 rows, and `docs/conventions.md` defines the register by exactly the five contents it names.
   A validator cannot tell *not assessed* from *not applicable*, so the fix was to make each cell say
   which kind of statement it is making. **A column that is empty on 100% of rows is a stronger signal
   than one that is empty on some**, and it is cheap to check.
13. **A SECOND MARKDOWN TABLE INSIDE A REGISTER SECTION SILENTLY REDEFINES THAT SECTION'S FIELD NAMES.**
   `gen_status.py`'s `parse_tables` sets `header` from the **first** table it meets after a `## `
   heading and never resets it, so a legend table placed in a section's preamble becomes that section's
   schema: every real row then parses under the legend's column names, loses its `id`, and disappears.
   The fix drafted for finding 12 did this to `RR` — four rows, gone from a page CI keeps current — and
   it was caught only by generating the page, not by reading the diff. **This is the strongest argument
   in this list for `C34` asserting a per-section ROW COUNT and not only per-row shape**, because the
   failure mode is rows going missing rather than rows being wrong, and a per-row check sees nothing at
   all. The legend is prose now.
14. **A STATUS VALUE OUTSIDE ANY PINNED VOCABULARY — THE CHECK IS ENUM MEMBERSHIP, NOT AN EMPTY
   CELL.** Eight rows of the `C` register carry the literal word `unknown` in `Status`: `C9`, `C10`,
   `C12`, `C14`, `C16`, `C18`, `C19`, `C20`. **THIS ITEM SAID *"EIGHT ROWS CARRY NO STATUS AT ALL …
   Axis 2's mandatory field is actually absent"* UNTIL 2026-09-23**, and `C33`'s second review pass
   showed the mechanism was wrong: `grep -n '^| C9 ' docs/plans/00-register.md` returns
   `| C9 | TestFlight runbook | P1 | unknown |`, the cell is non-empty, and it is non-empty at
   `bc4e0f2` too. **Parsing the `C` table for an empty `Status` cell returns `[]`.** So a `C34`
   validator written to the shape as it was specified — fire on an absent status — would have fired on
   **zero of the eight rows it was written for**, passed, and reported the register clean. That is this
   list's own failure mode: a check whose fixture satisfies both the right and the wrong
   implementation, except that here the fixture would not exist at all.

   **The real defect is a value outside the vocabulary**, and the check must be enum membership:
   `Status` is one of a pinned set and `unknown` is not in it. The set is the register's own —

## The transcription procedure, and why it is a procedure

`C29`'s defect was matching rows on ID across two documents, in a file carrying duplicate IDs, and
pasting the wrong row's text. **The `A` table in `OPEN.md` is not in ID order** — the source runs
`A1`…`A11`, then `A18`, `A17`, `A16`, `A12`, `A13`, `A15`, `A14` — so a transcription that assumes the
numbers ascend pairs `A18`'s watchdog-kill text with the ID after `A11`. That is `C29` in a new
costume.

The defence, and nothing else catches it:

1. **Transcribe in source order**, one physical `OPEN.md` line to one register line, carrying ID and
   text together. Never sort while transcribing.
2. **Sort to ID order as a separate, mechanical second pass** (`conventions.md`: every register is
   sorted by ID).
3. **Diff the `(ID, first 40 characters of Title)` pairs** before and after the sort, both lists
   sorted. Identical output proves no cell crossed a row, and the empty diff goes in the PR. *"The
   sort looks right"* is exactly the evidence `conventions.md` refuses.

There is no `A`-row equivalent of the `O23`/`O24`/`O25` collisions: eighteen IDs, `A1`–`A18`, one
occurrence each, checked.
