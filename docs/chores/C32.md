## Why the new files are not edits to a baseline

Two artifacts are created:

- `docs/specs/V15-AMENDMENT-BASELINE.txt`
- `docs/specs/V15-AMENDMENTS-APPLIED.md`

Neither is inside `zenpom-v1.5.md`. They stand in exactly the relationship
`docs/specs/AMENDMENT-BASELINE.txt` already has to `SPEC.md`: an instrument **about** a baseline,
maintained by the thing that measures it, rather than a part of the baseline itself.

`SPEC.md` can carry its own `## Amendments applied` list because the **owner** edits `SPEC.md`.
`zenpom-v1.5.md` cannot: the agent is forbidden to touch it, and a ledger the agent may not
maintain is a ledger that rots.

**Open question for the owner, not decided here.** The owner may prefer an `## Amendments applied`
section *inside* `zenpom-v1.5.md`, matching `SPEC.md`. That is an edit to a ratified baseline and
needs a `D<n>` of its own, exactly as `D40` was needed for `D33`. It is recorded here rather than
proposed.

## How the detector decides which baseline a delta owes

**It reads a declaration the deltas already write:** the first backticked span in the **first
paragraph** of the `**Currently` block, when it looks like a document name. No declaration means
`SPEC.md`, which is today's behaviour for every delta.

Only the first paragraph is scanned, because a delta with no `**Proposed` marker has a block that
runs to the end of its body — `D28` mentions `F2c.md` two paragraphs down and `D34` mentions
`CLAUDE.md`, and neither is a declaration. Run over the real tree, exactly `D31` (`zenpom-v1.5.md`)
and `D40` (`CLAUDE.md:10`) declare **inside the block**.

**The review added a second place to look, and it is the fix for `D33`.** When the block declares
nothing, the delta's **preamble** — the text between the heading and the marker — is scanned for a
backticked name that resolves to a *watched baseline*, and nothing else. Two ratified deltas write
theirs there: `D33` opens *"Owed because `docs/specs/zenpom-v1.5.md` is a ratified baseline"* and
`D35` *"This supersedes the stop condition in `docs/specs/zenpom-v1.5.md`"*. Admitting only a watched
name is what keeps the dozens of incidental `.md` mentions in a preamble from redirecting anything.
Run over the real tree, the preamble adds exactly `D33` and `D35`, both to `zenpom-v1.5.md`, and
**neither owed set moves**: `SPEC.md` stays `{D4, D17}` and v1.5 stays `{D31}`.

**A declaration REDIRECTS; it never excuses.** When the declared name resolves to nothing watched,
the block is judged against `SPEC.md` — the behaviour every delta had before `C32`. The first draft
returned `nil` there, which is the first blocking finding below.

This narrows the hole the `C32` register row names in its own words: *"`quotesLiveSpecText` treats
any `**Currently:**` block as owing SPEC.md text, and `D40` is the first delta to use that marker to
quote a file other than SPEC.md — it passes only because the string `docs/specs/zenpom-v1.5.md`
happens not to occur in SPEC.md."* **It does not close it, and the first draft of this file claimed
it did.** With the fallback restored, `D40` is judged against `SPEC.md` again and passes for the
reason it always did: the string it quotes is not in `SPEC.md`. What the declaration rule genuinely
buys is the *redirect* — a delta quoting v1.5 is measured against v1.5 — not an excuse for a delta
quoting something unwatched. Removing the luck-dependence for an unwatched document needs that
document watched, and `CLAUDE.md` is not a ratified baseline.

**What did not change: either owed set.** `SPEC.md` is `{D4, D17}` and v1.5 is `{D31}`, before and
after, under the colon-only matcher, under both spellings, with the declaration rule, and with the
preamble rule. Verified by running at every step. That is the single fact that makes this change safe
at a baseline of zero — and after the review it is a fact about *both* baselines and every rule in
the chain, not about the marker alone.

**No fuzzy matching.** `AMENDMENT-BASELINE.txt` records why verbatim comparison is deliberate: fuzzy
comparison buys one true positive at the cost of false ones, and a check that cries wolf stops being
read. Nothing here relaxes it.

### `C32-M6` was not in the plan, and it found a defect

`C32-M6` removes `D31` from `V15-AMENDMENTS-APPLIED.md`. The v1.5 ratchet should have gone red at 1,
because `D31` is the one delta owed against v1.5. **It passed.** That is a mutation that escaped, and
the rule is that an escape is a finding about the instrument, not a nuisance.

The cause, found by printing `applied` rather than by reading: `appliedAmendments(in:)` — code
inherited unchanged from before `C32` — matched the string `## Amendments applied` **anywhere in the
file**. This ledger *explains* in prose why `SPEC.md` may carry its `## Amendments applied` list
inline and v1.5 may not, and that mention comes first. The parser read its section from the mention,
returned the ids in the surrounding paragraph — `["D31", "D41"]` — and never saw the real list at
all. It missed `D33` entirely and reported `D31` as applied *from the sentence explaining that it is
applied*.

**It hid because the wrong answer happened to contain the id being asked about.** A fixture that
satisfies both the right and the wrong implementation distinguishes nothing, and this one did for
three green runs.

**The fix is in the instrument:** the heading is now matched at the start of a line. `C32-M6` was
then re-run from a confirmed-green baseline and caught. Only the second run is evidence.

**This also means the architect's work order was wrong on one empirical point**, and the correction
is recorded rather than smoothed over: it predicted the v1.5 owed set would be empty once the
declaration rule was applied, and told the coder to state in the ledger that the applied list does
not move the number. It does. `D31` is owed, on the incidental fragment `docs/plans/parked.md`, and
`C32-M6` is the proof that the ledger is load-bearing today.

## The second adversarial review, and the two blocking findings

The first review (below) was run in-session against `C32`'s own tree. A second, independent review
was then fired at the finished work and returned **two blocking findings and five non-blocking**.
Both blocking findings were real. Both are fixed. Nothing was refuted, and the reason is worth
recording: **neither finding was about the code being misread — both were about a judgement changing
downstream of an assertion that could not see it**, which is the failure mode this project's own
mutation rule exists for and which six mutations had not reached.

### Blocking 1 — the declaration rule silently narrowed the `SPEC.md` ratchet

`owedBaseline(for:)` returned `nil` when a delta's declared document matched no watched baseline.
Before `C32` there was no declaration rule at all: any `Currently` block whose fragments matched live
`SPEC.md` text was counted. So the new rule **dropped** a delta that names `CLAUDE.md` or `F2c.md`
while quoting `SPEC.md` verbatim — and the suite stayed green at 633, because
`theColonFormBlockIsByteIdentical` asserts the marker *slice* is unchanged, which it was. **The
judgement downstream of the slice changed and nothing looked at it.**

The claim in this file and in the register that the `SPEC.md` owed set was unchanged *"verified by
running"* was true for today's 43 deltas and true **by luck** — which is the same luck-dependence
`D41`'s second clause exists to remove.

**Fixed:** a declaration only ever redirects. An unresolvable one falls back to `SPEC.md`, exactly as
before `C32`. `anUnwatchedDeclarationIsStillJudgedAgainstSpec` pins it, using the reviewer's own
trigger — a `CLAUDE.md:10` declaration carrying live `SPEC.md:31` as its quotation — and `C32-M7`
restores the old `nil` and is caught.

### Blocking 2 — the new v1.5 ratchet does not detect `D33`, the case it exists for

`D41`'s second hole: *"`zenpom-v1.5.md` is an equally ratified baseline with no amendment ledger, no
baseline file and no ratchet — and `D33` amends it. Nothing would ever have gone red."* After `C32`
there is a ledger, a baseline file and a ratchet, and **`D33` still does not go red.** The first
draft of this file disclosed that in one subordinate clause; the register row asserted *"A SECOND
BASELINE IS WATCHED"* without it, and no owner item recorded it.

Two causes, and only one is fixable:

1. **Wrong baseline — fixed.** `D33`'s block declares nothing, so it defaulted to `SPEC.md`. The
   declaration rule now also reads a delta's **preamble**, where `D33` writes *"Owed because
   `docs/specs/zenpom-v1.5.md` is a ratified baseline"*. `theBaselineADeltaDeclaresInItsPreambleIsRead`
   pins it; `C32-M8` removes the preamble scan and is caught.
2. **No verbatim fragment — not fixable by this instrument, and now recorded.** `D33` amends an order
   **table** and quotes it as a comma list — `` `C21` ``, `` `F8` ``, `` `F12` `` … — every entry
   below the twelve-character fragment floor, while the live spec renders them one per table row. Its
   only fragment at or above the floor is the incidental *"delta owed: none"*. There is no
   twelve-character verbatim overlap to find, and lowering the floor makes `` `F8` `` match
   everything. This is the `D18` class `AMENDMENT-BASELINE.txt` already records: **a delta that
   paraphrases its baseline instead of quoting it is invisible.**

**Measured, not argued**, per the reviewer's trigger. The pre-`C31` tree was reconstructed —
`git show ac80738:docs/specs/zenpom-v1.5.md` and `ac80738:docs/plans/00-deltas.md`, the exact state
where `D33` sat ratified-and-unapplied — and the **finished** `C32` detector run over it:

### Two findings from this unit's own review, taken rather than filed

The review returned five non-blocking findings and the integration pass recorded that **none had been
taken**. Two of them were about the instrument this unit exists to build, so they were fixed here
rather than deferred, and each was given the assertion it was missing.

**The block name could veto the preamble.** `declaredBaseline(for:)` returned as soon as the
`Currently` block yielded any document-shaped name. When that name was *unwatched* the result was
`nil`, the preamble was never consulted, and the caller's fallback sent the delta to `SPEC.md`.

**That is not hypothetical, and the shape is already in the tree.** `D40`'s block opens with
`CLAUDE.md`, an unwatched document. A later delta written in `D40`'s form while declaring
`docs/specs/zenpom-v1.5.md` in its preamble would have been judged against the wrong baseline and
stayed invisible to the v1.5 ratchet — **the same miss `D41` Hole 2 is named for, reproduced inside
the instrument built to close it.** The block is now asked first and cannot veto;
`anUnwatchedBlockNameDoesNotVetoThePreamble` pins it, and its fixture names an unwatched document in
the block and a watched one in the preamble so that a short-circuiting implementation and a
falling-through one give different answers. A fixture naming the same document in both places would
have passed under either.

**`watchedBaselines` was read by position with nothing saying what the positions were.** Three call
sites index it — the two named ratchet tests and `owedBaseline(for:)`'s fallback. Insert a third
baseline at the front and `everyRatifiedSpecAmendmentIsApplied` measures a different document while
keeping its name, and every unresolvable declaration lands on the wrong contract, with nothing red.
`theWatchedBaselinesAreInTheOrderEveryCallerAssumes` costs two `#expect`s; `C32-M12` shows it catches
the swap, and that it takes a third test down with it.

**Three findings were NOT taken, and are recorded rather than implied.** `declaredDocument` still
admits `.swift` and `.txt` suffixes that no watched baseline has ever had — dead admission, and the
short-circuit fix above removes the harm it could do. `O46` sits above `O45` in `docs/reviews/OPEN.md`
against an otherwise ascending table. And the v1.5 baseline of 0 rests on `D31` matching an incidental
path fragment rather than any text it amends, which `V15-AMENDMENT-BASELINE.txt` states plainly — so
that ratchet's green is one edit to line 7 of `zenpom-v1.5.md` away from moving for a reason unrelated
to any amendment.
