# C16 — the app is killed by the watchdog reading whether music is playing

**Owner: the agent.** A defect, not a feature. No delta.

## What happened

`docs/crashes/ZenTomato-2026-08-26-134602.ips`, from the owner's phone. The
report is committed, because a crash you cannot re-read is a crash you argue about.

```
EXC_CRASH (SIGKILL)
FRONTBOARD  0x8BADF00D
scene-update watchdog transgression:
  exhausted real (wall clock) time allowance of 10.00 seconds
```

**The app did not crash. iOS killed it for not responding**, which is what the
owner saw: *"it was open, it stalled out, then I got an error message saying the
app had quit."* A stall, then a kill. The dialog offering a message is iOS's, not
ours.

## The decisive number

```
Elapsed total CPU time (seconds):        10.880 (user 6.630, system 4.250), 18% CPU
Elapsed application CPU time (seconds):   0.053, 0% CPU
```

**Fifty-three milliseconds of our code across ten seconds of wall clock.** The app
was not computing, looping, or leaking. It was **blocked, waiting**, and the
watchdog killed it for it.

That single line rules out an entire class of suspects and points at exactly one:
something synchronous and cross-process on the main thread.

## The stack, which names it

Main thread, top to bottom:

```
mach_msg2_trap
_dispatch_mach_send_and_wait_for_reply
xpc_connection_send_message_with_reply_sync
__NSXPCCONNECTION_IS_WAITING_FOR_A_SYNCHRONOUS_REPLY__
-[MPMusicPlayerController _validateServer]
-[MPMusicPlayerController _snapshot]
-[MPMusicPlayerController playbackState]
MusicKit_SoftLinking_MPMusicPlayerController playbackState
```

**`playbackState` is a synchronous XPC round-trip to the media server.** It reads
like a property and behaves like a blocking IPC call. When the media daemon is
slow, the caller waits — and this app calls it **on the main thread**.

Corroborating, from the same phone the same day:
`medialibraryd.cpu_resource-2026-08-26-113211.ips` — the media library daemon was
already in trouble two hours earlier.

## Our line

`AppleMusicPlayer.isPlaying`:

```swift
var isPlaying: Bool {
  player.state.playbackStatus == .playing
}
```

and `nowPlayingTitle` beside it, both read straight through to the player.

`MusicCoordinator.refreshIsPlaying()` calls both, and is reached from **seven**
places — including `onPlaybackStatusChanged`, which fires on every playback change
the system reports, and therefore most often exactly when the media server is
busiest.

## The uncomfortable part: this was a deliberate decision

`F4-contract.md` §8 says it in as many words:

> The system transport controls make our state and the player's disagree… `isPlaying`
> is **read live from the player rather than cached**, which keeps the skip button
> honest.

The reasoning was sound and the defect it prevented was real — a skip button that
lied about whether there was anything to skip. **What was not priced was that
"asking the player" is a blocking IPC call**, not a memory read. The comment in
`AppleMusicPlayer` says *"asked of the player each time"* as though that were free.

This is the same shape as the week's other findings: a confident sentence
describing a framework's behaviour, written without checking what the framework
actually does underneath.

## The fix, built

**The read moved off the main thread. It was not cached** — caching is what §8
correctly rejected, and it would bring back the skip button that lies.

- **`PlaybackSnapshot`** — both readings in one `Sendable` value, taken together
  because they are always used together and a row showing "playing" beside a stale
  track title would be a new way to be wrong.
- **`MusicPlaying.playbackSnapshot()`** — `nonisolated async`, so a caller on the
  main actor never waits. The protocol gained `Sendable`, which costs nothing: it
  is `@MainActor`, and a main-actor class is `Sendable` already.
- **`AppleMusicPlayer`** reads on a detached task, reaching
  `ApplicationMusicPlayer.shared` inside it rather than capturing anything.
  `MusicPlayer.State` is **not** main-actor isolated — checked in
  `MusicKit.swiftinterface`, not assumed — so this is allowed.
- **`MusicCoordinator.refreshIsPlaying()`** starts the reading and returns
  immediately.

**The hazard the hop introduces, and the guard for it.** `F6-contract.md` warns
that *"a suspension point is where the last two features found their real bugs"*,
and this one adds exactly that: two readings in flight, the older landing second,
putting a stale row on screen.

So readings are counted **separately from decisions**. `generation` tracks whether
there should be sound and is bumped by `apply()`; `playbackReadGeneration` tracks
readings. A skip deliberately does not bump the first but must still supersede an
older reading, and folding them together would tie a question to a decision that
has nothing to do with it. A reading that comes back stale is discarded.

## The spy now blocks, and that is the real repair

`SpyMusicPlayer.isPlaying` returned instantly. **That is why 484 passing tests
said nothing**, and fixing only the coordinator would have left the hole open for
the next person.

It now sleeps for `snapshotDelay` when its synchronous properties are read, as the
real one does. `MusicWatchdogTests` sets a delay of one second and asserts the main
actor returns in under 250 ms — a wide margin on purpose, because the claim is
*"did not wait for the player"*, not a performance figure, and a tight bound would
fail on a loaded machine and teach everyone to ignore it.

Three tests:

| Test | What it holds |
|---|---|
| `aWedgedMediaServerDoesNotStallTheMainActor` | The main actor does not wait. This is the watchdog kill, as a test. |
| `theAnswerStillArrives` | Off the main actor is not the same as ignored — §8's honest skip button still works. |
| `aLateReadingDoesNotOverwriteANewerOne` | The stale reading is dropped rather than drawn. |

`awaitPendingPlaybackRead()` is `DEBUG`-only and exists so those tests await the
actual task rather than a guessed number of `Task.yield()` calls — that idiom is
already in these tests, it depends on how many hops the implementation happens to
take, and it turns a real regression into an intermittent one the day that number
changes.

## Why no test caught it

Every music test runs against a stand-in that returns a value immediately. **No
test can fail on a call that is fast in the test and blocking on the device**, and
no fence in this repo distinguishes a property read from an IPC call.

Recorded as `A18`, since it was a gap in the standard of proof rather than in this
one fix. **The spy blocking is what closes it**, and it closes it for every future
reading of that player, not just this one.

## And a flight recorder, so the next one is not found by luck

The only reason this crash could be read at all is that the phone happened to be
plugged into the machine that built it. A development build's crash reports live
on the device and nowhere else.

**`HangReporter`** subscribes to MetricKit. iOS gathers hangs, crashes, CPU and
disk-write exceptions itself and delivers them in a batch on a later launch — so
there is no sampling loop, no timer, and no work on any hot path. Registering is
the cheapest line in `ZenTomatoApp.init`.

**`MXHangDiagnostic` is the one that matters**: it reports a hang with its stack
and duration, and iOS notices hangs well below the ten seconds at which the
watchdog stops asking politely. This kill would have shown up as a hang first.

**Nothing is transmitted.** `SPEC.md` says local only and no analytics, and a
crash reporter is the most natural place for that rule to be broken by accident.
Payloads are written into the app's own container, pruned to the last twenty, and
leave the device only when someone fetches them. `MXMetricPayload` — the daily
performance aggregates — is received and deliberately ignored, because keeping it
would be the first step towards the analytics the contract forbids.

**No setting, no screen.** `AppSettings` still holds six values.

## One thing the fence caught, worth recording

`TodoistEndpointTests` failed on `HangReporter`: `FileManager.url(for:…​create:)`
takes a parameter called `create`, and the fence forbids that word by regex across
the app's sources because `CLAUDE.md` says *"Never call create, update, or comment
endpoints."*

The fence is blunt and it is right to be — it holds a rule that must not be
negotiable. The fix was to call `urls(for:in:)` instead, which does the same job
without arguing with it. **The alternative — narrowing the fence to make room —
would have been the wrong repair**, and it is the one that looks reasonable at the
moment you are blocked.
