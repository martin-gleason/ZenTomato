# C11 — An explicit App ID with MusicKit (O14)

> **CORRECTED 2026-08-25, and the correction is the useful part.** The first version of this
> chore said the app needed a `com.apple.developer.musickit` entitlement. **There is no such
> entitlement for an iOS app.** MusicKit is an **App Service** on the App ID, not a
> Capability, and App Services grant nothing that reaches a provisioning profile.
>
> Xcode said so in the error and it was read past as boilerplate: *"This likely is not a valid
> entitlement and should be removed from your entitlements file."*
>
> The owner had already enabled MusicKit correctly — under **App Services**, saved — before
> any of the diagnosis below was written. What follows is what remains true.

**Owner: the human.** It needs the Apple Developer account. The agent can verify the result
but cannot produce it.

**Done, as far as it goes.** The App ID is explicit, MusicKit is enabled on it, and the app is
signed with a profile for that App ID. `scripts/check-musickit-entitlement.sh` exits 0.

**What remains open is whether it changed anything.** The `-7013` errors were attributed to a
missing entitlement, and that attribution was wrong — so whether they persist, and whether the
music row now gives a real answer instead of *"couldn't be checked"*, is a question for the
device rather than a settled fact.

## What is wrong

The app is signed with a **wildcard provisioning profile**, `iOS Team Provisioning Profile: *`,
whose App ID is `KH6NBQRZBY.*`.

**Read the profile, not the app's entitlements, or this looks fine.** The app's own
`application-identifier` reads `KH6NBQRZBY.com.martingleason.ZenTomato` — specific, and
reassuring, and beside the point. A wildcard profile signs any bundle id under the team and
stamps the real one into the app; what it cannot do is grant a capability. That distinction is
why this went unnoticed for seven features.

The entitlements the app actually carries are exactly three:

```
application-identifier               KH6NBQRZBY.com.martingleason.ZenTomato
com.apple.developer.team-identifier  KH6NBQRZBY
get-task-allow                       true
```

**A wildcard App ID cannot carry a capability.** So there is no MusicKit entitlement, and that
is what every launch has been saying:

```
ICError Code=-7013 "Client is not entitled to access account store"
applicationQueuePlayer _establishConnectionIfNeeded timeout [ping did not pong]
Aborted fetching subscription status because privacy link needs to be displayed first
```

`-7013` is not noise. It is the literal answer.

**`SPEC.md` C2 asked for this and it never landed:** *"create the App ID with the MusicKit
capability."* Automatic signing has been falling back to the team wildcard ever since.

## What it costs today, honestly: less than it looks

`AppleMusicAvailability` already turns a failed read into `.couldNotBeChecked` rather than
"no subscription" — one quiet line, the timer untouched. **Playback from the local library
needs no entitlement**, which is why F4's device checks passed with music playing and why a
full sprint plays through today.

What the app cannot do is ever *know* whether there is a subscription. That one row is
permanently uncertain, and the console is permanently noisy.

**What it costs tomorrow is different.** TestFlight and the App Store both want a real App ID.
This stops being cosmetic the moment a build leaves this machine.

## Steps

1. **developer.apple.com → Certificates, Identifiers & Profiles → Identifiers → +**
   → **App IDs** → **App**

   | Field | Value |
   |---|---|
   | Description | ZenTomato |
   | Bundle ID | **Explicit** · `com.martingleason.ZenTomato` |
   | Capabilities | **MusicKit** ✓ |

   Leave everything else alone. The app needs no push, no App Groups, no iCloud — and a
   capability enabled here that the app does not use is a claim it cannot honour.

2. **A second App ID for the watch**, explicit, `com.martingleason.ZenTomato.watchkitapp`.
   No capabilities: the watch has no music, no store and no network of its own.

   *(This one may already exist — `C8` created a profile for it on 2026-08-24. Check before
   adding a duplicate.)*

3. **Xcode → Settings → Accounts → Download Manual Profiles.** iPhone connected.

4. **Both targets → Signing & Capabilities.** Confirm the Team. Xcode should now choose the
   explicit App IDs over the wildcard. If the watch target still shows a wildcard, deleting
   the stale profile from `~/Library/Developer/Xcode/UserData/Provisioning Profiles/` and
   downloading again is the reliable fix — that is what unstuck it last time.

5. `make device`

6. `scripts/check-musickit-entitlement.sh`

## Done when

That script exits 0 — the built app carries `com.apple.developer.musickit` and its App ID is
explicit rather than `*`.

Then, on the phone: open the app and switch music on. The console should no longer carry
`-7013`, and the music row should give a real answer about the subscription instead of
*"couldn't be checked"*.

## The failure mode to expect

**Xcode preferring a cached wildcard profile over the new explicit one.** It presents as
nothing changing at all: the build succeeds, the app installs, and the entitlements are the
same three. `C8` hit exactly this with the watch profile, and the fix was clearing the stale
profile rather than anything in the project.

The check script reports the App ID it actually found, so a stale profile is visible rather
than a mystery.
