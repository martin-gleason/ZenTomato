# C14 — three findings from the first real sprint on ZenPom 0.9.0 (2)

**Owner: both.** The agent triaged; two of the three need the owner's ratification
before any code is written.

The first sprint run on a shipped build produced more than the whole of F6b's
polish pass did. Recorded here together because they arrived together, but they
are three different kinds of thing and only one of them is a bug.

---

## 1. The alarm is silent when the phone is silent — **a defect**

**This is the serious one.** `SPEC.md` F2:

> Block ends fire through AlarmKit, **so the alert sounds through silent mode and
> through an active Focus.**

That sentence is the reason AlarmKit was chosen over a notification. A Pomodoro
timer that cannot tell you a block ended has no working state to degrade into —
`D19.2` says exactly that, in contrast to music, which may fail quietly.

`O6` had never been tested. It has now been tested in the field and it failed, so
it stops being an untested assumption and becomes a defect against the contract.

**A defect needs no delta.** `D22` established the precedent: a fix that makes the
app do what the spec already says is a defect fix, not a change to the spec.

### What is already established, and what is not

Verified by reading the shipped build rather than assumed:

- The configuration is idiomatic — `AlarmManager.AlarmConfiguration.timer(...)`
  with `stopIntent`, `attributes`, and `sound:`
- `sound` is `.default` when the setting is on, `.named("Silence.caf")` when off
- **`Silence.caf` is genuinely in the shipped bundle** — checked inside the
  archive, not in `project.yml`
- `soundEnabled` defaults to **true**, so a fresh install is not silent by default
- `soundEnabled` is **snapshotted when a block starts**, not read when the alarm
  fires (`TimerState.swift:127`)

**The cause is not established, and it will not be guessed at.** Three framework
assumptions have already been wrong this week — the MusicKit entitlement that
does not exist, the watchOS platform assertion, and the profile-versus-entitlement
confusion. Asserting a fourth would be the same mistake with a different noun.

### The check that separates the two candidates

**Candidate A — the app's own sound setting is off.** Then `Silence.caf` is
playing, correctly, and there is no bug at all: the alarm is silent in *every*
mode, not only in silent mode. The snapshot behaviour above makes a variant of
this possible too — turning sound on *during* a running block does not affect
that block's alarm, because the value was captured when it started.

**Candidate B — AlarmKit is not piercing silent mode**, and the premise `SPEC.md`
rests on is wrong or incomplete.

They are distinguished by **one observation**, and it needs the owner's device:

> With the app's sound setting **on**, and starting the block **after** confirming
> that, run a short block to completion twice — once with the ringer switch
> **on**, once **off**.
>
> - Sounds with the ringer on, silent with it off → **Candidate B.**
> - Silent both times → **Candidate A**, and the setting or the snapshot is the
>   story.

Everything downstream depends on which of those it is, so nothing is proposed
here beyond the check.

## 2. Music cannot be restarted during a break — **reported as a regression; it is not one**

The owner reports this worked in a previous build. **The code does not support
that**, and saying so plainly is more useful than agreeing.

Both halves of the behaviour date from F4's first commit, `e107dea`
*("Apple Music — library playback, skip-only, pause on breaks")*, and neither has
changed since:

- `isTogglable` is **false whenever any block is running** — break included
- the transport controls require `kind == .work`, so a break has neither

`MusicRowModel` states the consequence in its own documentation: *"During a break
it is 0."* Zero interactive controls, by design.

And the contract agrees — `SPEC.md` line 27:

> **Music during breaks** — Pauses. Resumes at the next pomodoro.

**So this is a change to the contract, not a bug fix**, and it needs `D25`
ratified before a line is written. What the owner is asking for is reasonable —
a break is exactly when somebody might want music — but it is a new decision.

**What might explain the memory.** Two F4 follow-ups closed paths that let music
play when it should not have: `5e1bf46` *("D20's silence never ended, and two
paths let the music back")* and `c8ac12d` *("Stop is not a one-way door")*. Before
those, music could keep playing when the app believed it had stopped. If a build
from that window was on the phone, music continuing through a break would have
looked like a feature. That is a hypothesis offered as one, not a finding.

## 3. No choice of alarm sound — **needs a delta**

> *"the default alarm sucks, and will be quite jarring to folks using an app with
> Zen in the name."*

The product argument is strong and the naming point is fair: an app called ZenPom
whose one piece of audio output is a klaxon is contradicting itself at the only
moment it speaks.

**It cannot be built as things stand.** A sound picker is a **seventh** setting,
and `PolishFenceTests` pins `AppSettings` at six fields — a bound that was
mutation-tested with *an alarm-sound picker specifically* as the seventh. That
fence was put there on purpose and must be moved deliberately, in a diff the owner
reads, rather than nudged.

`D24` proposes it. The framework does not stand in the way: AlarmKit already takes
either `.default` or `.named(_:)` from the app's bundle, and this app already
ships one bundled sound file, so the mechanism is proven — what is missing is
permission and the sounds themselves.

**It is also the cheapest of the three to get wrong quietly.** Bundled audio is a
licensing question as much as a design one, and this repository is GPL-3.0 and
public — which makes it `C10`'s business too.

---

## Order

1. **The alarm defect**, once the check above says which cause it is. It is the
   only one that breaks a promise the spec makes.
2. **`D24`, the alarm sound**, if ratified — it shares a file and a test surface
   with (1), so doing them together avoids touching `AlarmKitScheduler` twice.
3. **`D25`, music in a break**, if ratified. Genuinely optional, and the only one
   of the three that nothing is currently wrong about.
