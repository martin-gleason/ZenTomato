# C26 — ZenTomato is still the app's name where the store looks

**Owner: both.** The agent changes the build settings; only the owner can touch App Store Connect
and only the owner knows what the rejection actually said.
**Status:** open. Raised 2026-09-11 after the owner reported the App Store rejected *ZenTomato*.
**Blocks:** submission. Nothing else.

---

## The first thing to establish, because it decides the size of this chore

**The display name is already `ZenPom`, on all three targets** — `project.yml:114`, `:241`, `:337`,
and `Support/ZenTomato-Info.plist:8`. The home screen already says ZenPom, and has since `C9b`.

So **the rejection was not about what a user sees on their phone**, and a find-and-replace over the
156 files naming ZenTomato would be the wrong response to it. Three things still carry the old name
where a reviewer would meet it, and they are not equally costly:

| What | Where | Visible to | Cost |
|---|---|---|---|
| `CFBundleName` | `$(PRODUCT_NAME)`, which is the target name `ZenTomato` | the Settings app, some system dialogs, and the submitted binary | **small** |
| The App Store Connect record | the portal, not this repository | the store listing and the reviewer | **owner only** |
| `PRODUCT_BUNDLE_IDENTIFIER` | `com.martingleason.ZenTomato` and three children | nobody — but it is the app's identity | **do not touch, see below** |

## Do not change the bundle identifier

**A bundle identifier is not a name, it is an identity**, and changing it makes a different app.
Specifically: a new App ID and provisioning profile, a TestFlight lineage that starts from zero, and
— the one that matters — **a new container on the device, which orphans the SwiftData store.**

That store holds the distraction log. `O1` is *one real day's export, read beside the Rhodia*, it is
the first of the four Rhodia reviews the v1.5 spec names as the end of the milestone, and it has
never been run. **Changing the bundle identifier would destroy the data `O1` needs before `O1` has
happened.**

The identifier is invisible to users. `com.martingleason.ZenTomato` shipping an app called ZenPom is
ordinary and thousands of apps do it. If the store specifically objects to the identifier, that is a
different chore with a migration in it and it owes a delta.

## What to do

**`C26-T1` · owner: human · Find out what was actually rejected.** Read the rejection message and say
which it names: the App Store Connect app name, the binary's `CFBundleName`, the icon, or something
else entirely. **Nothing below starts until this is answered**, because each answer points at a
different file and two of them are not in this repository at all.

*Checkpoint:* the rejection's own words, pasted into this file.

**`C26-T2` · owner: agent · Make `CFBundleName` say ZenPom.** Set `PRODUCT_NAME: ZenPom` on the app
target in `project.yml`, leaving the target *name*, the directories and the identifier alone. This is
the smallest change that makes the submitted binary call itself ZenPom.

*Checkpoint:* `make generate && make check-release`, then read `CFBundleName` back out of the built
`Info.plist` — **out of the artefact, not out of `project.yml`.** The value is `$(PRODUCT_NAME)` and
a test that reads the source reads the variable rather than what it expands to.

**`C26-T3` · owner: human · Update the App Store Connect record.** Portal work. The app's name there
is independent of anything in this repository.

**`C26-T4` · owner: agent · A fence, if `T1` says the binary was the problem.** One assertion that the
built app's `CFBundleName` is ZenPom, so this cannot regress silently into a second rejection.
**Mutation:** set `PRODUCT_NAME` back to ZenTomato and watch it fail.

## Deliberately not in this chore

**Renaming the directories, the targets, the scheme, the `.xcodeproj` and the repository.** It is 156
files, it touches every import path and the CI workflow, and **it fixes nothing the store objected
to** — the store cannot see a directory name. It is consistency work, it is real, and it wants its
own gate rather than riding along inside a submission fix where a mistake costs a rejection cycle.

The repository is also cited as `ZenTomato` across plans, reviews and source comments, and
`conventions.md` is explicit that an identifier is cited by name and a tidy sequence bought with a
broken citation is a bad trade.

## The question nobody has asked yet

**Is ZenPom itself clear?** The owner picked it after ZenTomato was taken or rejected; a second
rejection for the same reason would cost another cycle. Worth a search of the App Store before `T3`
rather than after.
