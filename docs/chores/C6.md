# C6 — Correction pass

**Owner: the agent.** **Branch:** `C6/correction-pass` · PR #8 (F6 + F3b) merged 2026-08-24, so the
corrections that touch `00-deltas.md` can land.

**Opened as `F7a`, renamed to `C6` on the owner's instruction — the same file, the same findings.**
The misfiling is itself a finding and is recorded as such: this is agent-authored work that produces
no user-visible change, which makes it a chore. It was filed as a feature because `conventions.md`
then defined a chore as *"an operational task the human performs"*, leaving agent work that is not a
feature with nowhere to go. `C6-T0` closes that gap. It is also not a retrofit: `F<N>b` is a second
pass on an **already-shipped** feature, and `F7` has not been built.

## Why this exists

On 2026-08-24 I ran `cat > docs/plans/F7.md` on a file I had never opened, destroying 153 lines of
plan written at F1. The file is restored. But the interesting part is not the overwrite — it is that
the overwrite was the *fourth* symptom of one cause, and the other three were already in the tree
before I made it.

**The cause: authority is split across three documents and nothing reconciles them.** `SPEC.md` is the
contract. `00-deltas.md` holds the amendments to the contract. `docs/plans/F<N>.md` holds the decisions
taken at each gate. No single read gives you the truth, and the working loop in `CLAUDE.md` says
*"Re-read `SPEC.md`"* — which, followed literally, returns answers that are two months stale.

That is not a discipline problem to be solved with a firmer instruction. `CLAUDE.md` already says the
agent must re-read the spec, and I did. It says hooks are deterministic and prose is advisory, and that
is exactly the lesson here: **every failure below is one that prose asked for and no hook checked.**

## Three hardenings

`CLAUDE.md`: *"Hooks (deterministic; prose is advisory)."* All three are executable. None is a rule
asking anybody to be more careful, because the failures above all happened under rules that already
asked exactly that.

### H1 — A delta-integrity test *(catches findings 2 and 7)*

`ZenTomatoTests/DeltaIntegrityTests.swift`, reading the tree through `#filePath` exactly as
`StatsFenceTests` already does. Four assertions:

1. **Every `D<n>` cited anywhere in `ZenTomato/`, `ZenTomatoTests/` or `docs/` has a `## D<n>` heading
   in `00-deltas.md`.** This fails today, on D14, in five production files. It is the whole of finding 2
   and it would have fired the day the citation was written.
2. **Every delta has an explicit status** — `Ratified`, `REJECTED`, or `Proposed` — within three lines
   of its heading.
3. **No gaps in the numeric sequence**, so a missing D14 is caught even before anything cites it.
4. **The index in C6-T5 lists every delta**, so the index cannot rot.

Cheap, deterministic, and it turns "a decision nobody wrote down" from a thing discovered two features
later into a red test.

### H2 — A spec-amendment ledger, enforced by test *(catches finding 1)*

The agent may never edit `SPEC.md`. So the hook cannot apply amendments — it can only make the backlog
impossible to ignore.

`SPEC.md` gains one section, written by you:

```
## Amendments applied
D1 D3 D6b D10 D11 D18 …
```

`DeltaIntegrityTests` then asserts: **every delta marked `Ratified` that contains a `**Currently:**`
block — i.e. every delta that proposes new spec text — appears in that list.** Any that does not is
printed by name with its one-line summary.

Today that test fails with roughly a dozen names, which is the correct and useful outcome: the gap
becomes a number on a screen instead of a thing nobody has counted. The agent cannot close it; it can
only refuse to let it stay invisible. **If you would rather the test only warn, it can print without
failing — but then it is prose again, and prose is what got us here.**

### H3 — Close the read-before-overwrite hole *(catches finding 3, the actual mistake)*

The `Write` tool already refuses to overwrite a file that has not been read this session. `cat > file`
through `Bash` does not. **The guard exists and I went around it.** Two layers, because the first is
advisory and the second is not:

**H3a — a `PreToolUse` hook** in `.claude/settings.json` matching `Bash` commands that redirect into a
tracked file — `> path`, `>> path`, `tee path` — under `docs/`, `ZenTomato/` or `ZenTomatoTests/`.
It blocks with: *"This file exists and was not read this session. Read it, or use Write, which enforces
that for you."* This stops the mistake at the moment it is made rather than at commit.

**H3b — a pre-commit check**, `scripts/check-wholesale-rewrite.sh`, joining the existing four. For every
**modified** (not added) file under `docs/`, compute the proportion of the original that survives. If a
single commit deletes more than 60% of an existing document, fail with the diffstat and require an
explicit `Rewrites:` line in the commit message naming the file and the reason.

This has a real precedent in this repo beyond my overwrite: `docs/reviews/F1.md` records *"Deletion
damage, assessed"*, and earlier in this project a `git checkout HEAD --` destroyed 350 of 377 lines of
`BlockLiveActivity.swift`. **Wholesale replacement has now happened twice.** The threshold is
deliberately high so that ordinary editing is untouched and only replacement trips it.

## What C6 does not do

- **It does not edit `SPEC.md`.** Authority for the contract stays with you; H2 only measures the gap.
- **It does not renumber deltas.** Existing IDs are cited across production code.
- **It does not reopen any ratified decision.** D22 stands; F7a records it where it should have been
  recorded. The four withdrawn format questions stay decided as `F6.md` decided them.
- **It builds no feature.** No app code changes except `snapshotNamesUsed`'s comment and its new
  project half.

## Risks

- **H2 fails on day one, loudly, and stays failing until you amend `SPEC.md`.** That is the design. If
  a dozen names is too much at once, the honest alternative is to amend the spec in one sitting and
  keep the test strict — not to soften the test.
- **H3a can be a nuisance.** It fires on legitimate first writes to a new file. It is scoped to files
  that already exist, which is the whole of the risk it addresses.
- **Twenty days to the hard stop.** C6 is documentation and three small tests. If it competes with F7
  for the remaining time, C6 wins: F7 is one feature and the harness is every feature after it. But
  the honest framing is that doing both may not fit, and F7 is the one `SPEC.md` says to abandon
  cleanly.
