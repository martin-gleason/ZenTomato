# F3 — Todoist

**Gate:** requires F5 merged, your yes, **D5** recorded, and **D9 decided** — shipping intent means
the embedded-client-secret trade this feature was ratified on no longer holds. C3 is done; the client ID and
secret sit unused in the git-ignored `Config/Secrets.xcconfig`, read by nothing until this feature.
**Branch:** `F3/todoist`
**Spec:** OAuth sign-in; fetch projects, sections, tasks; picker; attach a task to the current pomodoro;
**complete** a task with one button at the end of a pomodoro. *Done when:* sign-in, pick, and complete
work against your real account.

## Summary

The integration with the strictest rule in the project attached to it: **the only write is completing a
task.** No create, no update, no comment, no move, no delete. `CLAUDE.md` makes this non-negotiable and
`SPEC.md` says it is "enforced by hook, not by prose" — F1 built that hook and F3 is where it matters.

The API version question the spec told me to answer at build time is answered: Todoist removed REST v2
and Sync v9 on **2026-02-10**, and the unified **API v1** at `https://api.todoist.com/api/v1` is the
only live surface. Object IDs from the old APIs do not carry over. This is D5 in `00-deltas.md`, and it
is the deprecation the spec's warning was about.

## Preconditions inherited from F1

Two guardrails were deliberately left incomplete at F1 because completing them then would have meant
guessing F3's shape. Both are F3's to close, and F3's gate does not pass until they are.

1. **Fail the build on a blank credential.** `Config/App.xcconfig` declares the Todoist keys empty,
   and nothing checks them, because at F1 nothing reads one and a skeleton that refuses to build
   without a credential is a gate that cannot run green. F3 is the feature that first reads them, so
   F3 adds the check — an empty client secret must stop the build and name the key, not produce an
   app that installs, launches, and fails at the sign-in screen with no explanation.

   Note this must not break a fork or a CI run with no secrets configured. The check belongs on the
   *Todoist code path*, not on every build.

2. **Bind method to path in the no-writes hook.** `scripts/check-todoist-writes.sh` currently
   enforces *which addresses* the app may contact, not *what it does* at each one — and
   `POST /tasks` (create a task, the single thing the no-capture rule exists to forbid) shares its
   path with `GET /tasks` (read tasks). Nothing is exposed today because there is zero Todoist code
   in the tree, but F3 is exactly when that stops being true. The check must understand the verb
   before the first request is written, not after.

   This was left open deliberately rather than guessed at: a checker built against an imagined HTTP
   shape is a second fail-open wearing a confident comment. Now that F3 chooses the shape, it can be
   enforced properly.

## Tasks

### F3-T1 — OAuth

You ratified OAuth as specced, with the client secret embedded in a personal build. Flow:

```
ASWebAuthenticationSession
   → https://todoist.com/oauth/authorize?client_id=…&scope=data:read_write&state=<random>
   → callback on our custom scheme, state compared against what we sent
   → POST https://todoist.com/oauth/access_token   (client_id + client_secret + code)
   → access token → Keychain
```

- `state` is a fresh random value per attempt and the callback is rejected if it does not match. This is
  the CSRF guard; without it the callback handler will accept a code from anywhere.
- Scope `data:read_write`. Todoist has no scope narrow enough to express "read everything, and close
  tasks" — read/write is the smallest that permits completion. **The scope therefore grants more than
  we use, and the F1 endpoint allowlist is what actually constrains us.** Worth stating plainly: the
  guarantee here is enforced on our side, not Todoist's.
- Token stored with `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` — not synced to iCloud Keychain, not
  readable while locked. It never touches `.env`, `UserDefaults`, or a log line.
- Sign-out clears the Keychain item and the entire local cache.

**Never logged.** The token, the code, and the secret are excluded from every log statement and every
error description, including the ones that print a failing request for debugging. F1's gitleaks hook
catches them in the tree; this is the part it cannot catch.

### F3-T2 — API client

One file, `TodoistAPI.swift`, holding the base URL, the version, and every endpoint constant — so the
next deprecation is a one-file diff rather than a search across the codebase. The F1 allowlist mirrors
this file, and CI fails if a Todoist URL appears anywhere else.

| Purpose | Method | Path |
|---|---|---|
| Projects | GET | `/projects` |
| Sections | GET | `/sections` |
| Tasks | GET | `/tasks` |
| **Complete** | **POST** | **`/tasks/{id}/close`** |

That is the complete list. Anything else added to it is a visible, reviewable diff in a committed
allowlist file, which is the property we designed F1's hook for.

- v1 responses are cursor-paginated (`{results, next_cursor}`); the client follows cursors to
  exhaustion. **All** projects, sections, and tasks are fetched — `SPEC.md` says the picker shows
  everything, so there is no filtering at the API layer.
- Rate limits are confirmed against the live docs at implementation time and pinned in a comment next
  to the client. Our access pattern is deliberately quiet — refresh on foreground and on an explicit
  pull-to-refresh, never per keystroke — so we should sit far under any published ceiling. The picker's
  search filters the local cache, not the API.
- Errors: `401` ⇒ token rejected, clear it and prompt re-auth. `429` ⇒ respect `Retry-After`, back off.
  Offline ⇒ serve the cache, and disable the Complete button with a plain explanation rather than
  queueing a write to replay later. **A queued completion is a write we cannot see, and the one rule
  here is that we can always see our writes.**

### F3-T3 — The cache

`CachedProject`, `CachedSection`, `CachedTask` in SwiftData — mirrors of Todoist's rows and nothing
else. `CLAUDE.md`: "No local projects, tags, or task models beyond a cache of Todoist's."

Concretely, this means no field the app invents. No local `isFavourite`, no local ordering, no local
notes, no parent/child structure of our own devising. If a future screen wants to sort tasks a way
Todoist does not, the answer is that it does not get to. The reviewer agent is told that any local model
that could become a task hierarchy is a failure, and the way to stay clean is for these three types to
be dumb copies with a `syncedAt` and nothing more.

Refreshed on foreground and on pull-to-refresh. Full replace, not merge — simpler and correct, since
the cache is disposable by construction.

### F3-T4 — Picker

Project → section → task, hierarchical, all projects visible. A local search field filtering cached
titles.

**This is not a capture surface.** No add button, no empty-state "create your first task" prompt, no
text field that could be mistaken for one. `CLAUDE.md` calls the no-capture rule a standing rule from
your productivity system rather than a feature gap, so an empty project shows "No tasks in this
project" and stops there. The search field needs a deliberate design nudge — a search box that returns
nothing is exactly where other apps offer to create the thing you typed, and we must not.

Selecting a task attaches it to the current/next pomodoro. Selecting nothing attaches the **project**,
per the spec's vocabulary section. A pomodoro therefore always has an attachment; it is a task or a
project, never neither.

### F3-T5 — Attach and complete

- `PomodoroSession` and `Distraction` gain `taskID`, `taskTitle`, `projectID`, `projectTitle` — the
  snapshot columns F5 described. Optional, because rows captured before F3 merged legitimately have none.
- The Complete-task button joins the end-of-pomodoro sheet from F5-T2, alongside the sentence fields.
  One button, one `POST /tasks/{id}/close`.
- Optimistic in the UI, reconciled against the response; on failure the task returns to its uncompleted
  state with an explanation. No silent failure, and no retry queue — same reasoning as offline writes.
- Completing a task does **not** end the pomodoro, and ending a pomodoro does not complete the task.
  They are independent, and the sheet is simply where both happen to live.
- **The completion is recorded locally** (D11): task id, a snapshot of the title, and the timestamp.
  Append-only, and written only after Todoist confirms the close — a local row claiming a completion
  that failed would be worse than no row. This is a record of something this app did, not a task model:
  no hierarchy, no local task list, nothing that could grow into one.

## Tests

| Test | Asserts |
|---|---|
| `oauthStateMismatchRejected` | callback with a wrong `state` ⇒ rejected, no token stored |
| `tokenGoesToKeychainOnly` | token absent from `UserDefaults` and from any log sink |
| `tokenNeverAppearsInErrors` | a failing request's error description contains no credential |
| `paginationFollowsCursor` | 3 stubbed pages ⇒ all rows, no duplicates |
| `completeHitsCloseEndpoint` | exactly one request, exactly `/tasks/{id}/close` |
| `noMutatingRequestsOtherThanClose` | full stubbed session; every non-GET is the close call |
| `unauthorizedClearsToken` | `401` ⇒ Keychain cleared, re-auth prompted |
| `rateLimitBacksOff` | `429` + `Retry-After` ⇒ honoured |
| `offlineServesCacheAndDisablesComplete` | no network ⇒ picker works, Complete disabled |
| `projectAttachedWhenNoTaskChosen` | session has `projectID`, `taskID == nil` |
| `titleSnapshotTakenAtAttach` | later rename does not alter the stored session |

`noMutatingRequestsOtherThanClose` is the runtime companion to F1's static hook — one checks the source,
the other checks actual traffic. Both, because this is the rule the project cares most about.

## Risks

- **API v1 details** — v1 is recent and this plan is written from its published shape. Exact field
  names, cursor semantics, and rate limits are confirmed against the live documentation on the first
  day of the build. If anything material differs from the table above, that is a plan amendment before
  code, not a discovery in review.
- **Embedded client secret** — accepted, and acceptable only because this build is never distributed.
  If ZenTomato is ever handed to another person, this becomes a blocker (see D6).
- **Scope of `data:read_write`** — broader than our usage. Constrained by the allowlist, not the token.
- **A large account** — thousands of tasks across every project. Pagination and the local search must
  stay responsive; if they do not, the fix is indexing the cache, not filtering server-side, because the
  spec requires everything to be visible.
