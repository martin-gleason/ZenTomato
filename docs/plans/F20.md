## Paraphrasing it back

> *"I do think we need more testing on task/project selection, as I want to ensure that a user can pick a
> task or seris of tasks and reorder them."*
> *"let's set up a whole new feature branch for the tasks."*

**Two things, and reading them apart is the whole of this plan.** One is a *testing* request about
something that already exists. The other is a *feature* that does not exist at all.

## THE FIRST THING THIS PLAN FOUND: HALF OF IT IS ALREADY BUILT

**Picking a series of tasks works today.** `PlanBuilderView:170` holds
`@State private var selections: [SessionPlanStore.Selection]` — an array, bound into the pickers, passed
whole to `replacePlan(with:)`. Multi-select into a plan is shipped.

**And the order is already a stored field.** `SessionPlanItem.position: Int`, with its own doc comment:
*"Where this sits in the list, counting from zero… An order has to be written down somewhere, and with no
links between rows this is the only place it can go."*

**So this feature adds no column, no model and no concept.** What is missing is precisely two things: a
gesture, and one method on the store. `SessionPlanStore` has `replacePlan`, `stepOver`, `remove` and
`clear`; it has no `move`. No view in the app contains `onMove`, `EditButton`, or `.move(fromOffsets:)` —
checked across every file in `ZenTomato/Views/`.

**This changes what the owner asked for into something much smaller**, and it means the *testing* half of
the request is not a gap to fill but a claim to verify on the device — which is `T1`.

## The second thing it found: the model says items are never edited, and it says why

`SessionPlanItem`'s header is the most forcefully written comment in this codebase, and it is aimed at
this feature:

> *"An ordered list of tasks is one field away from being the local copy of Todoist this app is forbidden
> to keep, and the way it happens is never a bad decision — it is four good ones. 'The plan should show
> which ones are done.' 'It should sort by what's due first.' 'Grey out the finished ones.' Each is one
> small commit, each is obviously useful, and the destination is a second task model nobody designed."*

And `position`'s own neighbour: *"Entries are only ever created together, when a plan is built, and are
never edited afterwards."*

**Reordering edits `position` after creation, so that sentence stops being true, and the plan has to say
whether that matters.** It does not, and the reason is in the comment two lines above it: `position` *"is
a property of the list, not of the thing in Todoist — it says nothing whatsoever about the task, and
Todoist neither knows nor cares about it."* Editing a fact about the list is not a step toward a local
copy of Todoist; editing a fact about the **task** would be. The fence that matters —
`planItemHasFourStoredProperties`, which asks the database what columns the type has and fails on a
fifth — is untouched, because reordering needs no new column.

**That distinction is the load-bearing argument of this feature** and the sentence in the model must be
corrected rather than left to contradict the code.

## The third thing: THE ORDER MUST NOT REACH TODOIST

`CLAUDE.md`, non-negotiable: *"Todoist is the only task hierarchy… The only write to Todoist is complete
task. Never call create, update, or comment endpoints."*

**Reordering a plan must therefore be local and invisible to Todoist.** A reasonable-sounding next
thought — *"it should reorder the tasks in Todoist too"* — is forbidden, not merely out of scope, and the
pre-commit hook greps for those endpoints. Stated here so that nobody has to rediscover it while holding
a half-built drag gesture.

## The rulings this plan needs · owner: **human**

### Ruling A — WHEN can the plan be reordered? THIS IS THE GATE

Three answers, and they are three different features.

| | What it means | Cost |
|---|---|---|
| **1 · While building the plan only** | The list is reorderable in `PlanBuilderView` before *Save*. The plan the timer reads is never touched. | **S.** One `onMove`, one store method, no engine involvement at all. |
| **2 · Any time the timer is idle** | Including between blocks, mid-sprint. Items already worked are behind the cursor and cannot move; upcoming ones can. | **M.** Needs a rule for what the cursor means after a move, and the plan bar has to redraw. |
| **3 · Any time, including mid-block** | The list can be dragged while a pomodoro runs. | **L, and the agent recommends against it.** |

**Why option 3 is a trap and not just expensive.** `takeNextAttachment()` is called once, at the moment a
focus block *begins*, and the attachment is then frozen onto the timer row — deliberately, so that
*"renaming a task in Todoist during a 25-minute block must not change what the record says you were
working on"* (`SessionAttachment:29`). Dragging the list during a block cannot change what the running
block is attached to, so the gesture would appear to work and do nothing to the thing in front of you.
That is worse than not offering it.

**The agent recommends option 1 for tomorrow**, with option 2 as its own later unit if the owner wants
it. Option 1 is the request as stated — *"pick a task or series of tasks and reorder them"* is a planning
act, and `SessionPlan`'s own header says planning is the point: *"choosing what to work on is a planning
act, and doing it eight times an afternoon at the start of each block is the wrong moment for it."*
**Option 1 is that sentence implemented; option 2 partially contradicts it.**

### Ruling B — what happens to the cursor if option 2 is chosen?

Only if Ruling A is 2 or 3. If the plan is `[A, B, C, D]` with two worked and the cursor at 2, and `D` is
dragged above `C`:

- **Option i — the cursor stays at 2** and now points at `D`. Simple, and it silently changes what the
  next block will be.
- **Option ii — worked items are frozen** and cannot be moved or moved past. Honest, and it needs the
  list to draw two zones.

The agent would pick **ii**, because `currentIndex` is *"a fact about the list"* and a move that changes
what it means without saying so is the kind of quiet reassignment this codebase refuses elsewhere.

### Ruling C — does removing an item come with this?

`SessionPlanStore.remove(_:)` exists but nothing in the views calls it. If a reorder gesture is being
added to that list, an owner may reasonably expect swipe-to-delete in the same breath — and the store is
already able. **It is one line of view code and it is not in the request**, so it is asked rather than
assumed.

### Ruling D — the position in the order, and the baseline waiver

`D54` needs ratifying and a position in `zenpom-v1.5.md`. **The agent proposes last, at 16**, after `F2f`:
the plan surface is already usable, this is a convenience on top of it, and v1.5's order is explicitly
paced by review capacity rather than build time.

### `F20-T1` — What it does today · owner: **human** · *no code*

**The owner asked for testing, and this is it — before anything is built.** Multi-select is shipped;
nobody has watched it work.

Pick a project **and** two loose tasks in one sitting, save the plan, then run three pomodoros and answer:

1. Did all three land in the plan, in the order you picked them?
2. Did pomodoro one attach to the first, two to the second, three to the third?
3. Does the plan bar say the right count and the right next title?
4. **Did you want to reorder them, and at what moment?** — this answers Ruling A from use rather than
   from argument, which is worth more than either option's write-up.
5. What happened when you picked a project and a task *from inside that same project*? The model says a
   plan is *"flat even when it holds a project and tasks from inside that same project"*, and nobody has
   looked at what that reads like.

*Checkpoint:* the owner's answers. **If multi-select turns out to be broken, that is a defect fix and it
proceeds without a gate** — and it changes what the rest of this feature is for.

### `F20-T2` — The store can move an item · owner: **agent** · *no user-visible change*

One method, in the same shape as its four neighbours: it returns `false` when the write is refused rather
than throwing, because that is what `replacePlan`, `stepOver`, `remove` and `clear` all do and a fifth
convention in one type is a defect waiting to happen.

**It renumbers `position` across the whole list, not just the two items moved.** Swapping two numbers
leaves gaps and duplicates the moment a third move happens, and `position` is read by a sort — so the
list must come out of every move as a contiguous run from zero. A test asserts the *whole sequence*, not
that two items swapped.

*Edges:* a one-item plan · moving to the same index · an index out of range · a move on a plan that
cannot be read at all.

*Checkpoint:* the positions asserted as a whole list, before and after, across four moves.

### `F20-T3` — The gesture · owner: **agent**

`onMove` on the plan list in `PlanBuilderView`, bounded by Ruling A.

**The list is 368 lines and the file cap is 400.** This will not fit comfortably; the plan expects to
move the list into its own view first, which is a refactor and should be its own commit so the gesture's
diff is readable.

*Checkpoint:* drag a three-item plan into a new order on the simulator; the saved plan matches.

### `F20-T4` — The model stops contradicting the code · owner: **agent**

`SessionPlanItem`'s *"never edited afterwards"* becomes true-as-written or is corrected with the argument
above — that a fact about the **list** is not a fact about the **task**. And
`planItemHasFourStoredProperties` is re-run and re-recorded, because the whole reason that fence exists
is features like this one.

**`SessionPlan`'s header also says an item is *"not reordered"*** (`:40`). That sentence is about what
`stepOver` does and will read as a general prohibition after this ships. Both get fixed in one commit
with the reasoning, not silently.

*Checkpoint:* the fence green, the two comments true.

### `F20-T5` — Reordered on the phone · owner: **human**

Build a plan of four, drag the last to the front, run two pomodoros, and confirm the log attached them in
the new order — read in the export, not in the app.

*Checkpoint:* recorded as an `O<n>`, closed by the owner with a build number.

## Mutations

| Mutation | The named test that must fail |
|---|---|
| `F20-M1` · Swap the two moved items' `position` values and leave the rest alone | the whole-sequence assertion in `T2` — a swap looks right for one move and produces duplicate positions on the second |
| `F20-M2` · Make `move` return `true` when the write was refused | the refused-write assertion — the list redraws as though it had moved and the database disagrees |
| `F20-M3` · Add a fifth stored property to `SessionPlanItem` | `planItemHasFourStoredProperties` — the fence this feature is most likely to erode |
| `F20-M4` · Reorder by rewriting the plan through `replacePlan` | the identity assertion — `replacePlan` deletes and reinserts, so `currentIndex` would silently point at a different task |

**`F20-M4` is the interesting one and it is the shortcut a reasonable person takes.** Reordering "by
rebuilding the plan" is one line and it destroys the cursor, which is the load-bearing decision of the
whole plan feature (`SessionPlan:19` — *"THE CURSOR LIVES HERE AND NOT ON THE ITEMS"*). The mutation
exists because the wrong implementation is shorter than the right one.

## Evidence

`make ci` in the PR, with the full suite's count. Plus `F20-T1` and `F20-T5`, closed by the owner.

**Four mutations run and seen to fail.** And one thing that is *not* evidence and is named as such: there
is no UI test target, so the drag gesture itself is verified on the simulator and the device by hand, the
same way `F8`'s `onFit` closure is.

## Scope fence

**The order never reaches Todoist.** Not as a write, not as a "sync", not as a preference. The only write
is *complete task*, a hook greps for the rest, and reordering someone's Todoist project from a pomodoro
app is a different product.

**No fifth column on `SessionPlanItem`.** Not *done*, not *skipped*, not *due*, not *priority*. The model's
own comment names those four good decisions and where they lead; this feature touches `position` and
nothing else.

**No sorting.** *Reorder* is a person dragging a row. *Sort by due date* is the app holding an opinion
about Todoist's data, which is the local-copy problem wearing a different hat.

**Not the watch, not an App Intent, not the picker's own search** (`F19`), **and not mid-block
reordering** unless Ruling A says otherwise — and the plan argues it should not, because the gesture
would appear to work and change nothing about the block in front of you.
