**Source decision:** `docs/plans/parked.md`, "Instructions, and an explainer of the Pomodoro

**Depends on:** nothing. **Blocks:** `F8`, on the vocabulary. See *Why this goes first*.

## Paraphrasing it back

zenpom explains nothing. Every control is legible to the person who built it and to nobody else, and
the technique itself is assumed. F9 fixes that with two pieces — **what each control does**, and **a
short explainer of the Pomodoro technique** for somebody meeting it here.

The owner writes the words. A design tool places them. The agent executes. That is a departure from
the 5% dial and it is deliberate.

**This is not starting from zero.** Draft one exists at `docs/verbiage/ZenPom Instructions.md`,
written 2026-08-26, and it has already been checked against the source in
`docs/verbiage/NOTES-on-draft-one.md`. The tone is right — it explains the method before the buttons,
which is the correct order, and it says what the app is for in two sentences. F9 finishes it; it does
not restart it.

## Why this goes first, before `F8`

**`F8` would settle the vocabulary by force, badly.** The planner has to print sentences like
*"3 × 25 minutes with two 5-minute breaks"*, and it cannot print them without naming what it is
printing.

The words are genuinely unsettled today, and both directions of the error are already on the record:

- The owner's `F8` request said *"3 sprints over 120 minutes"* — but a sprint here is a whole set of
  pomodoros, so three of them at current defaults is **five hours, not two**.
- Draft one has the mirror-image slip: *"One full set of this is a Pomodoro!"* — teaching a word the
  app then contradicts, since the setting is `pomodorosPerSprint` and the Settings section is headed
  **Sprint**.

Neither is careless. They are the same unsettled vocabulary seen from two sides. The explainer is
already the place the app teaches the words, so it is the cheapest place to settle them — and
settling them is a **prerequisite** for `F8`, not a nicety.

## Decomposition

Six tasks. The first two deliver **nothing user-visible** and are labelled so.

### Foundational — no user-visible change

#### `F9-T1` — Settle the vocabulary · owner: **human + agent**

Produce the glossary the app and its copy both obey: **block · pomodoro · sprint · short break ·
long break · session plan · distraction (internal / external) · stopped early**.

The two live disputes it must rule on, both evidenced above: *what is one pomodoro* and *what is a
sprint*. Everything else is likely already consistent and needs confirming rather than deciding.

The agent assembles the evidence — every user-facing string and setting name in the source, with what
each currently implies. **The owner rules.** The ruling is recorded as a `D<n>`, because it binds
`F8` and any later copy.

**RULED 2026-09-09 by the owner: one pomodoro is one focus block; a sprint is the set of them.**
This is what the code already says — `pomodorosPerSprint`, the Settings section headed **Sprint**,
and `SettingsView`'s note that *"a sprint of one pomodoro is a real setting."* **No rename, no code
churn.** Two consequences follow, and they are the whole of `T1`'s remaining work: draft one's *"One
full set of this is a Pomodoro!"* is corrected, and `F8`'s phrasing becomes *"3 pomodoros over 120
minutes"* rather than *"3 sprints"*.

*Checkpoint:* a glossary table exists, ratified, and `F8`'s plan can cite it.

#### `F9-T2` — The vocabulary fence · owner: **agent**

A test that fails the build when shipped Swift puts a retired word in front of a user.
`PolishFenceTests` already does exactly this for parked vocabulary and is the model to extend rather
than a new thing to invent.

**Mutation, named now and run before this task is called done:** change a user-facing string to call
a whole set "a Pomodoro" and confirm the fence fails, with the count recorded. A fence that has never
been seen to fail is not evidence.

*Checkpoint:* the mutation is applied, the suite is seen to go red, the code is restored.

### Vertical slices — each one a thing you can hold

#### `F9-T3` — The help surface exists and is reachable · owner: **agent**

One screen carrying draft one's copy with **the three factual corrections applied, and nothing
else**. Ugly is fine here; wrong is not.

**RULED 2026-09-09 by the owner.** The original plan said *placed as-is*, which was defensible when
the destination was a Settings help sheet only a curious person would open. First-run placement
changed that: the first sentence a stranger reads would teach them a word the app then contradicts,
which is the precise failure `F9` exists to fix.

**The division of labour survives it.** The agent is not authoring copy — it is applying three
corrections that are already written down and evidenced in `NOTES-on-draft-one.md`, one of which is
the sprint/pomodoro sentence `T1` has now ruled on. Every other word stays the owner's, untouched,
until draft two.

**RULED 2026-09-09 by the owner: first run, and thereafter available in Settings.** The agent
recommended Settings-only; the owner ruled otherwise, and the recommendation is recorded rather than
erased because its reason still governs *how* this is built.

`parked.md`'s warning stands and becomes a constraint rather than an objection. **Three fences, so
"first run" does not become an onboarding flow nobody wanted:**

1. **One screen, not a sequence.** No paging, no progress dots, no multi-step wizard.
2. **Skippable at first sight, and shown exactly once.** A persisted flag, and the same screen stays
   reachable from Settings forever after.
3. **It never appears again on its own** — not after an update, not after a reinstall-over.

**A collision that has to be resolved before this can be built.** First run is *already occupied*:
`C9` records that what a tester actually sees on first launch is a screen asking for a Todoist
personal API token. So `F9-T3` is not "add a first-run screen", it is **"order two first-run
surfaces"**, and the order is a real decision:

- **Explainer first** — the app says what it is before it asks for a credential. Better for anybody
  who is not the owner, and it is the sequence draft one's own *"not necessary"* claim implies.
- **Token first** — the current behaviour, unchanged.

**RULED 2026-09-09 by the owner: the explainer comes first, then the token screen.** The app says
what it is before it asks for a credential. This also removes a quiet contradiction: draft one claims
Todoist is *"not necessary"*, and a token wall as the first thing anybody sees says otherwise.

**It carries an obligation.** Explainer-first is only honest if the token screen is genuinely
skippable, and `C9` records that **nobody has run a first launch without a token.** That check moves
from "someday" to a precondition of `T3`, because the copy and the sequence now both assert it.

*Checkpoint:* on a **fresh install** on the device, the explainer appears once, is skippable, does
not reappear on next launch, and is still reachable from Settings.

#### `F9-T4` — Draft two · owner: **human**

The owner's writing task, and the largest single piece of human work in v1.5.

**Three factual corrections already found** (`NOTES-on-draft-one.md`, unedited and the owner's to
accept or reject):

1. *"One full set of this is a Pomodoro!"* — the app calls that a **sprint**.
2. *"At the end of the focus sprint you can write a sentence"* — it is at the end of the **block**.
   As written it promises a sheet where one never appears.
3. *"once the timer starts, it doesn't stop"* — true of **pausing**, which deliberately does not
   exist. But a block can be **stopped**, and the export has a whole *"Stopped early"* section that
   records the reason. Worth a clause, because *"you can stop, and it is written down"* is a feature
   of the log rather than an admission.

**Four things still unwritten**, from `parked.md`'s own scope: the **Skip** and **Stop** music
controls · the **attachment line**, including that it is frozen while a block runs · the **sprint
dots** · what the **six settings** do.

Plus the small copy fixes already listed, and dropping the trailing editor timestamp.

*Checkpoint:* draft two lands in `docs/verbiage/`, and the agent re-runs the same
checked-against-the-source review that produced the notes on draft one.

#### `F9-T5` — Placement · owner: **agent, with Claude design in the loop**

Draft two placed and animated. **First time a design tool is in this project's loop**, which is worth
naming at the gate rather than discovering mid-build: it is a new step in the pipeline, not just a
new screen.

*Checkpoint:* the placed screen on the device, screenshotted into the PR.

#### `F9-T6` — The new surface is accessible · owner: **agent, then human on hardware**

VoiceOver and AX5 on the help surface. This project has an open finding that the countdown was
coarsened to whole minutes to cut announcement spam and **nobody has confirmed on hardware whether
iOS re-announces at all** (`O8`). A new text-heavy screen is where that gets tested properly.

*Checkpoint:* the device check, recorded as an `O<n>` and closed by the owner with the build number.

## Two further rulings, 2026-09-09

**Sequencing: place draft one as-is first, draft two after.** `T3` and `T5` do not wait on the
owner's writing task. The cost is one round of re-placement when draft two lands, bought deliberately
so the owner writes final copy for a screen he has already seen and held.

**The learning dial does not move. It stays at 5%, and `F9`'s copy is a stated exception.** The dial
counts who writes Swift, and the owner still writes none. `parked.md` set this division of labour on
purpose; recording it as an exception keeps the dial meaningful rather than quietly eroded.

## Scope fence

**Everything in this plan is text and one screen.** A first-run *screen* is in scope as of the
2026-09-09 ruling; a first-run **flow** is not, and the three fences on `T3` are what keeps those
apart. Specifically not in F9, and each would need its own gate: a multi-step onboarding sequence ·
any change to what a control *does* · a capture surface of any kind · settings beyond explaining the
six that exist · the About screen, which is `C22`-blocked.

## One question this raises that is not mine to answer

Draft one says zenpom is *"built to work with Todoist, but it is not necessary."* That is **probably
true** — the app records blocks with no task attached and the export has a *"No task"* line — but
`C9` flagged first-launch-without-a-token as an open question and **nobody has run it.** What a
tester actually sees on first launch is a screen asking for a Todoist personal API token.

**This is the first claim a new user will test.** It should be confirmed on a fresh install before it
ships in writing, because being wrong here is worse than being silent. Proposed as a new owner item
rather than an assumption inside `F9-T4`.
