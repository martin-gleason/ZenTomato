# F2 — Timer engine

**Gate:** requires F1 merged, your yes on this plan, and ratification of **D3** (AlarmKit).
**Branch:** `F2/timer-engine`
**Spec:** Pomodoro / short / long break cycle per settings, **and the screen that sets them** (D10).
Survives backgrounding. *Done when:* unit tests cover the cycle and a backgrounded timer ends on time
on a device.

## Summary

The engine and the alerting. Two ideas carry this feature, and both are decisions to make once and
never revisit.

**The timer does not count.** It records the wall-clock instant the block ends and derives everything
from that. A `Timer` exists only to refresh the label sixty times a minute; it is never the source of
truth. This is the difference between a timer that survives backgrounding and one that quietly loses
four minutes because iOS suspended the process — and the spec's *Done when* is precisely that case.

**The alert is a system alarm, not a notification.** Per D3, block ends fire through AlarmKit, so they
sound through silent mode and through an active Focus. A Pomodoro user is, by definition, in a Focus
session; an alert a Focus can swallow is not an alert.

**Proposed spec delta:** D3 — ratified. See `00-deltas.md`.

## Decisions taken at this gate (2026-08-22)

Three things the roadmap draft left to me that were not mine to decide.

**A skipped work block does not count as a pomodoro.** It is recorded with `wasAbandoned = true` and
excluded from every count in F6. The reasoning is the Rhodia review: a number is only worth reading if
it means what it says, and "pomodoros" has to mean blocks finished rather than blocks begun — otherwise
an afternoon of bailing out reads as a productive one. The rows stay on disk, so if the pattern of what
you abandon turns out to be interesting, F6 can surface it later without re-capturing anything.

**Auto-start carries you through a sprint, not into the next one.** When the long break ends the engine
returns to idle and waits, even with auto-start on. Four pomodoros and a long break is a natural
stopping point, and a timer that quietly begins a fifth while you have walked away is a timer you stop
trusting — it also fills your stats with abandoned rows generated by an empty room. Restarting is one
tap. The setting's name is read as "auto-start next *block*", which is exactly what it now does.

**The Live Activity names the task once there is one.** F2 shows the block kind — "Focus — 24:58" —
because no task exists yet. F3 replaces that label with the attached Todoist task. A glance at a locked
phone should say what you are meant to be doing, not merely that a timer is running; the second is
already obvious from the countdown. Noted for F3: this puts task titles on a screen anyone can read
over your shoulder, which is a trade worth remembering rather than rediscovering.

## The cycle

```
        ┌──────────────────────────────────────────────┐
        ▼                                              │
  ┌──────────┐   n < perSprint   ┌────────────┐        │
  │   WORK   │──────────────────▶│ SHORT BREAK│────────┘
  └──────────┘                   └────────────┘
        │ n == perSprint
        ▼
  ┌────────────┐
  │ LONG BREAK │──▶ sprint complete, n resets to 0
  └────────────┘
```

With defaults: work, short, work, short, work, short, work, **long**. The fourth pomodoro is followed by
the long break, not a short one — the long break ends the sprint rather than interrupting it.

Edge case worth stating because it is off-by-one bait: `pomodorosPerSprint == 1` means every work block
is followed by a long break and no short break ever occurs. That is correct, and it has a test.

## Tasks

### F2-T1 — State model

```swift
enum BlockKind { case work, shortBreak, longBreak }

@Model final class TimerState {          // exactly one row; the resumable truth
    var kind: BlockKind
    var startedAt: Date
    var endsAt: Date                     // ← the only thing that matters
    var completedInSprint: Int
    var sessionID: UUID
    var isRunning: Bool
}

@Model final class PomodoroSession {     // one row per finished block
    var id: UUID
    var kind: BlockKind
    var startedAt: Date
    var endedAt: Date
    var wasAbandoned: Bool
    // F3 adds taskID/taskTitle/projectID/projectTitle; F5 relates distractions here
}
```

`PomodoroSession` is created in F2 rather than deferred to F6, and that is a judgment call worth naming
so the reviewer does not have to guess: the engine is the only thing that knows a block finished, so
the engine is what must record it. F6 reads these rows; it does not create them. F2 writes no field it
does not itself populate — the Todoist columns arrive in F3, attached to the same model.

### F2-T2 — The engine

`@MainActor @Observable final class TimerEngine`. Public surface: `start()`, `stop(reason:)`, and a
derived `remaining: Duration`.

**There is no `skip()`** (delta D13). A pomodoro is indivisible — it finishes or it is void — and an
exit that costs one tap is not an exit from a focus block, it is a way of not having one. The only way
past a block is to let it end.

**`stop(reason:)` takes the reason as a parameter rather than trusting the screen to collect one.**
A second caller added later cannot quietly abandon a block without saying why; the requirement lives
in the type. The reason is stored on `PomodoroSession.abandonReason`, which is `nil` for every block
that ran to its end.

**No controls on the Live Activity at all** (delta D12). Not pause, and — since the device review —
not dismiss either. The card reads; it does not act. A Lock Screen button reaches the app through an
App Intent that does nothing if iOS has reclaimed the app's memory, so a dismiss could silently reach
nothing and be reconciled later as a *completed* block. Abandoning happens in the app, where the
engine is certainly running.

**No pause.** This deserves a sentence because AlarmKit's own guidance suggests a pause/resume control
in a countdown Live Activity, so its absence will look like an oversight. It is not. `SPEC.md`'s
customization list does not include pause, a paused pomodoro is not a pomodoro under the method, and a
pause button on the Lock Screen is the single easiest way to turn a focus block into a soft
twenty-minute negotiation with yourself. The Live Activity offers **dismiss** only, which ends the
block and records it with `wasAbandoned = true`. If you want pause, it is a spec delta and I will build
it — but I would rather you had to ask.

**Deriving the display:** `remaining = endsAt.timeIntervalSinceNow`, clamped at zero, recomputed on a
display-linked refresh. A `Timer` that stops firing while suspended therefore costs nothing.

**Clock skew.** `endsAt` is an absolute `Date`, so if the user (or a timezone change, or NTP) moves the
system clock, a block can appear to jump or complete instantly. Guard: alongside `endsAt` the engine
stores the boot-relative deadline from `ContinuousClock`. On foreground it compares the two; if they
disagree by more than a few seconds the wall clock moved, and the continuous clock wins. This is the
one place the code is more complicated than it looks like it needs to be, so it gets a comment
explaining why rather than a future reader simplifying it back into a bug.

**Settings changed mid-sprint** apply at the next block boundary, never to the running block. Shortening
the work length while a work block runs must not retroactively end it. Tested.

### F2-T3 — AlarmKit and the Live Activity

- Request `AlarmManager` authorization at first start, not at launch. Asking for an alarm permission
  before the user has ever started a timer is how permission prompts get denied.
- On block start, schedule a countdown alarm for `endsAt` carrying typed metadata: block kind, sprint
  position, and (from F3) the task title, so the Lock Screen says *"Ch.3 draft — 4:58"* rather than
  *"Timer."*
- Widget extension target `ZenTomatoActivity` with the countdown Live Activity: remaining time, block
  kind, task title, dismiss. Lock Screen and Dynamic Island presentations.
- On skip, stop, or settings-driven reschedule, **cancel the outstanding alarm first**. A stale alarm
  firing four minutes after the user skipped is the most likely user-visible bug in this feature and it
  gets its own test.

**Authorization denied.** There is no notification fallback — you chose AlarmKit alone, and building a
second alerting path would double F2's test matrix for a case that resolves with one tap. Instead, if
authorization is denied the app shows a blocking explainer with an Open-Settings button, because a
Pomodoro timer that cannot reliably tell you a block ended has no working state to degrade into. This
is deliberate, and it is the honest answer to the reviewer's "notification permission denied" check.

### F2-T4 — Background and relaunch

- On background: state is already persisted; the alarm is already scheduled. Nothing to do — which is
  the point of the design.
- On foreground/launch with `isRunning`: if `endsAt` is in the future, resume the display. If it is in
  the past, the block finished while suspended — write its `PomodoroSession`, advance the cycle, and
  account for the possibility that **more than one** block elapsed (phone left overnight with auto-start
  on). The engine advances to the correct present-day state rather than replaying a night of pomodoros
  into the stats. Tested with a 14-hour gap.

### F2-T5 — Settings screen (D10)

The six values `SPEC.md` permits, and nothing else: work length, short break, long break,
pomodoros-per-sprint, sound on/off, auto-start next block on/off. A plain `Form`, reached from the
timer screen.

- **Bounds.** Each duration is 1–120 minutes and pomodoros-per-sprint is 1–12. One minute is a real
  setting rather than a debug affordance — it is what makes the cycle testable by hand in eight minutes
  instead of two hours — and the upper bounds exist so a mistyped value cannot schedule an alarm days
  away.
- **Changes apply at the next block boundary, never to the running block.** Shortening the work length
  mid-block must not retroactively end it. Already tested by `settingsChangeMidBlock`; the screen makes
  that path reachable by a person for the first time, so it also gets a note in the UI when a timer is
  running.
- No seventh field. No appearance control. See D10's scope fence.

### F2-T6 — Timer screen

Remaining time, block kind, sprint progress (● ● ○ ○), Start / Skip / Stop. F5 adds the I and E buttons
here; F3 adds the task name; F4 adds the music toggle. No placeholders for any of them.

## Risks

- **AlarmKit is young** — shipped in iOS 26 and its behaviour around rescheduling and cancellation is
  the least-documented part of this feature. Mitigation: alarm scheduling sits behind one small
  protocol, so if it disappoints, swapping to notifications is a one-file change, not a rewrite. This
  is the most likely source of an unpleasant surprise in F2.
- **Live Activity budget** — iOS limits update frequency. Countdowns render client-side from the end
  date, so we should not be pushing updates at all; if we find ourselves wanting to, that is a signal
  the design drifted off the wall-clock model.
- **Swift 6 + SwiftData** — `ModelContext` is not `Sendable`; all store access stays on the main actor.
