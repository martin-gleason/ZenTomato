# F14 — The watch can launch a pom

**Status:** plan written, awaiting the gate. No code has been written.
**Spec:** `docs/specs/zenpom-v1.5.md`, item 6 in the ratified order. Baseline `docs/specs/SPEC.md`
and the vocabulary in `docs/specs/definitions.md` both still bind.
**Branch, if it is approved:** `F14/launch-from-the-wrist`
**Delta position:** **none owed.** The ruling is below and it is made explicitly rather than assumed,
because the v1.5 spec asked for it to be *"confirmed at its gate"*.
**Shares a seam with:** `F10`, the "start a sprint" App Intent. That seam is named in this plan and
`F10` is expected to use it rather than open a second door.

---

## Paraphrasing it back

Today a pom begins in exactly one place: the Start button on `TimerView`, which calls
`TimerEngine.start()`. Everything else about the wrist already exists — `F7` shipped a watch app that
is told what is running and can send a distraction tap back.

F14 adds one thing: **a button on the wrist that makes the phone begin a block**. The wrist does not
run it, does not decide what it is attached to, and does not decide how long it lasts. It rings a
doorbell; the phone answers, decides, and starts. The wrist then sees the block appear in the state
the phone already sends it, which is how it learns whether it worked.

The reason it earns space is stated in the spec and it is a condition, not a convenience: `O15` — the
outstanding *Done when* for `F7` — already requires the watch to work **with the phone in another
room**. If that is the posture, then walking back to the phone to press Start is the friction the
watch was bought to remove.

**What this is not.** It is not independence. It is not a second timer. It is not a task picker, and
the sharpest question in this plan is the one about attachment, below.

## Ruling on the delta, since the spec asked for it explicitly

`docs/plans/00-deltas.md`, `D2`, ratified 2026-08-21, proposes this text into `SPEC.md`:

> **F7 — Watch companion.** watchOS 26 companion app. **The phone is the source of truth and runs the
> only timer engine.** The watch displays the running block, the block kind, and the attached task, and
> puts the I and E distraction buttons on the wrist. **The watch never runs a timer of its own, never
> controls music, never picks a task, and never edits a distraction note.**

**Four prohibitions, stated as an explicit list.** Runs a timer · controls music · picks a task ·
edits a note. A launch command is none of them, on the design below:

- **It does not run a timer.** The phone computes the block's length from its own settings, mints the
  session id, writes the row and schedules the alarm — every line of that is already in
  `TimerEngine.begin(kind:completedInSprint:settings:)` and none of it moves.
- **It does not pick a task.** The attachment comes from `SessionPlanStore.takeNextAttachment()`,
  exactly as it does when the phone's own button is pressed. See the next section; this is the whole
  argument.
- **It touches neither music nor notes.**

**And it does not decide anything, which is the load-bearing part.** The wrist sends a request
carrying a moment and an identity. Every judgement — is this fresh enough, is a block already
running, is the alarm permission granted, what does it attach to — is made on the phone. That keeps
the sentence *"the phone is the source of truth"* literally true rather than nearly true. The
`WatchBlockState` file already states the invariant it will have to live beside: *"this carries facts,
never instructions"*. A launch request is the one instruction that crosses, and it crosses in the
other direction, on its own channel, to a phone that is free to refuse it.

**So: no delta is owed, and F14 may be built once the gate is passed.**

**The condition under which that ruling flips, written down so it is checked rather than remembered.**
If at any point during the build the launch needs to *choose* an attachment — a "start on this task"
control, a most-recent-task fallback, anything that makes the wrist the author of what a pom is
about — then `D2`'s *never picks a task* is contradicted, work stops, and a `D<n>` is proposed. The
same applies if the watch ever has to judge its own request's freshness.

### The one place a rule and the ratified spec disagree

**`docs/plans/F7.md` says the opposite of this feature**, in its Risks section: *"A watch app invites
a complication, a start button, a task picker, 'just' a pause control. Every one is out of scope."*

That sentence was correct when it was written and is now superseded for exactly one of its four
items. `F7.md` is a **plan**, not a baseline; `docs/specs/zenpom-v1.5.md` is ratified, is later, and
admits `F14` by name with its own earned-entry argument. Under `docs/conventions.md` the baseline
wins and a plan is not amended to match reality.

**I am not resolving it silently in either direction**, per the convention that says to name the
disagreement and ask. It is Q5 at the bottom of this plan. My own answer: the ratified spec wins, and
`F7.md` gets no edit — but the next person to read that risk list will read it as still binding, so
the honest fix is a one-line pointer, which is itself a change to a shipped plan and therefore the
owner's call.

## What does a pom launched from the wrist attach to?

**This is the question that decides whether the feature is worth building**, because the distraction
log is the reason the app exists and a pom attached to the wrong task is worse than a pom attached to
nothing. A wrong attachment does not look wrong: it produces a perfectly ordinary row, in the
fortnightly export, against work somebody did not do.

**The answer: whatever the phone's own Start button would have attached it to. Nothing else.**

`TimerEngine.begin` already contains the only attachment rule this app has:

> `state.attach(newKind == .work ? attachments?.takeNextAttachment() : nil)`

A wrist launch goes through that same line, because it goes through the same engine call. **The
feature adds no attachment rule at all**, which is the strongest property available here: there is no
second rule to drift from the first, nothing to keep in step, and nothing new for a review to check.

The three alternatives, and why each lost:

**"The last attachment"** — reuse whatever the previous focus block was about. Rejected, and it is
the dangerous one, because it is the one that feels helpful. It guesses, and `D21b` is a standing
demonstration that the guess is wrong in the ordinary case: `takeNextAttachment()` deliberately steps
over anything already ticked off this sprint, precisely so a recurring task completed at 10:20 is not
handed straight back to the block at 10:30. A last-attachment fallback reintroduces that bug on one
device only, where nobody would look for it.

**"Refuse to launch unless the plan has an item"** — safest for the log, and rejected anyway. A pom
with no attachment is already legal on the phone: `takeNextAttachment()` returns `nil` when the plan
is empty or exhausted, `attachment` is optional throughout `TimerState`, and `F6` already renders a
tap whose block it cannot resolve. Refusing on the wrist would give the wrist a stricter rule than
the phone, which is a second rule by another name. It is put to the owner as Q1 because the argument
on the other side — *the log is the point, so never start a pom that cannot be attributed* — is not
a silly one.

**"Ask on the wrist"** — a picker. Refused outright: `D2` forbids it, and `F7.md`'s reasoning stands
on its own merits — *"picking a task is a considered act at a desk, not a wrist interaction."*

**The receipt is what makes this honest.** After a successful launch the phone sends the block back
through `updateApplicationContext` — `WatchStatePublisher`'s `Observations` loop watches
`(isRunning, kind, endsAt)` and a launch changes all three, so the send is certain; **how soon it
arrives is the system's business and is not asserted here** (`updateApplicationContext` coalesces and
delivers at the system's convenience — `F14-T2`'s spike is where a real number comes from).
`WatchBlockState.Block.attachmentTitle`
already carries the task's title, or the project's, or nothing. So the wrist does not merely start a
pom — it shows what it started and what that pom is about. A launch that lands unattached says so on
the screen, in the same place a phone-started one would.

### A consequence of the same rule that the feature's name hides

**The phone's Start button does not always start a pom.** `TimerEngine.start()` begins
`engine.kind`, and `goIdle(kind:completedInSprint:)` queues whatever comes next — which after a
completed focus block, with auto-start off, is a **break**. `TimerView` labels the idle control from
that queued kind for exactly this reason.

The wrist cannot currently see it: `WatchBlockState` carries a block only while one is running, so an
idle watch knows nothing about what Start would begin. F14 therefore has to add the queued block to
the idle payload — its kind and its length — so the button can say *Start focus · 25:00* or *Start
short break · 5:00* rather than lying by omission.

That addition stays inside the type's own doctrine: it is a **fact about the phone's state**, not an
instruction, and the watch renders it without deciding anything from it.

**But the fact can go stale on the wrist, and the existing publisher will not notice.**
`WatchStatePublisher.Signature` is exactly `(isRunning, kind, endsAt)` — deliberately narrow, and the
file says why. The queued block's **length** is not in it, and while the phone is idle that length is
read from `AppSettings` on every render (`TimerView.model(at:)` leans on `engine.remaining(at:)`
returning the whole block while idle, for precisely this reason). So: idle wrist reads *Start focus ·
25:00*, the owner changes the focus length to 30 in Settings, nothing about `(isRunning, kind,
endsAt)` moves, **and the wrist goes on offering 25:00 until the next boundary.** Pressing it starts a
correct 30-minute block — the phone computes the length, as it must — but the label lied on the way in,
which is the one thing this section added the queued fact to stop.

**`F14-T2` therefore owns the fix, not just the field:** the queued length joins the `Signature`, so a
settings edit while idle is a change worth a message. That is a widening of a type whose comment
explains why it is narrow, so the widening is stated here rather than discovered in review — the
narrowness was about not waking the loop for a plan edit the wrist cannot see, and this is a change
the wrist is now displaying.

The alternative — make the wrist button pom-only and have the phone refuse when a break is queued —
is rejected for the usual reason: it gives the two devices different rules, and it would let the
wrist skip a break the sprint had earned, which contradicts the doctrine already in the source that a
long break is something a pom earns.

## The seam, and why F10 must come through it

**One entry point: `BlockLauncher`, a new phone-side type in `ZenTomato/Timer/`.**

```
   Phone Start button ─┐
   Wrist launch    ────┼──▶  BlockLauncher.launch(_ request) ──▶ TimerEngine.start()
   F10's App Intent ───┘        freshness · duplicate · authorization · already running
```

One method, `launch(_:) async -> LaunchOutcome`, taking a request that carries **who asked, when they
asked, and a request id**, and returning a single enum of outcomes: started · alreadyRunning · stale ·
notAuthorized · unavailable. Every door gets the same answer to the same question, and each door's
only remaining job is to phrase that answer for its own surface.

**Why a new type rather than "everyone calls `engine.start()`".** Three of the four judgements above
do not belong to the engine and should not be pushed into it. Freshness is a property of a *remote*
request; the engine has no opinion about how a command travelled. Duplicate suppression is the same.
And the engine's `start()` deliberately **prompts for alarm authorization** when it is
`.notDetermined` — which is correct for a thumb on the screen and catastrophic for a wrist, since it
would put a permission dialog on a phone in another room and then await an answer nobody is there to
give. `BlockLauncher` is where a remote caller is refused before that can happen.

**Why the phone's own button routes through it too.** Because the alternative is two paths, and this
project has already paid for that lesson: the alarm-silencing work took eleven adversarial review
passes to reconcile three paths that were asking the same question in three slightly different ways.
The phone's button passes `requestedAt: now` and its own source, so freshness is trivially satisfied
and nothing about its behaviour changes — but there is exactly one implementation of *what starting a
block means*.

**`F10` uses this and adds nothing.** A Shortcut that turns on Do Not Disturb and starts a sprint is
the same operation arriving through a third door; `DismissBlockIntent` already proves an intent can
reach the running engine through `TimerEngineHolder`, and an intent has the same three problems a
wrist has — it may arrive at a phone whose app is not resident, it may be run twice, and it must
never trigger a permission prompt from outside the app. That is this seam's job description. **If
`F10` opens its own path, this plan was wasted**, and the fence in `F14-T1` is what makes that
visible rather than arguable.

**The fence:** a test that scans the app's Swift sources and fails if `engine.start()` is called
anywhere but `BlockLauncher`. It is a string scan, which is crude — and it is the same crude
technique `WatchLinkTests.noStoreOnWatch` and `theWatchOwnsNoTimer` already use to hold `D2`, so it
is consistent with the repository rather than novel.

**The scan covers the app target's sources only, and that boundary is not a detail.** `ZenTomatoTests`
calls `await engine.start()` at **104 sites** (counted 2026-09-09, `grep -rn "engine.start()"
ZenTomatoTests`), by design — the suite drives the engine directly and must go on doing so. A fence
worded as *"anywhere in the repository"* would go red the moment it was written and be deleted by the
end of the afternoon. `WatchLinkTests.watchSources()` is the existing precedent for scoping a scan to
one target's files.

## Unreachable, asleep, or not running

**A launch that arrives four minutes late is a lie about when you started.** That single sentence
sets every transport decision below, and it points the opposite way from `F7`'s.

**The tap and the launch are opposite kinds of message and must not share a channel.**

| | A distraction tap | A launch request |
|---|---|---|
| What it is | a **fact about the past** | a **command about the present** |
| Worst failure | being dropped | being delivered late |
| Therefore | `transferUserInfo` — queued, persisted, survives a kill | a channel that **fails fast** |
| When it fails | *"1 tap waiting to sync"* — it is safe | *"Couldn't start — use your phone"* |

So the launch uses `sendMessage` with a reply handler. `transferUserInfo` is the wrong API here for
the same reason it was the right one there, and using the wrong one would not fail loudly — it would
work perfectly on a desk, next to the phone, every time it was tried.

**That choice rests on a claim about `WCSession`, and this plan does not assert it: `sendMessage`
requires live reachability and errors promptly when there is none — *unverified*.** It is the
repository's stated understanding (`ZenTomatoWatch/WatchLink.swift`, the note at the top, and
`WatchTapInbox.swift`'s *"promises eventual delivery, not prompt delivery"*), which is a belief
written down, not a measurement. Under `docs/conventions.md` a decision about what another system can
do is not ratifiable until something has run, so **how quickly an unreachable `sendMessage` fails, and
with what error, is part of the `F14-T2` spike's output** alongside the background-wake question. If
it turns out to hang rather than fail fast, the wrist needs its own timeout and `F14-T4` grows a
fifth refusal.

**Belt and braces, on the phone, because the wrist is not trusted to judge:** the request carries
`requestedAt`, and `BlockLauncher` refuses anything older than a freshness window (Q2). A stale
request is answered `stale` and nothing starts. This is what makes the four-minutes-late case
impossible even if the transport surprises us.

**Idempotency, reusing `F7`'s proven pattern.** The request carries a `UUID` and the launcher ignores
one it has already honoured, so a double press or a system-level resend cannot produce two blocks.
The store of honoured ids is **in memory only** — no new SwiftData model — and that is sufficient
rather than lazy: a duplicate arriving after the app has restarted is by definition older than the
freshness window and is refused on that ground instead.

**The reply is the receipt, and it can be lost.** If the reply does not arrive the wrist must say the
launch failed — while the block may in fact be running. This is not hypothetical and it is not fixed
by trying harder. It self-corrects: `WatchStatePublisher` sends the new block through
`updateApplicationContext` as soon as its `Observations` loop sees `isRunning` change, so a wrist
showing "couldn't start" beside a running block reconciles on its own — **how long that takes is the
system's, not ours, and the plan does not put a number on it.** **The wording must survive being
briefly wrong**, which is why it is *"couldn't start"* and not *"nothing is running"*.

**Three states of the phone, and what each does:**

- **Foreground or recently backgrounded, reachable.** The ordinary case. Starts, replies, and the
  state follows.
- **Not resident — iOS reclaimed its memory, or the app was force-quit.** `WCSession`'s ability to
  wake a counterpart iOS app in the background for a `sendMessage` is **a claim about somebody else's
  system, and this plan does not assert it.** Under `docs/conventions.md` that makes it unratifiable
  until something has run, so `F14-T2` opens with a spike whose *output* is the evidence, and the
  transport choice is provisional until then. If it turns out the phone cannot be woken, the feature
  still works whenever the app is resident and says so honestly when it is not — a smaller feature,
  not a broken one, and the owner should know that before saying yes.
- **Out of range.** `sendMessage` errors, the wrist says so, and nothing is queued. **Deliberately
  nothing is queued**, which is the whole ruling of this section.

**One consequence found by reading, not assumed, and it needs the device to settle.** Music and the
outbound state publisher are both started from `TimerView`'s `.task` in `ZenTomatoApp` —
`running.music.start()`, `running.blockPhase.start()`, `running.watchState.start()`. If the app is
woken into the background without that scene appearing, a wrist-launched block may begin **silent**,
and the wrist may not be told about it until the phone is next opened. I could not verify this
without running it on hardware. It is Q4, and it is in the device check either way.

### Foundational — no user-visible change

#### `F14-T1` — `BlockLauncher` · owner: **agent**

The seam described above, and nothing else: the request type, the outcome enum, the four judgements,
and `TimerView.startBlock()` rerouted through it. No watch code, no new payload, no transport.

**With no remote caller in existence, behaviour is byte-for-byte what it is today** — that is the
acceptance condition, and it is what makes this safe to land before anything visible exists. The
existing suite is the instrument: it passes unchanged or the reroute is wrong.

The fence lands here too, because a seam nothing enforces is a suggestion.

*Checkpoint:* the full existing suite passes unchanged; `startHasOneCaller` is seen to fail when a
second call site is added by hand.

#### `F14-T2` — The launch channel · owner: **agent**

The spike first, and it answers **two** questions, both of them claims about somebody else's system:
**can a `sendMessage` from the wrist reach an iOS app that is not in the foreground?** and **when the
phone is unreachable, how fast does `sendMessage` fail, and with what?** Run it, paste what happened,
and only then finish the transport. If the answer to the first is no, the plan above still stands and
the wrist's honest refusal gets more work to do. If the answer to the second is *"it hangs"*, the
wrist needs its own timeout and `F14-T4` gains a fifth sentence.

Then: a `WatchLaunchRequest` payload beside `WatchTap` in `ZenTomato/WatchLink/Payload/`, a third key
in `WatchLinkKeys`, `session(_:didReceiveMessage:replyHandler:)` on `PhoneWatchLink` doing what that
file's existing delegate methods do — decode and hand off, no logic — and the queued-block fact added
to `WatchBlockState` so an idle wrist knows what Start would begin, **plus the queued length added to
`WatchStatePublisher.Signature`** so that fact cannot go stale behind a settings edit.

No button. The wrist cannot yet send one; the phone can receive one.

*Checkpoint:* the phone's receive path, driven directly in a test with a crafted payload, starts a
block for a fresh request and returns each of the four refusals for the cases that earn them. The
spike's output is in the PR.

### Vertical slices — each one a thing you can hold

#### `F14-T3` — The button, and the receipt · owner: **agent**

`WatchTimerScreen`'s idle state currently reads *"No block running / Start one on your phone."* It
becomes a button labelled from the queued block — *Start focus · 25:00* — with a haptic on press, the
same `.click` the capture buttons use, for the same reason: a wrist control that gives nothing back
is one somebody presses again.

**The two-second lesson from `F7` applies directly.** `WatchLink.record(_:)` carries a comment about a
synchronous system call that blocked the main actor for over two seconds and made a live button read
as dead — and the owner pressed it repeatedly, each press becoming a real row. A launch button has the
same shape and worse consequences, so the send goes off the main actor and the button shows a
*pending* state the instant it is touched, before anything slow happens.

*Checkpoint:* on the paired watch, with the phone reachable in another room, one press starts a pom
and the wrist flips to the running block with the right task title on it.

#### `F14-T4` — The refusals · owner: **agent**

Four outcomes reach the wrist and each gets a sentence that is true: already running (which is what a
double press looks like when the reply for the first was lost) · not authorized, which asks for the
phone once rather than blaming the watch · unreachable · stale.

**Wording is the deliverable here, not plumbing.** `F7` set the standard on the tap side — *"waiting
to sync"* rather than *"failed"*, because the tap was already safe. A launch is the opposite case and
the wording has to be the opposite too: it did **not** happen, and saying anything softer would leave
somebody believing a pom was running while they walked away.

*Checkpoint:* each of the four, produced deliberately on the device — airplane mode for one, a block
already running for another — read back off the wrist.

#### `F14-T5` — The log is indifferent · owner: **agent**

**The task that protects the reason the app exists.** A wrist-launched pom must be indistinguishable
in the database from a phone-launched one: same attachment rule, same session row, same distraction
rows hanging off it, same shape in the stats and the Markdown export. No column says where it came
from, and none should — that would be a fact about a door, in a file whose job is to be readable at
the fortnightly review.

`StatsMarkdownGoldenTests` is the instrument, as it was for `F8`.

*Checkpoint:* the export of a day containing one wrist-launched pom and one phone-launched pom, read
side by side. If they differ at all, F14 is wrong.

#### `F14-T6` — A pom launched from another room · owner: **human**

`SPEC.md`'s standard: closed on hardware, by the owner, with a build number and their own words.

Put the phone in another room with the app **backgrounded, not open**. Launch from the wrist. Walk to
the phone. Answer four things: did it start · did it start *when you pressed it*, or minutes later ·
was it attached to the right thing · **was there music**.

*Checkpoint:* recorded as an `O<n>`, closed by the owner with the build number.

## Mutations

**A test that has never been shown to fail is not evidence.** Each of these is applied to the shipped
code, the named test is *seen* to fail, and the count is recorded before the task is called done. The
`M<n>` numbers are allocated in `docs/plans/00-register.md` when the rows are written — not here,
because that file is shared and an id claimed in advance is an id claimed twice.

| Break this | This test must fail |
|---|---|
| Delete the freshness check — honour a request of any age | `aStaleLaunchIsRefused` |
| Honour a request id that has already been honoured | `oneRequestStartsOneBlock` |
| Let a remote launch through while authorization is `.notDetermined` | `aRemoteLaunchNeverPromptsForPermission` — asserted on `SpyAlarmScheduler`, which already records whether `requestAuthorization()` was called. The assertion is *"the spy was never asked"*, not *"no block started"*: a mutant that prompts and then starts a block satisfies the second and is the exact defect. |
| Attach a wrist-launched pom from the previous block instead of `takeNextAttachment()` | `aWristLaunchAttachesLikeAPhoneLaunch` |
| Add a second call site of `engine.start()` in a view | `startHasOneCaller` — scanning the app target only; see the fence above |
| Leave the queued block's length out of `WatchStatePublisher.Signature` | `anIdleWristSeesASettingsChange` — change the focus length while idle and assert a new state was sent carrying the new length |
| Send the launch by `transferUserInfo` instead of the fail-fast channel | `theLaunchIsNeverQueued` — **and it cannot be a bare source scan for `transferUserInfo`.** `ZenTomatoWatch/WatchLink.swift:109` already calls it, correctly, for the tap; a scan of the watch sources for that string is red before the mutation is applied and therefore proves nothing. The test drives the launch send path against a fake session that records which API it was handed and asserts on *that*. |

The fourth is the one that matters most and the one whose fixture is easiest to get wrong. **The plan
under test must have a second item that differs from the first**, or both implementations return the
same attachment and the assertion distinguishes nothing — the exact shape of the toothless tests this
project has already been bitten by five times.

## Scope fence

Not in F14, each needing its own gate: **stopping or abandoning a block from the wrist** · skipping a
break · starting the next block early from a running one · a task picker or any attachment control ·
music control · a complication or watch-face button (that is `F17`) · any watch-side alarm, notification
or end-of-block haptic · choosing an `F8` shape from the wrist · a "start with this task" variant of
`F10`'s intent · any column recording which door a pom came through.

**"While you're in there, add a Stop button" is the one that will be asked mid-build**, because the
wrist will look half-finished with one control on it. It is out, and not merely on scope grounds:
`TimerEngine.stop(reason:)` **requires a reason by its type**, deliberately, so that no second caller
can quietly abandon a block without one — and a wrist cannot supply a written sentence. A wrist Stop
would either bypass that requirement or invent an empty reason, and both are the defect the signature
exists to prevent.

**Second most likely: "start the next pom early from a break."** Also out — that is a decision about
the sprint, and the engine's doctrine is that a break follows a pom that earned it.

## Open questions for the gate

Six, batched. Nothing below is invented an answer for.

1. **Attachment, when the plan is empty.** The plan's ruling is *launch anyway and attach to nothing*,
   because that is what the phone's button already does and a stricter wrist rule is a second rule.
   The case for refusing is that the log is the point. **Which?**
2. **The freshness window.** How old is too old? A minute is generous; ten seconds is strict enough to
   annoy on a slow link. I would take **30 seconds** — long enough to survive an awkward handshake,
   short enough that nobody is still standing there wondering. It is arbitrary until you say a number.
3. **Does the wrist button appear during a break, to start the next pom early?** I would say no —
   idle only. Named because it is the first thing that will feel missing.
4. **The background-music consequence.** If a wrist launch into a backgrounded app starts a **silent**
   pom, is that acceptable, or should the phone refuse to start a block it cannot run properly? I
   cannot answer this without the device, and the answer changes what `F14-T2` builds.
5. **The `F7.md` disagreement.** Its risk list says a start button is out of scope; the ratified v1.5
   spec says F14 is in. The baseline wins and no plan is edited to match reality — but the next reader
   of `F7.md` will read that sentence as binding. Leave it, or add a one-line pointer to `F14`?
