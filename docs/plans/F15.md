# F15 — The graphics pass

**Status:** plan written, **awaiting the gate.** No code has been written.
**Spec:** `docs/specs/zenpom-v1.5.md`, ratified 2026-09-09, item 9 of eleven.
**Vocabulary:** `docs/specs/definitions.md`, ratified 2026-09-09.
**Baseline still binding:** `docs/specs/SPEC.md` (v0.1).
**Input:** `docs/ZenTomato redesign scope.zip`, tracked deliberately (`docs/plans/parked.md`, "The design
handoff") because ignoring it left it on one disk where two ordinary git operations destroyed it in a
morning. **Read for this plan by unpacking it to `/tmp`, outside the tree. Nothing from it was
unpacked into the repository and nothing from it is proposed for commit.**

---

## Paraphrasing it back

The earned-entry line is *"lets the app look professional rather than built"* — the owner's words,
*sharper, professional grade*. That is a judgement about finish, not a list of screens, so the first
job of this plan is to turn it into work that can be shown to be done.

My reading: **this is not a redesign and it must not become one.** The design system is not the
problem — it is two-layer, 20 semantic colour roles, every contrast figure measured and asserted, and
a SwiftLint rule with teeth that fails the build if `Palette.` appears outside the token layer. An app
looks *built* rather than *professional* in the places where the system it already owns is not
actually reaching. So F15 is the pass that closes that gap: find every surface drawing outside the
token system, put it back inside, and leave behind a fence so it cannot drift out again.

That framing has one large advantage over the alternative, and it is the reason I am proposing it:
**it is verifiable.** "Recreate the mock" is judged by eye and by eye alone. "No surface draws outside
the token system" is a search, a lint rule, and a count — and the eye is then spent on the one thing
only an eye can do.

**It is not thinner than expected. It is richer — and it is not a graphics pass.** Its own README

**So the zip is v1.5's design input, not F15's.** Treating it as F15's build list would quietly pull
`F12` and `F16` forward into a feature that owes no delta, which is exactly how scope arrives without
a decision. What F15 can legitimately take from it is the *token and layout transcription* in
`recreation-notes.md` — the pixel baseline — and the icons.

### The finding that matters most: the one shippable asset already ships

The zip's three icon SVGs are already in the repository, and they are the same drawing.

`Design/icon/AppIcon-light.svg` (4,106 bytes) against the zip's (4,090 bytes): the entire difference is

They are already rendered: `ZenTomato/Resources/Assets.xcassets/AppIcon.appiconset/` holds

That is worth saying out loud before this is scheduled, because "the graphics pass has assets waiting
in a zip" and "the graphics pass has one already-shipped icon and a mock of four unbuilt features" are
very different features to plan an afternoon of review around.

## The delta position — confirmed, with the condition that makes it true

**The brief's expectation is right: F15 as scoped below owes no `D<n>`.** It changes no locked
decision, adds no setting, adds no screen, adds no stored field, and adds no `ColorRole`. It moves
existing surfaces onto tokens that already exist and fences them there.

**That is a conclusion about the scope, not about the zip**, and it is only true while the fence
holds. Three items in the bundle each *do* owe a delta, and the largest of them looks harmless:

- **The Ensō block style owes one.** Not because it is a drawing — because it is a **chooser**.
  `SPEC.md`'s locked decisions end: *"Timer customization: work length, short break, long break,
  pomodoros-per-sprint, sound on/off, which alert sound, auto-start next block on/off. **Nothing
  else.**"* A "Block style — Rule / Ensō circle" row in Settings is timer customisation that is not on
  that list, and it is persisted (`blockStyle`, per the zip's own State management section). The
  precedent is directly on point and recent: `F8`'s Ruling D put its two controls on the shape screen
  rather than in Settings **specifically** to avoid this clause, and recorded why. `D24` had to be
  ratified to give `AppSettings` its seventh field.
- **Themes are `F12`** and the v1.5 spec already records the delta they owe (`SPEC.md`'s out-of-scope
  list names themes explicitly).
- **The garden is `F16`**, and its delta must argue the accumulate-only form specifically.

The Island tomato is the interesting middle case: the zip argues it is content-only, derived purely
from start/end dates, with no `.update(` anywhere — which, if true, contradicts nothing. It is still a
**new drawn glyph in a surface the app cannot screenshot in CI**, so it is fenced out below on
verification grounds rather than contract grounds, and it is the one I would most expect to be argued
about.

**No decision number is claimed here** (number allocated by the owner at ratification, in build order — three plans in this batch each reasoned independently to the same next-free number and none could see the others). F15 as
planned does not need it.

## The ordering problem: `F12` is scheduled before this, and both touch the token layer

This is a real question for the owner and I have a recommendation rather than an answer.

**The collision is smaller than it looks, and it is not where it seems to be.** The zip's theme tables
override `action` / `actionActive` / `onAction` for the accent swaps, and re-derive grounds and ink for
the two full palettes — but the **base (Sage) table it publishes is the table that ships today**,
unchanged, to the hex. So the graphics pass as scoped here does not redefine the palette, and themes
built first would not be invalidated by it. The fear behind the question is sound; on the evidence in
the zip it does not fire.

**Where it does fire is roles, and the arithmetic is one-directional.** A theme is a full table keyed
by role. Add a `ColorRole` case *before* `F12` and one value is written. Add the same case *after*
`F12` and it has to be given a value in every theme table — six, plus Auto's fallback — and every one
of those new pairings has to be re-measured against the AA harness, because `DesignTokenTests`
measures pairings and `everyForegroundRoleIsAudited` fails a role nobody measured. **Roles are what
themes multiply. Drawings are not.** A shape added after themes costs nothing; a role added after
themes costs sevenfold.

There is also a mechanical collision that is pure merge order, not invalidation:
`ZenTomatoTests/PolishFenceTests.swift`'s `theTokenLayerDoesNotGrow` pins exact counts — 20 `ColorRole`
cases, 13 `Typography` statics, 15 `Spacing`, 6 `Radius`. Whichever feature moves those numbers second
rebases onto a number the other one moved. Annoying; not expensive.

**Recommendation: keep the ratified order — `F12` before `F15` — and buy the risk off with a fence
rather than with a re-order.** F15 declares that it adds **no new `ColorRole` case**, and
`theTokenLayerDoesNotGrow` is the instrument that proves the declaration rather than the plan
asserting it. The order was ratified on review-capacity grounds (small PRs first, `F12` is an S,
`F15` is an M), and that reasoning is untouched by anything I found.

**The condition on which I would reverse it**, and it belongs to the owner: **if `F15` is meant to
re-cut the palette** — if *sharper* means new colour, not the existing colour applied properly — then
it must come first, and the seven-fold argument above is why. The zip does not ask for that; the
owner's two words might. That is Open question 2.

## What can be asserted, and what cannot

This project has been bitten precisely here. `conventions.md` records the table: a CSS rule deleted
outright, green. A mark rendering four pixels tall, green. A download button shipping bytes nobody
validated, green **twice**, because both fixes re-derived the expected bytes instead of reading the
download path. A visual overhaul is the hardest thing in v1.5 to verify and pretending otherwise is
the failure mode, so this section is written before the tasks rather than after them.

**Assertable, in `make ci`, today:**

1. **Token identity.** `DesignTokenTests.everyRoleMatchesTheDesignSystem` runs per role against a
   table transcribed independently of `ColorRole.swift`. A typo in a hex is caught and the failure
   names the role.
2. **Contrast.** `textOnSurfaceMeetsAA` (4.5:1), `borderOnSurfaceMeetsNonTextMinimum` (3:1), and
   `everyForegroundRoleIsAudited`, which fails if a role is added without being measured at all.
3. **Counted fences over source.** `PolishFenceTests.theTokenLayerDoesNotGrow` and its siblings read
   the actual files and count. This is the shape that catches "one reasonable-looking case at a time".
4. **The two-layer rule.** `.swiftlint.yml`'s `palette_outside_token_layer`, `severity: error`, over
   `App|Views|Models|Timer|Alarm|Shared|Stats|Export|Sprint|Todoist|Plan|Music`, `ZenTomatoActivity`
   and `ZenTomatoWatch`.
5. **Geometry of a pure drawing.** Where a shape is a function of its inputs, the path it produces can
   be asserted without a screen — extent, closure, monotonicity against progress — **at the size it
   will actually be drawn, read off the object the renderer consumes.** That is the specific
   correction the four-pixel-tall mark demands: assert the artefact, not the model that generated it
   (the validate-every-artefact rule).

**Not assertable by anything in this repository, at any effort:**

whether it looks professional · whether the numeral still dominates at AX5 · whether the icon holds up
on a home screen among thirty other icons · whether dark mode is readable outdoors · whether the watch
face reads at a glance · whether any of it is *sharper*.

**Those are `F15-T6`, an owner item, and this plan does not pretend a test covers them.** Naming that
honestly is the point of the section: the eye budget is small and fixed, so it is spent only on what
the eye alone can settle.

### Foundational — no user-visible change

#### `F15-T1` — The drift audit, executable · owner: **agent**

`Typography.swift` opens with a claim: *"There is no `Font.system(...)` and no `Font.custom(...)`
anywhere else in the app. Every piece of text gets its font from a role named below. That is a
property a reviewer can check with a search."*

**The claim is false, and nothing checks it.** `.swiftlint.yml` has exactly one custom rule and it
guards colour. A search finds six violations, all in one file:

```
ZenTomatoWatch/WatchTimerScreen.swift:38   .font(.system(.title, design: .rounded).monospacedDigit())
ZenTomatoWatch/WatchTimerScreen.swift:70   .font(.system(size: 11))
ZenTomatoWatch/WatchTimerScreen.swift:104  .font(.system(size: 11))
ZenTomatoWatch/WatchTimerScreen.swift:130  .font(.system(.title3, design: .rounded).weight(.semibold))
ZenTomatoWatch/WatchTimerScreen.swift:166  .font(.system(size: 11))
ZenTomatoWatch/WatchTimerScreen.swift:171  .font(.system(size: 11))
```

`ZenTomato/` and `ZenTomatoActivity/` are clean — the Live Activity extension names `Typography.kicker`,
`Typography.title` and `Typography.data` throughout. So the type scale is honoured everywhere it can
be seen on a phone and abandoned on the wrist, where three raw point sizes and a `.rounded` face that
exists nowhere else in the app are drawing the screen.

**This is the whole thesis of the feature in one file**, which is why the audit is the foundational
task rather than a preamble: the app looks *built* on the watch because the system does not reach it.

The task delivers a `typography_outside_token_layer` custom rule alongside the colour one, scoped at
first to the surfaces where it is **already green**, plus a counted assertion recording the watch's
six as a known number that `F15-T3` drives to zero. **A rule that cannot go green on the day it lands
is a rule somebody disables**, which is why it arrives in two steps and why the second step is a
separate task with its own checkpoint.

**Two scoping details that decide whether it lands green, both of them checked rather than assumed:**

- **The rule's `included:` enumerates the drawing directories, exactly as the colour rule does** —
  `ZenTomato/(App|Views|Models|Timer|Alarm|Shared|Stats|Export|Sprint|Todoist|Plan|Music)` plus
  `ZenTomatoActivity`. It must **not** be scoped at `ZenTomato/` wholesale: `Typography.swift` is the
  file that is *allowed* to say `Font.system`, and it says it ten times. A rule pointed at the whole
  target fails on the token layer it exists to protect, on the first run. That is precisely why the
  colour rule spells its directories out, and the reason transfers unchanged.
- **The count assertion strips comment lines before counting**, reusing the shape of
  `PolishFenceTests.stripped(_:)`. `Typography.swift`'s own doc comment contains the string
  `Font.system(...)` while stating the rule — and `StatsFenceTests`' reason is already written down
  in this repository: *a fence that cannot tell a refusal from a violation fires on the sentence that
  states the rule, and is switched off within a month.*

*Checkpoint:* `make lint` green with the new rule live; the count assertion reads 6 for
`ZenTomatoWatch` and 0 for the other two targets; and adding one raw font call to `TimerScreen.swift`
is seen to fail the build.

#### `F15-T2` — The design system compiles for watchOS · owner: **agent**

**Verified from `project.yml`: the watch target does not compile the design system at all.** Its
`sources` are `ZenTomatoWatch`, `ZenTomato/WatchLink/Payload`, `ZenTomato/Timer/BlockKind.swift`,
`ZenTomato/Distraction/DistractionTally.swift` and the asset catalog. `ZenTomato/DesignSystem` is not
among them. The watch cannot name `Typography.data` or `ColorRole.textMuted` because neither type
exists in that target — it draws with `.foregroundStyle(.secondary)` at seven sites and raw sizes at
six.

**And the colour rule "covering" `ZenTomatoWatch/` is covering nothing — for two reasons, and the
first one is worse than the one I noticed first.** `.swiftlint.yml` includes the watch in
`palette_outside_token_layer`'s `included:` regex, whose own comment says the hole was closed
*"because a guard with a hole is one that gets believed when it should not be."*

1. **SwiftLint never opens a watch file at all.** The file's own top-level `included:` is
   `ZenTomato`, `ZenTomatoActivity`, `ZenTomatoTests` — `ZenTomatoWatch` is not on it. A custom
   rule's `included:` narrows the set of files the linter is already walking; it cannot add one. So
   the watch's name inside the rule is decorative, and has been since `F7`.
2. **And even if it were linted, it cannot see `Palette`** — the type is not in its target.

The guard is green twice over for the wrong reason, which is the same class of false assurance as a
green suite over a broken parser. **The consequence for this plan is concrete:** any checkpoint that
says "the rule's `included:` gains `ZenTomatoWatch`" is a no-op unless the **top-level** `included:`
gains the target too, and that is the change that carries the risk — it puts the watch under *every*
rule, under `--strict`, for the first time. Pre-existing violations there (line length, hygiene
opt-ins) are unknown until it is run, and a first run that fails on a hundred unrelated warnings is
the rule somebody disables. **Run it before committing to it**; if the watch is not already clean,
the cleanup is named in the PR as its own commit rather than absorbed.

This task adds the semantic layer to the watch target and does nothing else. **Nothing consumes it
yet**, so there is no user-visible change and it is safe to land alone.

**The one thing that may not work, named before it is built rather than discovered:**
`ZenTomato/DesignSystem/SwiftUI/Color+ColorRole.swift` opens `import UIKit` and builds every colour
through `UIColor { traits in … }`. That file is deliberately the only one in the design system that
knows iOS exists — its own doc says *"a future port to another Apple platform rewrites this file and
nothing else"* — and this is that port. The semantic layer (`ColorRole`, `Typography`, `Spacing`,
`Radius`, `Palette`, `RGBColor`) is plain Swift and should cross untouched. **I have not compiled it
and do not claim it compiles.** If the bridge needs a watchOS path it is written here, in the one file
whose job is to be rewritten, and not by scattering `#if os(watchOS)` through the screens.

**A hole this task opens, and must close in the same commit.** `WatchLinkTests`' two fences —
`noStoreOnWatch` and `theWatchOwnsNoTimer` — search for `import SwiftData`, `ModelContainer`,
`ModelContext`, `FetchDescriptor`, `TimerEngine`, `AlarmManager`, `import AlarmKit`, `import MusicKit`,
`Timer.publish`. **They do not read the watch target's sources.** `WatchLinkTests.watchSources()`
enumerates one directory — `ZenTomatoWatch/` — and nothing else, so every directory `project.yml`
*also* gives the watch target (`ZenTomato/WatchLink/Payload`, `ZenTomato/Timer/BlockKind.swift`,
`ZenTomato/Distraction/DistractionTally.swift`) is already compiled onto the wrist unread by the
fence. Adding `ZenTomato/DesignSystem` widens that gap by seven more files.

The design system does contain none of those strings — checked by grep over
`ZenTomato/DesignSystem/`, zero hits — so the fence would stay green either way. **That is the
problem, not the reassurance:** it would stay green because it never looked, which is the same class
of false assurance this task is complaining about in the colour rule two paragraphs up. So `F15-T2`
extends `watchSources()` to walk every path `project.yml` lists under the `ZenTomatoWatch` target
rather than the one directory that shares its name, and the mutation that proves it is naming a
forbidden string into a design-system file and watching the fence fail.

*Checkpoint:* the watch target builds with the tokens compiled in, every existing test still passes
including both `WatchLinkTests` fences, and **the watch screen looks exactly as it does today** —
because nothing has been changed to use them yet.

### Vertical slices — each one a thing you can hold

#### `F15-T3` — The watch stops drawing in platform defaults · owner: **agent**

The six font sites take `Typography` roles; the seven `.foregroundStyle(.secondary)` sites take
`ColorRole` inks. The wrist then draws in the same vocabulary as the phone and the Lock Screen card,
which is the difference the owner is describing when they say *built*: two surfaces of one app that do
not look like one app.

**Two things it must not quietly do.** It must not invent a role or a type size for the watch — if the
scale genuinely does not cover a 40mm screen, that is a finding to state out loud, not to absorb, and
it would move `theTokenLayerDoesNotGrow`'s numbers where a reviewer can see it. And it must not touch
the tap path: `WristTapReflectionTests` and `WatchTapInboxTests` guard the reason the watch exists,
and a restyling that changes when a tap becomes a durable row is a defect in F15, not a new behaviour.

*Checkpoint:* the phone and the watch photographed side by side showing the same running block, in
both appearances; `F15-T1`'s count assertion goes 6 → 0; **`.swiftlint.yml`'s top-level `included:`
gains `ZenTomatoWatch`** — without which the rule's own `included:` naming the watch is decorative,
per `F15-T2` — and `make lint` is green after it; the distraction suites unchanged and still green.

#### `F15-T4` — The sprint rule fills as it goes · owner: **agent** · **gated on Ruling A**

`O23`, open since sprint 2, in the owner's words: *"progress bars should fill up, not just appear
full."*

**This task contradicts a decision the source already argues at length, which is why it is gated and
not simply done.** `SprintProgressView.swift` carries a section headed `TWO STATES, NOT THREE`: a
segment is finished or it is not, and *"the block that is running is given no third appearance,
because it does not need one: the word above the countdown names it and the countdown is visibly
moving."* It also records that the two inks measure 1.37:1 against each other, so the finished/unfinished
distinction is carried by **height** rather than by colour, deliberately, to clear 1.4.11 and to
survive colour blindness and a photograph. A third, partially-filled state has to answer both of those
or it reintroduces the failure that shaping fixed.

If the owner rules it in, the shape I would build is the **running segment filling horizontally from
its leading edge at the unfinished height**, so the existing height step stays the signal that a
segment is *done* and the fill is a second, weaker signal that one is *underway*. If they rule it out,
`O23` is closed as ruled rather than left open — an open cosmetic item nobody intends to do is worse
than a closed one, because it reads as a backlog.

*Checkpoint:* at 40% through a block the rule's running segment measures 40% of its width **read off
the drawn geometry at the size it renders**, not off the model; the finished/unfinished height step is
unchanged in a screenshot; `SprintProgressTests`' one existing case —
`filledAndEmptySegmentsAreNotDistinguishedByColourAlone`, and it is one, not two — still passes.

#### `F15-T5` — The icon's render path is proven rather than assumed · owner: **agent** · **no user-visible change**

`Design/icon/` holds three SVGs and `make-icon.sh`; `Assets.xcassets/AppIcon.appiconset/` holds three
1024² PNGs generated from them on 22 August. **Nothing checks that the PNGs still correspond to the
SVGs.** Edit an SVG and the app ships the old icon, silently, for as long as nobody regenerates — and
the SVG carries a comment instructing the next person to edit exactly that file.

This is the validate-every-artefact rule in its literal form: *validate every artefact, not just the primary one.* The icon is
the first thing anybody sees and it is a derived output nothing asserts on.

The task adds a check that fails if what ships no longer derives from the SVGs, naming which file.
The assertion reads the **committed PNG bytes** and compares them with what the SVGs produce; it must
not compare the SVG with itself, which is the re-derivation trap that let a bad download line through
twice.

**Two things this task asserts about a system outside this repository, and neither is verified. They
are the reason `F15-T5` is not ratifiable as written.** `conventions.md`: *a decision about what
another system can do is not ratifiable until something has run*, and the evidence is the observable
end state, not the configuration field.

- **`rsvg-convert` is deliberately not in the build or in CI.** `make-icon.sh`'s own header says so in
  as many words: *"It is NOT part of the build or of CI — the PNGs it produces are committed, so a
  clone builds without it."* Putting a regenerating check into `make ci` therefore adds a `librsvg`
  dependency to the macOS runner, to the pre-commit path, and to every fresh clone. **Whether that
  dependency is wanted is the owner's call, not mine** — it is Open question 6.
- **Byte-identical re-rendering is unverified.** The check as drafted assumes `rsvg-convert` produces
  the same bytes on the runner as it did on the machine that wrote the PNGs on 22 August. Different
  `librsvg` versions, different `cairo`, different `libpng` — any of the three can change the encoded
  bytes without changing a single pixel, and the result is a check that is red on every run for a
  reason nobody can act on. That is worse than the hole it closes.

**So the task's first step is to run it, not to write it:** render each SVG twice on this machine and
on the runner image, compare, and record the output in the register row. If bytes are stable, the
byte comparison ships. If they are not, the check falls back to something that does not depend on the
renderer being deterministic — a committed content hash of each SVG, checked against a hash recorded
beside the PNGs at generation time, which catches the failure this task exists for (*an SVG edited,
the PNG not regenerated*) with no dependency on `librsvg` at all. **Which of the two ships is decided
by the run, and the row records the command and its output.**

*Checkpoint:* the determinism run above, recorded; then `make ci` fails when one hex in
`AppIcon-dark.svg` is changed and passes when the icon is regenerated; the failure message names the
file.

#### `F15-T6` — The device look · owner: **human**

`SPEC.md`'s standard: a *Done when* is closed on hardware, by the owner, with a build number and their
own words. This is the part no test reaches, so it is stated as five specific looks rather than as
"does it look good":

1. The home screen, among real icons, in light and dark and tinted.
2. The timer screen idle and running, at the default text size and at AX5.
3. The same two in dark, and one of them outdoors.
4. The watch beside the phone, same running block — the `F15-T3` question.
5. The Lock Screen card and the Dynamic Island, glanced at rather than studied.

## Scope fence

Not in F15. Each needs its own gate, and the first three each need a `D<n>` before they can be built
at all:

- **The Ensō circle block style.** Owes a delta: it is a persisted timer-customisation setting and
  `SPEC.md`'s locked list ends *"Nothing else."*
- **Themes.** That is `F12`, with its own delta.
- **The garden.** That is `F16`, with its own delta, and its accumulate-only ruling to argue.
- **The Dynamic Island tomato.** Content-only by the zip's argument, but a new drawn glyph in the one
  surface CI cannot photograph. If it is wanted, it is wanted as its own gate with its own device
  check.
- **The Settings restructure into three groups**, and the Music row's `Music: {Service}. {Status}`
  format. The format exists to hold Spotify and YouTube Music, which the v1.5 spec puts in **v2.0** as
  providers. Building the row shape now is preparing for scope, which `CLAUDE.md` forbids in the same
  sentence as building it.
- **Any new `ColorRole`, `Typography`, `Spacing` or `Radius` token.** The counted fence is the
  enforcement and mutation 2 is its proof.
- **Any photograph or bitmap in-app.** The flat-surface rule stands; the zip flags its own CC receipts
  as inspiration only.
- **Animation beyond the existing 100–260ms functional transitions.** No bounces, no confetti.

**The Ensō is the one most likely to be asked for mid-build**, and it is the most attractive thing in
the bundle — a calligraphic stroke that draws itself, with the exact generator already written in
`ensoStroke()`. Two reasons it is out, and the second is the one that would bite. It is a **setting**,
which is the clause above. And its verification burden is the largest in the whole milestone: a
resolution-independent brush stroke with ink depletion, a kasure tail and three stacked wobble sines
is judged by eye and by nothing else — and the file containing the generator references ten
stylesheets that are not in the bundle, so we do not yet know it renders at all. A feature whose
correctness is entirely a matter of taste is a feature that needs its own gate, not a slice of one
that is trying to prove finish by counting.

## Open questions for the gate

Six, batched. None is answerable by investigation and each changes what gets built.

**1. `O23` — a rule and the need disagree, so I am naming it rather than picking.** The owner asked
for progress bars that fill. `SprintProgressView` was deliberately built with two states and no third,
and the argument in its source is a good one: the running block is already named above and already
counting, and the finished/unfinished distinction is carried by *height* because the two inks measure
1.37:1 against each other. **I would build it** — the shape in `F15-T4`, filling at the unfinished
height so the height step stays the "done" signal — because the owner has looked at the real screen
during a real sprint and the doc comment has not. But it reverses a written decision, so it is the
owner's. **If it is refused, `O23` should be closed as ruled**, not left open.

**2. Does *sharper* mean new colour, or existing colour applied properly?** This plan assumes the
latter and the ordering recommendation depends on it. If F15 is meant to re-cut the palette, it must
run **before** `F12`, because a role added after the theme tables exist must be given a value in seven
of them and re-measured against the AA harness in every one. A drawing added after themes costs
nothing; a role costs sevenfold. **My recommendation: keep the ratified order, `F12` then `F15`.**

**3. Does F15 own the watch?** Every piece of verified drift I found is on the wrist, so on the
evidence it should. But `F14` (the watch can launch a pom) and `F17` (a complication) are both in this
milestone and both will open that target. Doing the styling here means `F14` inherits a watch already
on the token system; doing it in `F14` means one PR instead of two. **I would do it here**, because
`F14` and `F17` are both larger than they look and a restyling folded into either would be the part
that gets cut. The owner's review-capacity argument might say otherwise.

**4. Is the icon in scope as a *design*, or only as a *pipeline*?** The zip's icons are the ones
already shipping. If *professional grade* included a new icon, **the zip does not contain one** and
F15 as planned will not produce one — `F15-T5` proves the existing icon ships correctly and stops
there. Drawing a new mark is a different feature with a different kind of gate.

**5. What would make `F15-T6` a pass?** It is the only checkpoint in this plan settled by judgement,
and *"looks professional"* is not a threshold. Two or three named apps or screens the owner considers
the standard would turn it into a comparison; without them the honest position is that the checkpoint
is the owner's sentence and the feature is done when they write it. **Expectations set at the gate are
cheaper than expectations discovered at the review** — this is the one worth the round trip even if
the answer is "I'll know it when I see it", because that answer is itself a decision and can be
recorded.

**6. Does `make ci` get a `librsvg` dependency?** `F15-T5` closes a real hole — an SVG edited, the PNG
not regenerated, the old icon shipped silently — but the obvious check regenerates the PNGs, and
`make-icon.sh` says in its own header that `rsvg-convert` is deliberately *not* part of the build or
of CI so that a clone builds without it. Adding it to `make ci` means the macOS runner, the pre-commit
path and every fresh clone acquire a Homebrew dependency to check three files that change perhaps once
a year. **The alternative needs nothing installed:** commit a hash of each SVG alongside the PNGs and
check that instead — it catches the same failure and adds no tool, at the cost of not proving the PNG
itself is correct, only that it was generated from the SVG that is there now. **I would take the
hash**, because a gate that a clone cannot run is a gate that gets skipped. The owner owns the trade.
