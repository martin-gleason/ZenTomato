# F10 — A "start a sprint" App Intent

**Status:** plan written, **awaiting the gate.** No code has been written.
**Spec:** `docs/specs/zenpom-v1.5.md`, item 7 in the ratified order — *"Lets a Shortcut turn on Do
Not Disturb and start a sprint together."*
**Baseline:** `docs/specs/SPEC.md` (v0.1) and `docs/specs/definitions.md`, both binding.
**Delta owed:** **none.** The argument is at the bottom and it was checked line by line rather than
assumed.
**Depends on:** **`F14-T1` — `BlockLauncher`.** F10 does not build an engine entry point and no
longer proposes one. See *The ruling of 2026-09-09* below.
**Revised 2026-09-09** after the owner's ruling that `BlockLauncher` is the single engine entry
point. What was withdrawn, and what it cost, is recorded in its own section rather than deleted.

---

## Paraphrasing it back

Today, starting a sprint means picking up the phone, unlocking it, finding zenpom and pressing Start.
`C21` — the Focus runbook, first in the v1.5 order — will tell you how to build an iOS Focus that
allows zenpom and silences everything else, but it is a thing you do *by hand*, separately, before
you press Start. Two actions, in a fixed order, one of which is invisible once you are working.

F10 makes the second of those two actions available to Shortcuts, so the pair can be one tap or one
automation. The Shortcut turns on the Focus and then tells zenpom to begin. **The value is not that
starting a sprint becomes faster** — it is already one tap inside the app. The value is that the step
you would otherwise forget is now welded to the step you never forget, and the sprint that most
needed the Focus is exactly the sprint during which you would have forgotten to set it.

**Mechanically this is now very small, and after the 2026-09-09 ruling it is smaller than it was.**
`ZenTomato/Shared/DismissBlockIntent.swift` already proves the mechanism end to end: a `struct`
conforming to an App Intents protocol, a `static let title`, a `perform()` that does one thing, and a
known fixed place to look for the running app's object graph. F10 is a second command through the
same door, and everything the command must *decide* has been moved out of it. **Almost all of the
work in this plan is in what the command must not do**, and in phrasing an answer somebody standing
in another room can act on.

## The ruling of 2026-09-09, and what it withdrew

**RULED BY THE OWNER: `F14`'s `BlockLauncher` is the single engine entry point.** Every way of
starting a block — the in-app Start button, the wrist, this App Intent, and later `F17`'s
complication — goes through it. **`F10` is a caller. It builds no seam of its own.**

### What was withdrawn

The previous version of this plan proposed **`TimerEngineHolder.startSprint()`** — a second static
function beside the existing `dismissRunningBlock()`, whose whole body was `await engine?.start()` —
and named it as the shared surface `F14` would inherit. **That design is withdrawn in full.** So is
the paragraph that told `F14`'s gate to answer this plan if it proposed a different path; the
argument ran the other way and `F14` won it.

### Why, and it is not a naming preference

`TimerEngine.start()` is declared at `ZenTomato/Timer/TimerEngine.swift:302`, and lines 303–313 read,
in order: `guard !isRunning else { return }` (303), clear `lastFailure` and `lastCompletedSprintSize`
(304–305), then lines 307–311 verbatim

```
authorization = alarms.authorization
if authorization == .notDetermined {
  authorization = await alarms.requestAuthorization()
}
guard authorization == .authorized else { return }
```

**That `await` is the whole reason the withdrawn design was wrong.** It is correct behaviour for a
thumb on the screen: somebody is looking at the phone, a permission sheet appears, they answer it,
the block starts. It is wrong for every remote door. A Shortcut fired at a phone in another room — or
by a time-of-day automation with nobody in the house — would reach a permission prompt nobody can
see, and `start()` would sit awaiting an answer that is not coming. A thin `startSprint()` forwarding
straight to `start()` inherits that verbatim and has nowhere to put the judgement, because a function
whose body is one call has no room for one.

`BlockLauncher` is where that judgement lives, along with three others F10 also needs and would
otherwise have had to invent: **freshness**, **duplicate suppression**, and **the already-running
case**. `F14`'s plan reaches the same conclusion in its own words, and reached it first — *"It is exactly
right for a thumb on the screen … It is exactly wrong for every other door"* (`docs/plans/F14.md:219`).

### The price of the withdrawal, stated rather than buried

Three real costs, so the refused option shows what it was buying:

1. **F10 can no longer be built before `F14-T1`.** The ratified order already puts `F14` sixth and
   `F10` seventh, so this costs nothing *as ordered* — but it turns a soft ordering preference into a
   hard dependency, and if `F14` slips, F10 slips with it or F10 builds `F14-T1` itself. That is
   Open Question 5.
2. **A second file now sits between the intent and the engine.** The withdrawn design had one hop
   (intent → holder → engine); this has two (intent → launcher → engine), and a reviewer reading only
   the intent file learns less than they used to. The compensation is that the extra hop is the file
   where the interesting decisions are, and it is tested once for three callers instead of three
   times.
3. **F10 stops owning its own refusals.** The outcome list the Shortcut sees is `F14`'s enum, not
   F10's. If `F14` names an outcome badly, F10 inherits the bad name and cannot fix it alone. Better
   than two enums that disagree, which is what the withdrawn design would have produced by the second
   feature.

### What F10 hands to `F14`, and what it keeps

The owner asked that nothing worth keeping be lost with the seam. Read through, three things in the
old plan were load-bearing. **Two of them stay in F10, because they guard F10's own file**, and one
belongs to `F14`.

| From the old plan | Where it goes now |
|---|---|
| The **parameterless-intent fence** and the **no-capture-surface guard** (old section 1) | **Contested — the gate must settle it, and this plan does not.** This plan keeps it in `F10-T1`. But `docs/plans/F14.md:300–305` has already claimed it — *"That fence moves here, because the door it guards is now this plan's"* — as **`noCaptureAtAnyDoor`**, written in `F14-T1`, failing on `@Parameter`, `AppEntity`, `EntityQuery`, `IntentParameter` or `ParameterSummary` anywhere under `ZenTomato/` or `ZenTomatoWatch/`, with `F14-M7` as its mutation. So the sentence this row used to carry — *"there is nothing for `F14` to hold"* — was **false against the file as written**. Either `F14-T1` ships that fence and `F10-T1` shrinks to what is genuinely F10's alone (the existence assertion on `StartSprintIntent`, and Fence B), or `F14` drops it. **Two fences of the same shape is the outcome to avoid; which one goes is the owner's call, not this plan's.** |
| **What a Shortcut-started sprint attaches to** (old section 3) | **Stays in F10 as a statement of fact**, and it agrees with `F14` exactly: nothing new is built, `takeNextAttachment()` is the only rule. |
| **Starting on top of a running block must not discard the log in progress** (old section 3) | **Belongs to `F14`.** It is now `BlockLauncher`'s `alreadyRunning` outcome, and F10 asserts it from its own door rather than implementing it. |

**RULED 2026-09-09 by the owner: `F14-T1`'s wide fence wins.** `noCaptureAtAnyDoor` scans both `ZenTomato/` and `ZenTomatoWatch/`, and it is the only capture fence on any launch door. The narrow per-intent fence is withdrawn — two fences of the same shape is how one of them gets deleted as redundant by somebody who can only see one. Whichever plan owns the fence also owns promoting `swiftFiles(under:)` and `code(of:)` off `private` on `StatsFenceTests`; that is `F14`.


**This plan does not edit `docs/plans/F14.md`** — that file has its own gate and, at the time of
writing, another author. The third row above is therefore recorded here as a **requirement F10 brings
to `F14`'s gate**, in one sentence so it can be checked: *`BlockLauncher`'s `alreadyRunning` path
writes no row, records no reason, cancels no alarm and calls `TimerEngine.stop(reason:)` under no
circumstances.* `F14`'s plan already implies this — its scope fence refuses a wrist Stop for exactly
the `stop(reason:)` argument — but implication is not a fence, and F10's `F10-T3` asserts it from the
Shortcuts side regardless of what `F14` writes down.

## The two things this plan is still actually about

### 1. The command takes no parameters, ever, and something enforces it

**`SPEC.md`'s out-of-scope list says "any capture surface of any kind", and `CLAUDE.md` states it as
a standing rule: the app never accepts a new task from the user.** The rule has always been argued in
terms of text fields — `StatsFenceTests.noCaptureSurfaceInThisFeature`
(`ZenTomatoTests/StatsFenceTests.swift:210`) greps a feature's files for `TextField`, `SecureField`,
`TextEditor`, `.searchable` and `UITextField`, which is the right fence for a screen.

**An App Intent parameter is a capture surface with a different shape, and the existing fence cannot
see it.** `@Parameter var task: String` is *understood* to compile into a field that Shortcuts draws
and that Siri will dictate into — **a framework claim, unverified here, and listed as such below** —
and that a user fills in with a task name: a task that exists nowhere in Todoist, born inside zenpom,
attached to a pomodoro and written into the log. It would pass every capture test in the suite,
because none of them look at App Intents and none of them look for `@Parameter`.

**And a Shortcut is exactly where somebody would add one.** The natural next request after "start a
sprint" is "start a sprint on *this*", and it will feel like a small addition to an intent that
already exists. It is not small. It is the rule change `docs/specs/zenpom-v1.5.md` files under
*"Never — not deferred"*.

**The ruling changed nothing about this, and that is worth saying explicitly.** Routing through
`BlockLauncher` does not protect the rule: the parameter would be added to the *intent*, and the
launcher would receive a perfectly ordinary request with a task name attached to it. The fence has to
sit on the intent's own source, which is F10's file, which is why this stays here.

**So F10 ships the fence with the feature**, in `T1`, not as a garnish on the end: a test that reads
the app's own Swift sources — a directory scan, not one filename, for the reason in `T1` — and fails
if `@Parameter`, `AppEntity`, `EntityQuery`, `IntentParameter` or `ParameterSummary` appears in it.
`WatchLinkTests` is the precedent — it reads the watch target's sources rather than a hand-maintained
file list, for the same reason.

**And the overlap has to be named here too, because this is where the argument lives.** `F14-T1`
already plans the same scan under the name `noCaptureAtAnyDoor` (`docs/plans/F14.md:300–305`, mutation
`F14-M7`). The reasoning above is unaffected — the fence is right either way — but **who writes it is
an open item for the gate**, and it is the first row of the withdrawal table above. If `F14` keeps it,
`F10-T1` keeps only the parts no all-of-`ZenTomato/` scan can do: the assertion that
`StartSprintIntent` exists and Fence B's thin-caller check.

**A note for a reviewer who greps and gets a fright.** `StatsFenceTests.nothingOutOfScopeAndNoForcedShortcuts`
(`StatsFenceTests.swift:227`) lists `"AppIntent"` among its forbidden words, scoped to
`Self.featureFiles`. That list is **not** only F6's directories. Read at `StatsFenceTests.swift:280`,
it is `ZenTomato/Stats`, `ZenTomato/Export`, `ZenTomato/Sprint`, every `ZenTomato/Views/Stats*.swift`
— **plus four named edited files**: `ZenTomato/Views/TimerScreen.swift`,
`ZenTomato/Views/TimerView.swift`, `ZenTomato/Views/PlanBuilderView.swift` and
**`ZenTomato/App/ZenTomatoApp.swift`**.

That last one is the one that matters, because `ZenTomatoApp.swift` is where this project already
sets `TimerEngineHolder.engine`, and it is the plausible landing site for whatever app-side wiring
lets an intent find `BlockLauncher` (Open Question 4). **So the correct statement is conditional, not
absolute:** the ban is not tripped *provided* F10 adds no `AppIntent`, `WidgetKit`, `Theme` or
`CloudKit` token to any of those four files. The intent file itself lives elsewhere and is
unaffected, as `DismissBlockIntent` already is. The fence strips comments before searching
(`Self.code(of:)`, `StatsFenceTests.swift:326`), so an explanatory comment is safe; a symbol is not.

**`T2` and `T3` must therefore state, as a checkpoint condition, that they touched none of those four
files** — or, if `T3` genuinely needs to, the fence is *narrowed* with the argument written down,
never widened and never deleted. `WatchLinkTests`' own comment explains what happens when a fence
that has gone wrong is deleted wholesale rather than narrowed.

### 2. What it attaches to, and what a second Shortcut mid-block must not destroy

**What a Shortcut-started sprint attaches to: whatever the session plan already says, through the
seam that already exists.** `ZenTomato/Plan/SessionAttaching.swift` is the engine's whole knowledge
of Todoist — one method, `takeNextAttachment()` (declared at line 31, implemented at
`SessionPlanStore.swift:296`, called at exactly one site, `TimerEngine.swift:724`), used once at the
start of each focus block and never for a break. Its header states the reason it pulls rather than
being pushed: *"Blocks begin with nobody looking."*

A Shortcut-started block is precisely that case, and it is the case the protocol was designed for.
**So F10 needs no attachment code at all.** A sprint started from a Shortcut attaches exactly as an
auto-started one does, which is exactly as a hand-started one does, which — after `F14` — is exactly
as a wrist-started one does. This is worth stating in the plan because "how does the Shortcut know
what task?" is the obvious question, and its correct answer is *the same way the app already knows*,
not *the Shortcut tells it*.

**It is also the strongest available property.** There is no second attachment rule to drift from the
first, nothing to keep in step, and nothing new for a review to check. `F14`'s plan reaches the same
place and rejects a "last attachment" fallback on `D21b`'s evidence; F10 inherits that ruling without
restating the argument.

**What happens when a block is already running: nothing, and the log of the block in progress is
untouched.** `TimerEngine.start()` opens with `guard !isRunning else { return }`
(`TimerEngine.swift:303`); after `F14`, a remote caller does not even reach it — `BlockLauncher`
answers `alreadyRunning` first.

**This is the ruling that matters most and it keeps its argument, because the argument is why the
requirement handed to `F14` is worded the way it is.** The only way out of a running block is
`TimerEngine.stop(reason:)` (`TimerEngine.swift:329`), and that method's own header says why: *"A
pomodoro is indivisible: it is finished or it is void, never paused and never quietly skipped."* It
requires a reason **by type**, so that *"a second caller added later cannot quietly stop a block
without one."* F10 is that second caller. An intent that started a fresh sprint on top of a running
one would have to either call `stop(reason:)` with a reason nobody typed — inventing a sentence for
the export's `Stopped early` section — or abandon the block some other way and lose its distraction
rows. Both discard the log of a block in progress, which is the one thing this app exists to produce.

**So the ruling is: `F10` never stops anything.** The intent is start-only. The word "stop" does not
appear in it and `T1`'s Fence B says so.

**The cost, stated rather than buried:** somebody who fires the Shortcut mid-block gets no visible
effect and may fire it again. That is the correct behaviour and it is also confusing, which is why
the intent must **report back** rather than silently succeed — `T3`. The alternative — refusing at
the Shortcuts level by making the intent unavailable while running — is believed not to be available,
on the understanding that iOS offers an intent from a cached description rather than by asking the
running app. **That is a claim about iOS and it is UNVERIFIED**; nothing in this checkout establishes
it and no command has been run against it. Nothing in this plan depends on it being true — if an
intent *can* withdraw itself, that is a smaller design, not a different feature.

## Open Question 6 is closed, by citation

The previous version of this plan asked the owner what the intent should do **when the queued block
is a break** — `TimerEngine.start()` begins `engine.kind`, and `goIdle(kind:completedInSprint:)`
(`TimerEngine.swift:823`) leaves a break queued after a completed pom with auto-start off — and
offered three candidates, one of which was *refuse unless a focus block is queued*.

**`F14` has already ruled it, and this plan does not re-ask.** From `docs/plans/F14.md`: the wrist
button is labelled from the queued block — *"Start focus · 25:00"* or *"Start short break · 5:00"* —
and the alternative *"make the wrist button pom-only and have the phone refuse when a break is
queued"* is **rejected**, on two grounds:

- it **gives the two devices different rules**, which is a second rule by another name; and
- it would **let the wrist skip a break the sprint had earned**, contradicting the doctrine already
  in the source that a long break is something a pom earns.

Both grounds apply verbatim to a third door. A Shortcut that refused when a break was queued would be
a third rule, and it would let an automation skip an earned break.

**So F10 starts whatever block is queued, and says which in what it reports back** — the old
candidate (a), now settled rather than asked. This also resolves the vocabulary problem that made the
question sharp: under `docs/specs/definitions.md` a **sprint** is the set of poms before the long
break and a **block** is any single timed span, so a door named *start a sprint* that may begin a
break was a definitions violation on its face. There is now no F10-owned function to misname —
`BlockLauncher.launch(_:)` is named for what it does. **The feature's user-facing title is the
ratified v1.5 sentence and stays**; what the Shortcut *reports* is what makes it honest.

**If the owner wants this reopened, it reopens at `F14`'s gate, not here** — one ruling, one place.

## What is not verifiable from this checkout

**Three things about how iOS behaves cannot be settled by reading this repository**, and the
convention that a decision about another system is not ratifiable until something has run applies to
each. They are Open Questions, not plan steps:

- whether `perform()` can reach a resident app's object graph at all when the phone is locked, or
  whether `openAppWhenRun` (or the `ForegroundContinuableIntent` / `opensIntent` family) is required;
- whether an `AppShortcutsProvider` phrase is wanted, which is a Siri surface and not merely a
  Shortcuts one;
- whether an intent can make itself unavailable while a block is running, or whether iOS offers it
  from a cached description regardless of the app's state.

**The old plan listed a fourth — whether `AlarmKit` will grant or prompt from a background launch.
It is no longer F10's question.** After the ruling, F10 never lets a prompt happen: the request
carries its source, `BlockLauncher` refuses to prompt for a remote one, and the intent reports
`notAuthorized` instead. Whether the prompt *would* have worked is now uninteresting, because nothing
asks.

**Two smaller framework claims elsewhere in this plan are unverified in the same way, and are marked
where they appear:** that `AppIntent.isDiscoverable` defaults to `true` (`T2`), and that an
`@Parameter` renders as a field Shortcuts draws and Siri dictates into (section 1). The second
changes nothing — the fence is built whether or not the mechanism is exactly that — but neither is
written here as established.

**These are stated as unverified. Writing them down does not test them.**

### Foundational — delivers nothing user-visible

#### `F10-T1` — The fences · owner: **agent**

**This task adds no engine code, no seam and no function on `TimerEngineHolder`** — that is the
withdrawal, made concrete. It adds two tests and nothing else, so there is genuinely nothing for a
person to see.

It is first because both fences can be written and *broken* before there is a feature standing on
them, and because a fence written after the file it guards is a fence written to fit.

**Fence A — no parameters.** A test failing on `@Parameter`, `AppEntity`, `EntityQuery`,
`IntentParameter`, `ParameterSummary`, and the capture patterns `StatsFenceTests` already uses.

**Three mechanics on Fence A, because the obvious way to write it is vacuous:**

1. **It scans a directory, not one filename** — every `.swift` under the app source, using
   `StatsFenceTests.swiftFiles(under:)` (`StatsFenceTests.swift:302`), or at minimum the whole
   intents directory. A fence pointed at one path stops fencing the day somebody adds a *second*
   intent file next to it, which is precisely how a parameter would arrive. **Both helpers named in
   this section are `private static` on `StatsFenceTests` today** (`:302` and `:326`), so a new test
   type cannot call them until they are promoted; `F14`'s plan already records that promotion as its
   own commit, which is a second reason the ownership question above has to be answered first.
2. **It asserts the file it expects is actually there.** A source-reading test whose target does not
   exist passes for the wrong reason — and between `T1` and `T2` the target genuinely does not exist,
   so this fence *starts* vacuous. The test must `#expect` that at least one intent file was found
   and that it declares `StartSprintIntent`, so `T1`'s checkpoint is honest: the fence is **written
   and seen red** in `T1`, and only goes green in `T2`.
3. **It reads code, not comments** — through `StatsFenceTests.code(of:)` (`StatsFenceTests.swift:326`),
   which strips comments first. A fence that cannot tell a refusal from a violation is one somebody
   switches off within a month, and this intent's doc comment will say the word *parameter*.

**Fence B — thin caller, start-only.** Two assertions in one test, and the second is new since the
ruling:

- the intent's stripped source mentions none of `stop`, `handleDismiss`, `abandon`, `recordSession`;
- **`perform()`'s body is a single call into `BlockLauncher` and contains no call to
  `TimerEngine.start()`, no `requestAuthorization`, and no `isRunning` check.** This is what "thin
  caller" means as a testable claim rather than an intention. It is deliberately narrower than
  `F14-T1`'s own `startHasOneCaller` fence — that one asserts the *engine* has one caller; this one
  asserts the *intent* re-implements none of the launcher's four judgements.

The comment-stripping matters more here than anywhere: the whole argument in section 2 will be
written into that file's header, in the words it forbids.

*Checkpoint:* the full existing suite passes unchanged with no production file added; Fence A is
**seen red** because the intent it guards does not exist yet; both fences are seen to fail when
deliberately broken (`F10-M1`, `F10-M2`). None of the four files in `StatsFenceTests.featureFiles` is
touched.

### Vertical slices

#### `F10-T2` — The intent · owner: **agent**

`StartSprintIntent`, conforming to `AppIntent` — **not** `LiveActivityIntent`, which is
`DismissBlockIntent`'s protocol (`DismissBlockIntent.swift:40`) and is the one appropriate to a button
on an alarm alert. Unlike that one it **is** discoverable: `DismissBlockIntent` sets
`isDiscoverable = false` explicitly at line 55 to stay out of Shortcuts, and the whole point of F10 is
the opposite. `isDiscoverable` is *believed* to default to `true` — **a framework claim, unverified;
confirmed by the device check rather than asserted, and stated explicitly in the source either way.**
That single line of difference carries the feature, and is therefore the line a review must look
hardest at.

**`perform()` is one call.** It builds a launch request — source, a moment, a request id, per
`F14`'s request type — hands it to `BlockLauncher`, and turns the outcome into what `T3` decides the
Shortcut sees. It reads no settings, checks no authorization, and asks the engine nothing.

**The source field is not a formality.** It is what tells `BlockLauncher` this is a remote door and
must never prompt, which is the whole substance of the 2026-09-09 ruling. If `F14`'s request type
turns out not to carry a source, F10 cannot get the behaviour it needs and that is a blocking
mismatch to raise at `F14`'s gate, not to work around here.

**Where the file lives.** `ZenTomato/Shared/` is compiled into the Live Activity extension as well
(`project.yml`, `ZenTomatoActivity` sources), and `DismissBlockIntent` is only there because the
widget needs the *name* of the command for its button — hence its `#if !WIDGET_EXTENSION` switch at
lines 69–71. **Nothing in the widget needs to start a sprint**, so this file should not be in
`Shared/` and should not need that switch. Proposed location: **`ZenTomato/Intents/`**, which does
not exist today (checked). A `project.yml` change is not required — the app target globs `ZenTomato`
wholesale.

*Checkpoint:* on a device, "ZenPom" appears in the Shortcuts app with one action, "Start a sprint",
which takes no inputs — and there is nothing in it to type into. Fence A goes green. None of the four
files in `StatsFenceTests.featureFiles` is touched.

#### `F10-T3` — What it says back · owner: **agent**

The honest half, and after the ruling it is mostly **translation**: `BlockLauncher` returns one
outcome and this task turns it into a sentence a Shortcut's owner can act on, plus the tests that
prove each one is reachable from this door.

`F14` names five outcomes — **started · alreadyRunning · stale · notAuthorized · unavailable**. Read
against F10's door specifically, which is not the same reading as the wrist's:

| Outcome | What F10 says, and whether F10 can even produce it |
|---|---|
| `started` | names the block that began — *focus* or *break*, per the closed OQ6 — and its length |
| `alreadyRunning` | *"A block is already running. Nothing was changed."* The important word is **nothing**. |
| `notAuthorized` | *"Alarm permission hasn't been granted. Open ZenPom once and allow alarms."* Never a prompt. |
| `unavailable` | no engine to reach — see below; this is the outcome Open Question 1 decides the frequency of |
| `stale` | **probably unreachable from this door**, because the intent mints `requestedAt` on the phone microseconds before the call. Stated as *probably* because I have not read `F14`'s freshness implementation — it does not exist yet. If it is unreachable, the test says so explicitly rather than asserting a case that cannot occur. |

**The `unavailable` case is F10's own problem and always was.** Whatever `BlockLauncher` is reached
through, something must find it in a process iOS may have reclaimed. For `DismissBlockIntent` a miss
is tolerable — reconciliation recovers the block from its stored end time
(`TimerEngineHolder.swift:52–65` explains exactly this). **For a start command there is nothing to
reconcile from: a sprint that was never begun leaves no trace, and a Shortcut that silently did
nothing is worse than one that failed.** Subject to Open Question 1, this task launches the app to
perform the command.

*Checkpoint:* a Shortcut run from a locked phone with the app not resident starts a real focus block;
the same Shortcut run mid-block reports that a block is already running **and leaves the running
block's distraction rows exactly as they were**; and with alarm permission refused it reports so
without any prompt appearing on the phone. Neither `ZenTomatoApp.swift` nor the three view files in
`StatsFenceTests.featureFiles` gains an `AppIntent` symbol; if `T3`'s answer to Open Question 1 forces
one, that fence is narrowed with the argument written down, and the narrowing is its own review item.

#### `F10-T4` — The log is unchanged · owner: **agent**

**The task that protects the reason the app exists.** A sprint started through the intent must
produce records indistinguishable from one started by thumb, and — after `F14` — from one started by
wrist: the same attachment from `takeNextAttachment()`, the same `Distraction` rows, the same session
rows, the same Markdown export. **No column says which door it came through, and none should.**

`StatsMarkdownGoldenTests` is the instrument — the export of a Shortcut-started sprint is compared
against the golden, and a difference is a defect in F10, not a new export format.

## Contract compliance, stated explicitly

- **No capture surface.** The intent takes no parameters. Fence A, Fence B and `F10-M1` enforce it.
  This is the feature's central risk and is treated as such.
- **Todoist writes are complete-task only.** F10 adds no Todoist call. The allowlist script sees no
  new endpoints.
- **Todoist owns the hierarchy.** F10 defines no task, project or tag; it reads the existing plan
  through the existing `SessionAttaching` seam, at the one site that already calls it.
- **Local only, no analytics, no network.** F10 adds none.
- **Secrets never enter the tree.** F10 touches no configuration.
- **The agent never edits `SPEC.md`.** This plan proposes no edit to it.

**No delta is owed, and here is the check rather than the assertion.** `docs/specs/zenpom-v1.5.md`'s
order table marks `F10` *"Delta owed? no"*. Against `SPEC.md`'s out-of-scope list line by line: an App
Intent is not a widget (the list bars *"widgets beyond the Lock Screen Live Activity"*, and an intent
is neither a widget nor a `WidgetKit` surface — `DismissBlockIntent` is already an intent and shipped
under `F2`); it is not a capture surface, **provided it takes no parameters**, which is why that
condition is a fence and not a footnote; it creates no Todoist task; it is not a theme, a streak, a
badge, macOS, CloudKit or a playlist. Against the locked-decisions table: it adds no timer
customization, so the *"Nothing else"* clause is untouched — it starts the block the settings already
describe.

**The withdrawal does not change this finding, and the check was re-run rather than assumed.** Calling
a shared launcher instead of a private seam adds no surface to the contract; it removes one.

**The no-delta finding holds only while the intent stays parameterless and start-only.** An intent
that took a task name, or a duration, would owe a delta and in the first case would be refused
outright.

## Scope fence

Not in F10. Each needs its own gate, and each would owe its own argument:

- **A duration parameter — "start a two-hour sprint".** **This is the thing most likely to be asked
  for mid-build**, because `F8` will have shipped by then and the arithmetic will already exist. It
  is out because a shape chosen outside the shape screen bypasses `F8`'s Ruling B — that a shape runs
  once and writes nothing *unless deliberately saved* — and because a shape needs to be seen before
  it is run. `F8`'s own scope fence already refuses "saving a shape for reuse", and a Shortcut holding
  a duration is a saved shape with a different owner.
- **A task-name parameter, or any parameter that names work.** Refused, not deferred. It is the
  capture surface under a different name and `docs/specs/zenpom-v1.5.md` files it under *"Never — not
  deferred"*.
- **A "stop the sprint" intent.** Out for the reason in section 2: an abandon needs a typed reason and
  an intent cannot ask for one. It is also the exact path `DismissBlockIntent`'s header records having
  *removed*.
- **A "complete the current task" intent.** It is a Todoist write from outside the app, and the one
  write this app is allowed is deliberately hand-made at the end of a pomodoro.
- **An `AppShortcutsProvider` Siri phrase**, unless Open Question 2 says otherwise. A spoken phrase is
  a second surface with its own failure modes and its own review.
- **Reporting timer state back to a Shortcut** — "how long is left". A read-only intent sounds free
  and is a second public description of the engine's state that can drift from the screen's.
- **Any change to `BlockLauncher`'s behaviour.** F10 may *use* it and may state requirements it needs
  from it, as it does above. Changing what it does — a new outcome, a different freshness rule, a
  source that behaves specially — is `F14`'s gate. **This fence is new, and it is the one the
  withdrawal creates:** the failure mode of a shared seam is a caller that adds one special case for
  itself.

## Open questions for the gate · owner: **human**

Batched. Nothing below `T1` starts until they are answered. **Seven** — the seventh added at review,
because `F14`'s plan and this one both claim the same fence and neither may decide that alone. Two of
the old six are gone —
Open Question 6 is closed by `F14`'s ruling, above, and the old Open Question 4 (where mutations are
recorded) is answered by namespacing them to this plan — and two are new, both created by the
withdrawal: how a system-invoked command finds `BlockLauncher`, and what happens if `F14` slips.

**1 — Does the intent open the app, or try to work in the background?**
This decides `T3`. `openAppWhenRun` makes the behaviour reliable — there is certainly a process to
reach — at the price of the phone unlocking and zenpom appearing on screen, which partly defeats "one
tap and get on with it". Not opening is quieter and may simply fail, because whatever the intent
looks up is `weak` and iOS reclaims a backgrounded app's memory whenever it likes. **I would pick
opening the app**, on the grounds that this app has already ruled once — in `DismissBlockIntent`'s
header — that a command which cannot reliably record what it did is worse than no command. But it is
a feel question about the owner's own morning routine and I should not settle it by reasoning.
**This is a claim about what iOS does, so whichever way it goes, it is confirmed by running it on the
device before the row is written.** Not from the SDK header.

**2 — Is a Siri phrase wanted, or is the Shortcuts action enough?**
The earned-entry sentence says *"a Shortcut"*, so the plan assumes no. Saying "start a sprint" out
loud is a real convenience and a real second surface. If it is wanted it should be at this gate, not
retrofitted.

**3 — What should the intent say back, and does it matter?**
`BlockLauncher` returns an enum; a Shortcut can branch on a returned value, but only if the owner
intends to build a Shortcut that does. If the answer is "it just needs to work", `T3` returns a
dialogue string and stops there; if the owner wants the Shortcut to notice, the intent returns a
value and that is a slightly larger design.

**4 — How does a system-invoked command find `BlockLauncher`?**
The ruling settled *which* type decides; it did not settle how an intent reaches it. `TimerEngineHolder`
exists because *"a command invoked by the system has no route into the app's object graph except a
known, fixed place to look"* (`TimerEngineHolder.swift:11–15`), and that reasoning is untouched by
the ruling. Two shapes: `TimerEngineHolder` gains a forwarding lookup that makes no judgement, or
`BlockLauncher` gets its own equivalent. **I would keep it in `TimerEngineHolder` — one global, one
file that knows it exists — but this is `F14`'s seam and F10 should not decide its shape.** Named
here so it is settled at one of the two gates rather than discovered at F10's build.

**5 — Order, and what happens if `F14` slips.**
F10 now hard-depends on `F14-T1`. The ratified order already puts `F14` sixth and `F10` seventh
(`docs/specs/zenpom-v1.5.md`, rows 6 and 7), so the ordinary path is fine. The question is the exception: if `F14` is deferred or cut, does F10 build `F14-T1` itself —
inheriting the review burden of a seam with three future callers — or does F10 wait? **I would have
F10 wait**, because a launcher built by its second caller is a launcher shaped like that caller. But
this is a milestone-pacing decision and the stop condition is four Rhodia reviews, not a feature list.

**6 — A rule and the evident need disagree, and I am naming it rather than picking.**
`docs/conventions.md` says *"write the plan before you write the code, and wait"*, while Open Question
1 is a load-bearing fact about what iOS will do that cannot be established without running something
on hardware — and the convention that a claim about another system is not ratifiable until something
has run points the other way. **I would answer Question 1 with a throwaway spike on the device before
`T2` is written**, kept out of the branch, with the result recorded here as an amendment. That is
neither building ahead of the gate nor ratifying a guess, but it is a shape this project has not used
before and the owner should say whether it is allowed. **`F14-T2` already proposes exactly this
shape** for its own two iOS questions, so the answer given at `F14`'s gate probably answers this one
too.

**7 — Which plan owns the parameterless fence, `F14-T1` or `F10-T1`?**
Both currently claim it: `F14-T1` as `noCaptureAtAnyDoor` scanning all of `ZenTomato/` and
`ZenTomatoWatch/` (`docs/plans/F14.md:300–305`, mutation `F14-M7`), and `F10-T1` as Fence A over the
intent sources. **Two fences of the same shape is the bad outcome** — the second one added is the one
somebody deletes as redundant, and deleting either takes the argument with it. The helpers both plans
lean on, `swiftFiles(under:)` and `code(of:)`, are `private` on `StatsFenceTests` today, so whichever
plan wins also owns promoting them. I have deliberately not picked: the fence guards F10's door but is
written before F10 exists, and that is a scheduling judgement across two gates, not a fact I can
establish by reading. **If `F14` keeps it, `F10-T1` still stands** — it keeps the `StartSprintIntent`
existence assertion and Fence B, and both still have mutations that break real code.
