# F10 — A "start a sprint" App Intent

**Status:** plan written, awaiting the gate. No code has been written.
**Spec:** `docs/specs/zenpom-v1.5.md`, item 7 in the ratified order — *"Lets a Shortcut turn on Do
Not Disturb and start a sprint together."*
**Baseline:** `docs/specs/SPEC.md` (v0.1) and `docs/specs/definitions.md`, both binding.
**Delta owed:** **none.** The argument is below and it was checked rather than assumed.

---

## Paraphrasing it back

Today, starting a sprint means picking up the phone, unlocking it, finding zenpom and pressing Start.
`C21` — the Focus runbook, first in the v1.5 order — will tell you how to build an iOS Focus that
allows zenpom and silences everything else, but it is a thing you do *by hand*, separately, before
you press Start. Two actions, in a fixed order, one of which is invisible once you are working.

F10 makes the second of those two actions available to Shortcuts, so the pair can be one tap or one
automation. The Shortcut turns on the Focus and then tells zenpom to begin. **The value is not that
starting a sprint becomes faster** — it is already one tap inside the app. The value is that the step
you would otherwise forget is now welded to the step you never forget, and the sprint that most
needed the Focus is exactly the sprint during which you would have forgotten to set it.

**Mechanically this is small, and it is small for a reason.** `ZenTomato/Shared/DismissBlockIntent.swift`
already proves the whole mechanism: a `struct` conforming to an App Intents protocol, a `static let
title`, a `perform()` that does one thing, and `TimerEngineHolder` as the one route from a
system-invoked command into the running app's object graph. F10 is a second command through the same
door. Almost all of the work in this plan is in what the command **must not** do.

## The three things this plan is actually about

### 1. The command takes no parameters, ever, and something enforces it

**`SPEC.md`'s out-of-scope list says "any capture surface of any kind", and `CLAUDE.md` states it as
a standing rule: the app never accepts a new task from the user.** The rule has always been argued in
terms of text fields — `StatsFenceTests.noCaptureSurfaceInThisFeature` greps a feature's files for
`TextField`, `SecureField`, `TextEditor`, `.searchable` and `UITextField`, which is the right fence
for a screen.

**An App Intent parameter is a capture surface with a different shape, and the existing fence cannot
see it.** `@Parameter var task: String` is *understood* to compile into a field that Shortcuts draws
and that Siri will dictate into — **a framework claim, unverified here, and listed as such below** —
and that a user fills in with a task name — a task that exists nowhere in Todoist, born
inside zenpom, attached to a pomodoro and written into the log. It would pass every capture test in
the suite, because none of them look at App Intents and none of them look for `@Parameter`.

**And a Shortcut is exactly where somebody would add one.** The natural next request after "start a
sprint" is "start a sprint on *this*", and it will feel like a small addition to an intent that
already exists. It is not small. It is the rule change the spec calls *"Never — not deferred"*.

**So F10 ships the fence with the feature**, in `T1`, not as a garnish on the end: a test that reads
the app's own Swift sources — a directory scan, not one filename, for the reason given in `T1` — and
fails if `@Parameter`, `AppEntity`, `EntityQuery`, `IntentParameter` or a
`ParameterSummary` appears in it. `WatchLinkTests` is the precedent — it reads the watch target's
sources rather than a hand-maintained file list, for the same reason.

**A note for a reviewer who greps and gets a fright — corrected at review, because the first version
of this paragraph read the fence's file list short.** `StatsFenceTests.nothingOutOfScopeAndNoForcedShortcuts`
lists `"AppIntent"` among its forbidden words, scoped to `Self.featureFiles`. That list is **not** only
F6's directories. Read at `ZenTomatoTests/StatsFenceTests.swift:280`, it is `ZenTomato/Stats`,
`ZenTomato/Export`, `ZenTomato/Sprint`, every `ZenTomato/Views/Stats*.swift` — **plus four named edited
files**: `ZenTomato/Views/TimerScreen.swift`, `ZenTomato/Views/TimerView.swift`,
`ZenTomato/Views/PlanBuilderView.swift` and **`ZenTomato/App/ZenTomatoApp.swift`**.

That last one is the one that matters, because `ZenTomatoApp.swift` is where this project already sets
`TimerEngineHolder.engine`, and it is the plausible landing site for any app-side wiring `T3` turns out
to need. **So the correct statement is conditional, not absolute:** the ban is not tripped *provided*
F10 adds no `AppIntent`, `WidgetKit`, `Theme` or `CloudKit` token to any of those four files. The
intent file itself lives elsewhere and is unaffected, as `DismissBlockIntent` already is. The fence
strips comments before searching (`Self.code(of:)`), so an explanatory comment is safe; a symbol is not.

**`T2` and `T3` must therefore state, as a checkpoint condition, that they touched none of those four
files** — or, if `T3` genuinely needs to, the fence is *narrowed* with the argument written down, never
widened and never deleted. `WatchLinkTests`' own comment explains what happens when a fence that has
gone wrong is deleted wholesale rather than narrowed.

### 2. One engine entry point, named now, because F14 comes through the same door

**`F14` — "the watch can launch a pom" — is item 6 in the ratified order, one place ahead of this
one.** It is the same operation from a different door: something outside the timer screen asks the
engine to begin a block. F10's door is Shortcuts; F14's door is a wrist.

**If the two features each build their own path, they will drift**, and the drift will be invisible
where it matters. The failure mode is specific and it has already happened once in this project's
history — `DismissBlockIntent`'s own header records it. A Lock Screen button that assumed what a tap
meant would have been "a second copy of the rule that could drift". The engine is asked rather than
told, and the rule lives in one tested place.

Here the drift would show up on a locked phone (F10's case, where the app may not be resident) or an
out-of-range watch (F14's case, where the message arrives late or not at all). Neither is a place a
disagreement gets noticed.

**The seam, named: `TimerEngineHolder.startSprint()`** — *the name is Open Question 6, see the
correction below; everything else in this paragraph holds whichever name is chosen* — a second static
function beside the existing
`dismissRunningBlock()`, in `ZenTomato/Alarm/TimerEngineHolder.swift`. It is a named function on the
holder rather than the intent reaching in and calling the engine itself, for exactly the two reasons
the existing one gives in its own comment: it keeps the count of places that know the global exists
at one file, and it puts the explanation of what happens when there is no engine in one place instead
of at every call site.

**`F14` shares this function.** Written here, at F10's gate, so that F14's gate inherits it as a fact
rather than rediscovering it. If F14's plan proposes a second path into the engine, this paragraph is
the argument it has to answer.

**A correction from review, and it is load-bearing: `start()` does not start a sprint. It starts
whatever block is queued, and that block is sometimes a break.** `TimerEngine.start()` calls
`begin(kind: kind, …)` with the engine's *current* `kind`, and `goIdle(kind:completedInSprint:)` at
`ZenTomato/Timer/TimerEngine.swift:823` is reached with `transition.kind` when a focus block ends and
auto-start is off or the sprint has ended (`TimerEngine.swift:801–802`). So after a pom finishes with
auto-start off, the engine sits idle **with a break queued**, and `start()` begins that break. The
app's single Start button has the same behaviour, and gets away with it because the screen is showing
the block kind next to the button. **A Shortcut caller sees nothing**, which is exactly the "a command
that cannot reliably say what it did" problem `DismissBlockIntent`'s header rules on.

This bears on the seam's *name*, too. `docs/specs/definitions.md` is binding and says a **sprint** is
the set of poms before the long break, a **pom** is one focus block, and a **block** is any single
timed span. A function called `startSprint()` that may begin a short break is a definitions violation
on its face. The feature's *title* is the ratified v1.5 sentence and stays; the seam should be named
for what it does.

**This is an owner decision and is left open rather than settled here — Open Question 6.** The three
candidates, so the answer is cheap: (a) the seam is `startNextBlock()` and the intent starts whatever
is queued, break included, and says which in what it reports back; (b) the seam is `startSprint()`
and it refuses unless a focus block is queued, which is new behaviour the engine does not have today
and therefore owes its own argument; (c) the intent reports "a break is queued" as a fourth outcome
and starts it anyway. **Nothing in `T1` is written until this is answered**, because it decides both
the seam's name and `T3`'s outcome list.

**What it does underneath, on candidate (a): `await engine?.start()`, and nothing else.**
`TimerEngine.start()` at `ZenTomato/Timer/TimerEngine.swift:302` already contains every rule that matters — it refuses if a
block is running, clears `lastFailure`, asks for alarm authorization if it has not been asked, refuses
to begin without it, and calls `begin(...)` with the settings read fresh. **F10 must not reimplement
any of that**, and the fence in `T1` says so by construction: the intent's `perform()` is one call
into the holder, as `DismissBlockIntent`'s is.

**The alternative that lost: an intent that starts a block directly.** It would let F10 do something
`start()` cannot, such as begin at a particular length. Its price is a second copy of the
authorization check, the running-block check and the settings read — three rules that would then have
two implementations, one of which is only ever exercised on a locked phone. It also owes a delta,
because a length chosen outside the settings screen is `F8`'s territory. Refused.

### 3. What it attaches to, and what happens when a block is already running

**What a Shortcut-started sprint attaches to: whatever the session plan already says, through the seam
that already exists.** `ZenTomato/Plan/SessionAttaching.swift` is the engine's whole knowledge of
Todoist — one method, `takeNextAttachment()`, called once at the start of each focus block and never
for a break. Its header states the reason it pulls rather than being pushed: *"Blocks begin with
nobody looking."* A Shortcut-started block is precisely that case, and it is the case the protocol was
designed for. **So F10 needs no attachment code at all.** A sprint started from a Shortcut attaches
exactly as an auto-started one does, which is exactly as a hand-started one does. This is a fact worth
stating in the plan because "how does the Shortcut know what task?" is the obvious question, and its
correct answer is *the same way the app already knows*, not *the Shortcut tells it*.

**What happens when a block is already running: nothing, and that is the design.** `TimerEngine.start()`
opens with `guard !isRunning else { return }`. A second Shortcut fired mid-block reaches the engine and
is refused. **The log of the block in progress is untouched** — no row is written, no reason is
recorded, no alarm is cancelled.

**This is the ruling that matters most and it deserves its argument.** The only way out of a running
block is `TimerEngine.stop(reason:)`, and that method's own header says why: *"A pomodoro is
indivisible: it is finished or it is void, never paused and never quietly skipped."* It requires a
reason **by type**, so that "a second caller added later cannot quietly stop a block without one." F10
is that second caller. An intent that started a fresh sprint on top of a running one would have to
either call `stop(reason:)` with a reason nobody typed — inventing a sentence for the export's
`Stopped early` section — or abandon the block some other way and lose its distraction rows. Both
discard the log of a block in progress, which is the one thing this app exists to produce.

**So the ruling is: `F10` never stops anything.** The intent is start-only. The word "stop" does not
appear in it and a test says so.

**The cost, stated rather than buried:** somebody who fires the Shortcut mid-block gets no visible
effect and may fire it again. That is the correct behaviour and it is also confusing, which is why the
intent must **report back** rather than silently succeed — see the open question on dialogue below.
The alternative — refusing at the Shortcuts level by making the intent unavailable while running — is
believed not to be available, on the understanding that iOS offers an intent from a cached description
rather than by asking the running app. **That is a claim about iOS and it is UNVERIFIED**; nothing in
this checkout establishes it and no command has been run against it. It is listed with the other three
in the unverified section below. Nothing in this plan depends on it being true — if it turns out an
intent *can* withdraw itself, that is a smaller design, not a different feature.

## What is not verifiable from this checkout, and is therefore an open question rather than a plan step

**Four things about how iOS behaves cannot be settled by reading this repository**, and the
convention that a decision about another system is not ratifiable until something has run applies to
each. They are in the Open Questions section rather than asserted here:

- whether `perform()` can reach a resident engine at all when the phone is locked, or whether
  `openAppWhenRun` (or the `ForegroundContinuableIntent` / `opensIntent` family) is required;
- whether `AlarmKit` will grant or even prompt for authorization from a background launch, given
  `start()` awaits `alarms.requestAuthorization()` when authorization is `.notDetermined`;
- whether an `AppShortcutsProvider` phrase is wanted, which is a Siri surface and not merely a
  Shortcuts one;
- whether an intent can make itself unavailable while a block is running, or whether iOS offers it
  from a cached description regardless of the app's state (section 3).

**Two smaller framework claims elsewhere in this plan are unverified in the same way, and are marked
where they appear:** that `AppIntent.isDiscoverable` defaults to `true` (`T2`), and that an
`@Parameter` renders as a field Shortcuts draws and Siri dictates into (section 1). The second changes
nothing — the fence is built whether or not the mechanism is exactly that — but neither is written
here as established.

**These are stated as unverified.** Writing them down does not test them.

### Foundational — no user-visible change

#### `F10-T1` — The seam and the fences · owner: **agent**

Adds the seam on `TimerEngineHolder` — `await engine?.start()`, with the same "this may legitimately
do nothing" explanation the existing `dismissRunningBlock()` carries. **Its name is Open Question 6**:
`startSprint()` as written throughout this plan, or `startNextBlock()`, which is what the function
actually does under `definitions.md`'s vocabulary — and nothing else. No intent
yet, so nothing a person can see changes.

It is first because it is the shared surface `F14` inherits, and because both fences can be written
and *broken* before there is a feature standing on them.

**Fence A — no parameters.** A test failing on `@Parameter`, `AppEntity`, `EntityQuery`,
`IntentParameter`, `ParameterSummary`, and the capture patterns `StatsFenceTests` already uses. It is
written in `T1` even though the file it guards arrives in `T2`, so that the fence exists before the
thing it fences.

**Three mechanics on Fence A, added at review, because the obvious way to write it is vacuous:**

1. **It scans a directory, not one filename** — every `.swift` under the app source, using
   `StatsFenceTests`' own `swiftFiles(under:)` helper, or at minimum the whole intents directory. A
   fence pointed at one path stops fencing the day somebody adds a *second* intent file next to it,
   which is precisely how a parameter would arrive.
2. **It asserts the file it expects is actually there.** A source-reading test whose target does not
   exist passes for the wrong reason — and between `T1` and `T2` the target genuinely does not exist,
   so this fence *starts* in the vacuous state. The test must `#expect` that at least one intent file
   was found and that it declares `StartSprintIntent`, so `T1`'s checkpoint is honest about it: the
   fence is **written and seen red** in `T1`, and only goes green in `T2`.
3. **It reads code, not comments** — through `StatsFenceTests.code(of:)`, which strips comments first.
   That file's own header explains why: a fence that cannot tell a refusal from a violation is one
   somebody switches off within a month, and this intent's doc comment will say the word *parameter*.

**Fence B — start-only.** A test failing if the intent's stripped source mentions `stop`,
`handleDismiss`, `abandon` or `recordSession`, and asserting that `perform()`'s body is a single call
into `TimerEngineHolder`. The comment-stripping matters here more than anywhere: the whole argument in
section 3 will be written into that file's header, in the word it forbids.

*Checkpoint:* the full existing suite passes unchanged with the new function present and unused; Fence
A is **seen red** because the intent it guards does not exist yet; and both new fences are seen to fail
when deliberately broken (below). None of the four files in `StatsFenceTests.featureFiles` is touched.

### Vertical slices

#### `F10-T2` — The intent · owner: **agent**

`StartSprintIntent`, conforming to `AppIntent` — **not** `LiveActivityIntent`, which is
`DismissBlockIntent`'s protocol and is the one appropriate to a button on an alarm alert. Unlike that
one it **is** discoverable — `isDiscoverable` is believed to default to `true` (**a framework claim,
unverified; confirmed by the device check rather than asserted, and stated explicitly in the source
either way**) and the whole point is that Shortcuts can see it — which is the single
line of difference that carries the feature, and therefore the line a review must look hardest at.

Whether the file belongs in `ZenTomato/Shared/` or somewhere app-only turns on one thing: `Shared/`
is compiled into the Live Activity extension as well (`project.yml`, `ZenTomatoActivity` sources), and
`DismissBlockIntent` is only there because the widget needs the *name* of the command for its button.
**Nothing in the widget needs to start a sprint**, so this file should not be in `Shared/` and should
not need the `WIDGET_EXTENSION` compile-time switch. Proposed location: `ZenTomato/Intents/`. A
`project.yml` change is not required — the app target globs `ZenTomato` wholesale, which is the point
of the directory glob comment in that file.

*Checkpoint:* on a device, "ZenPom" appears in the Shortcuts app with one action, "Start a sprint",
which takes no inputs — and there is nothing in it to type into.

#### `F10-T3` — When there is no engine, and what it says back · owner: **agent**

The honest half. `TimerEngineHolder.engine` is `weak` and set once at launch by `ZenTomatoApp`
(`ZenTomato/App/ZenTomatoApp.swift:147`), so a command that arrives while iOS has reclaimed the app's
memory reaches nothing. For `DismissBlockIntent` that is tolerable — reconciliation recovers the block
from its stored end time. **For a start command there is nothing to reconcile from: a sprint that was
never begun leaves no trace, and a Shortcut that silently did nothing is worse than one that failed.**

This task settles it, subject to Open Question 1: launch the app to perform the command, and return a
result the Shortcut can act on. Outcomes to distinguish, none of them an error in the ordinary
sense: **started** · **already running, nothing changed** · **alarm permission is not granted, so
nothing was started** — and, depending on Open Question 6, **a break was queued, not a pom**.

*Checkpoint:* a Shortcut run from a locked phone with the app not resident starts a real focus block,
and the same Shortcut run mid-block reports that a block is already running and leaves the running
block's distraction rows exactly as they were. Neither `ZenTomatoApp.swift` nor the three view files in
`StatsFenceTests.featureFiles` gains an `AppIntent` symbol; if `T3`'s answer to Open Question 1 forces
one, that fence is narrowed with the argument written down, and the narrowing is its own review item.

#### `F10-T4` — The log is unchanged · owner: **agent**

**The task that protects the reason the app exists.** A sprint started through the intent must produce
records indistinguishable from one started by thumb: the same attachment from `takeNextAttachment()`,
the same `Distraction` rows, the same session rows, the same Markdown export.

`StatsMarkdownGoldenTests` is the instrument — the export of a Shortcut-started sprint is compared
against the golden, and a difference is a defect in F10, not a new export format. If a scope decision
ever threatens the log, the log wins.

*Checkpoint:* the export of a Shortcut-started sprint, read beside the export of a hand-started one,
identical but for timestamps.

## Mutations

**A test that has never been shown to fail is not evidence.** Each is applied to the shipped code, the
named test is *seen* to fail, and the suite count is recorded before the task is called done.

| # | Break it like this | The test that must fail |
|---|---|---|
| 1 | Add `@Parameter var taskName: String` to `StartSprintIntent` and use it in `perform()` | Fence A — `noParametersOnTheStartIntent` |
| 2 | Make `perform()` call `TimerEngineHolder` *and* record a session row directly | Fence B — `theStartIntentOnlyStarts` |
| 3 | Delete the `guard !isRunning` from `TimerEngine.start()` and fire the intent mid-block | `startingTwiceLeavesTheRunningBlockAlone` (`T3`) — must fail on the distraction rows of the block in progress, not merely on a state flag |
| 4 | Delete `guard authorization == .authorized` from `TimerEngine.start()` and fire the intent with permission refused | `theIntentCannotStartWithoutAlarmPermission` (`T3`) |
| 5 | Make `begin(...)` skip `takeNextAttachment()` for the block the intent started | `aShortcutStartedPomAttachesLikeAnyOther` (`T4`) |
| 6 | Point Fence A's scan at a path that does not exist | Fence A's own existence assertion — `noParametersOnTheStartIntent` must fail, not pass green on an empty file list |

**Mutations 4 and 5 were rewritten at review, and the reason is worth keeping.** As first written,
Mutation 4 said *"make `startSprint()` call `begin(...)` directly"* — **which does not compile.**
`begin(kind:completedInSprint:settings:)` is `private` to `TimerEngine` (`TimerEngine.swift:710`), so
`TimerEngineHolder` cannot reach it and the mutation could never be applied. A mutation that cannot be
applied is not a mutation; it is a sentence. Both now break `TimerEngine` where the rule actually lives.

**And the honest limitation on 5, stated rather than left to a reviewer to find.** Because F10 adds no
attachment code, there is no "intent path" to break — the mutation necessarily breaks shared engine
code, so it will fail several existing tests as well as the named one. It therefore proves the golden
comparison has teeth; it does **not** prove anything about code F10 owns, because F10 owns none here.
`T4` is a characterization test, not a fence, and the plan should not claim otherwise.

**Mutation 3 is the one to get right, and it is the one most likely to be written toothlessly.** An
assertion that checks `isRunning` is still `true` after the second start passes whether or not the log
survived — a fixture that satisfies both the right and the wrong implementation distinguishes nothing.
The test must record distraction taps in the first block, fire the intent, and assert the **rows** are
still there and still attached to the same block.

**This project has no `M<n>` register.** `docs/plans/00-register.md` holds `O`, `D` and `C` sections
only; the `M` register named in `docs/conventions.md` has never been created here. Stated rather than
worked around: the six mutations above are recorded with their counts in `docs/reviews/F10.md` at the
review, and whether they also earn register rows is a question for the owner (Open Question 4).

## Contract compliance, stated explicitly

- **No capture surface.** The intent takes no parameters. Two fences and Mutation 1 enforce it. This
  is the feature's central risk and is treated as such.
- **Todoist writes are complete-task only.** F10 adds no Todoist call. The allowlist script sees no
  new endpoints.
- **Todoist owns the hierarchy.** F10 defines no task, project or tag; it reads the existing plan
  through the existing `SessionAttaching` seam.
- **Local only, no analytics, no network.** F10 adds none.
- **Secrets never enter the tree.** F10 touches no configuration.
- **The agent never edits `SPEC.md`.** This plan proposes no edit to it.

**No delta is owed, and here is the check rather than the assertion.** `docs/specs/zenpom-v1.5.md`'s
order table marks `F10` *"Delta owed? no"*. Against `SPEC.md`'s out-of-scope list line by line: an App
Intent is not a widget (the list bars *"widgets beyond the Lock Screen Live Activity"*, and an intent
is neither a widget nor a `WidgetKit` surface — `DismissBlockIntent` is already an intent and shipped
under `F2`); it is not a capture surface, **provided it takes no parameters**, which is why that
condition is a fence and not a footnote; it creates no Todoist task; it is not a theme, a streak, a
badge, macOS, CloudKit or a playlist. Against the locked-decisions table: it adds no timer
customization, so the *"Nothing else"* clause is untouched — it starts the sprint the settings already
describe. **The no-delta finding holds only while the intent stays parameterless and start-only.** An
intent that took a task name, or a duration, would owe a delta and in the first case would be refused
outright.

## Scope fence

Not in F10. Each needs its own gate, and each would owe its own argument:

- **A task-name parameter, or any parameter that names work.** Refused, not deferred. It is the
  capture surface under a different name and `docs/specs/zenpom-v1.5.md` files it under *"Never — not
  deferred"*.
- **A duration parameter — "start a two-hour sprint".** This is the thing most likely to be asked for
  mid-build, because `F8` will have shipped by then and the arithmetic will already exist. It is out
  because a shape chosen outside the shape screen bypasses Ruling B's protection in `docs/plans/F8.md`
  — that a shape runs once and writes nothing *unless deliberately saved* — and because a shape needs
  to be seen before it is run. F8's own scope fence already refuses "saving a shape for reuse", and a
  Shortcut holding a duration is a saved shape with a different owner.
- **A "stop the sprint" intent.** Out for the reason given in section 3: an abandon needs a typed
  reason and an intent cannot ask for one. It is also the exact path `DismissBlockIntent`'s header
  records having *removed*.
- **A "complete the current task" intent.** It is a Todoist write from outside the app, and the one
  write this app is allowed is deliberately hand-made at the end of a pomodoro.
- **An `AppShortcutsProvider` Siri phrase**, unless Open Question 3 says otherwise. A spoken phrase is
  a second surface with its own failure modes and its own review.
- **Reporting timer state back to a Shortcut** — "how long is left". A read-only intent sounds free
  and is a second public description of the engine's state that can drift from the screen's.
- **Anything on the watch.** `F14` is its own gate; F10's contribution to it is the named seam and
  nothing more.

## Open questions for the gate · owner: **human**

Batched. Nothing below `T1` starts until they are answered.

**1 — Does the intent open the app, or try to work in the background?**
This is the one that decides `T3`. `openAppWhenRun` makes the behaviour reliable — there is certainly
an engine, permission can certainly be prompted for — at the price of the phone unlocking and zenpom
appearing on screen, which partly defeats "one tap and get on with it". Not opening is quieter and may
simply fail on a locked phone, because `TimerEngineHolder.engine` is `weak` and iOS reclaims a
backgrounded app's memory whenever it likes. **I would pick opening the app**, on the grounds that this
app has already ruled once — in `DismissBlockIntent`'s header — that a command which cannot reliably
record what it did is worse than no command. But it is a feel question about the owner's own morning
routine and I should not settle it by reasoning.
**This is a claim about what iOS does, so whichever way it goes, it is confirmed by running it on the
device before the row is written.** Not from the SDK header.

**2 — What should the intent say back, and does it matter?**
Three outcomes exist (started · already running · no alarm permission). A Shortcut can branch on a
returned value, but only if the owner intends to build a Shortcut that does. If the answer is "it just
needs to work", `T3` returns a dialogue string and stops there; if the owner wants the Shortcut to
notice, the intent returns a value and that is a slightly larger design.

**3 — Is a Siri phrase wanted, or is the Shortcuts action enough?**
The earned-entry sentence says *"a Shortcut"*, so the plan assumes no. Saying "start a sprint" out loud
is a real convenience and a real second surface. If it is wanted it should be at this gate, not
retrofitted.

**4 — Where do the six mutations get recorded?**
`docs/conventions.md` says mutations are `M<n>` rows in `docs/plans/00-register.md`. **This project has
no `M` section in that file and never has.** Either the section is created — which is a change to a
document the owner owns — or the mutations live in `docs/reviews/F10.md` with their counts, as this
project has done to date. I would create the section, because the convention exists and the absence
looks like drift rather than a decision; but creating a register section is not the agent's call.

**5 — A rule and the evident need disagree, and I am naming it rather than picking.**
`docs/conventions.md` says four to six tasks per feature and this plan has five, which is fine. The
disagreement is elsewhere: the same document says *"write the plan before you write the code, and
wait"*, while four of this plan's load-bearing facts are about what iOS will do and cannot be
established without running something on hardware — and the convention that a claim about another
system is not ratifiable until something has run points the other way. **I would answer Question 1 with
a throwaway spike on the device before `T2` is written**, kept out of the branch, with the result
recorded here as an amendment to this plan. That is neither building ahead of the gate nor ratifying a
guess, but it is a shape this project has not used before and the owner should say whether it is
allowed.

**6 — What does the intent do when the queued block is a break? (Added at review.)**
`TimerEngine.start()` begins whatever block is queued, and after a pom with auto-start off that is a
short or long break — verified in the engine, not assumed. So a Shortcut named "start a sprint" can
begin a break, and the caller cannot see which. Three answers, and this is a decision about the owner's
own morning rather than a fact to be looked up:

- **(a)** the seam is `startNextBlock()`, the intent starts whatever is queued, and what it reports
  back says which. Smallest, and honest about what the engine does.
- **(b)** the intent starts a *pom* and refuses when a break is queued. It matches the name and the
  ratified sentence — but refusing is behaviour `TimerEngine` does not have today, so it is new engine
  logic and owes its own argument, and possibly a delta.
- **(c)** it starts the break and reports that it did, as a fourth outcome in `T3`.

**This decides the seam's name, `T3`'s outcome list, and one line of `T5`**, which is why it is at the
gate and not in the build. Under `docs/specs/definitions.md` a **sprint** is the set of poms and a
**block** is any timed span, so (a) and (c) are the vocabulary-correct options; (b) is the one that
makes the *feature title* true. I have not picked.
