# F5 — Distraction log

**Gate:** requires F2 merged, your yes, and ratification of **D4** (end-of-pomodoro sequence).
**Branch:** `F5/distraction-log`
**Spec:** I/E buttons on the running-timer screen; tap → record; end-of-pomodoro sentence prompt;
persisted. *Done when:* a pomodoro with three taps yields three records with the right task and
timestamps.

## Summary

Built third, before either integration, because `SPEC.md` says this is the point of the app and because
after F5 you have something genuinely usable — a working timer and a working log — regardless of what
happens to F3, F4, and F7.

One principle governs the whole feature: **the tap is the record.** Tapping I or E writes a durable row
immediately. The sentence is an optional annotation added later, to a row that already exists. Nothing
about capture depends on the prompt appearing, on the sheet being dismissed, or on the app surviving
the next thirty seconds. The reviewer agent asks directly whether a record can be lost between the tap
and the prompt; this design's answer is no, structurally, rather than no, probably.

**Proposed spec delta:** D4 — see `00-deltas.md`.

## The model

```swift
enum DistractionKind { case internal, external }   // the spec's I and E

@Model final class Distraction {
    var id: UUID
    var kind: DistractionKind
    var timestamp: Date              // the instant of the tap, not of the note
    var note: String?                // nil = skipped, and skipped is a normal outcome
    var session: PomodoroSession?    // the pomodoro it happened in
    // F3 adds taskTitle / projectTitle snapshots — see below
}
```

**Why the task is snapshotted rather than referenced.** When F3 lands, each `Distraction` stores the
task's ID *and* a copy of its title text at the moment of the tap. Todoist is a live system: the task
you were distracted from can be renamed next Tuesday or completed and swept away entirely. If stats
resolved titles by ID at read time, a two-week-old review would show blanks or, worse, today's wording
over last week's reality. The snapshot means the Rhodia review reads what was true when it happened.
The cost is denormalisation, which is the right trade for an append-only log.

## Tasks

### F5-T1 — Capture

Two large buttons, **I** and **E**, on the running-timer screen. Tap → haptic → write → the button's
count badge increments. The write is synchronous to the store before the haptic returns; there is no
in-memory buffer, no debounce, no batching.

Visible only during a **work** block. A distraction during a break is not a distraction.

Sized for a glance, not a look: these are pressed by someone who has just noticed their attention
wandering and wants to spend under a second on it. Big targets, high contrast, no confirmation, no
undo-toast that steals focus. (An undo path is *not* built — a mis-tap costs one row in a log you read
in aggregate, and building undo would cost more attention at capture time than it saves at review time.)

### F5-T2 — The end-of-pomodoro sheet

Per D4, one sheet at the end of a work block:

```
Block ends → break timer starts immediately, behind the sheet
┌─ End of pomodoro ────────────────┐
│  I  14:32   [                 ]  │
│  E  14:41   [                 ]  │
│  I  14:58   [                 ]  │
│                                  │
│  [Complete task]        [Done]   │   ← Complete task arrives with F3
└──────────────────────────────────┘
```

- One field per tap, in the order they happened, each labelled with its kind and time.
- Every field is skippable. Leaving them all blank and tapping Done is a first-class outcome, not a
  failure — the counts alone are data.
- **The break is already running.** This is the load-bearing detail from D4. Reflection never eats
  break time, and a sheet left open while you walk away does not silently stretch your day.
- No taps that pomodoro ⇒ no sheet at all (until F3, which needs the Complete-task button to appear
  regardless; F3 revisits this).
- Dismissed by swipe or by the app being killed ⇒ notes stay `nil`. The rows survive. The sheet is not
  re-presented later; a sentence written an hour after the fact is not the self-knowledge data the
  spec is asking for, and a queue of nagging prompts is a capture surface by another name.

### F5-T3 — Reading it back

A minimal list grouped by day: each distraction's kind, time, task, and note. Enough to confirm the
data is real and to satisfy the *Done when*. Counting, aggregating, and exporting are F6 — this view
does not try to be a stats screen.

## Tests

| Test | Asserts |
|---|---|
| `threeTapsThreeRecords` | the spec's *Done when*, verbatim: 3 taps ⇒ 3 rows, right kinds, right session, timestamps in order |
| `tapIsDurableBeforePrompt` | rows readable from a fresh context immediately after the tap, before any sheet |
| `killedBetweenTapAndPrompt` | simulated termination after tap ⇒ rows intact, notes `nil` |
| `skippingLeavesNilNotNotEmpty` | skipped ⇒ `note == nil`, distinguishable from a deliberate empty string |
| `notesAttachToCorrectTap` | 3 taps, note only on the second ⇒ lands on the second |
| `breakStartsBehindSheet` | `endsAt` of the break is set at block end, not at sheet dismissal |
| `noTapsNoSheet` | zero taps ⇒ sheet not presented |
| `tapsOnlyDuringWork` | capture unavailable during short and long breaks |
| `titleSnapshotSurvivesRename` | (F3) task renamed after the tap ⇒ log still shows the old title |

## Risks

- **Sheet vs. AlarmKit.** The block-end alarm and the sheet fire at the same instant. If the phone is
  locked, the alarm surfaces first and the sheet must be waiting when the user opens the app — not
  swallowed by a presentation race. Tested by backgrounding across the boundary.
- **Ordering against F3.** F5 ships before Todoist exists, so `taskTitle` is nil for every row captured
  before F3 merges. Those early rows are real data you will have generated by then, so F3 must add the
  columns as genuinely optional and F6 must render "no task" without apology, rather than treating a
  nil task as a bug. Noted here so it is not discovered in F6.
- **`internal` is a Swift keyword** — the enum case needs backticks or a different spelling. Trivial,
  but it is the kind of thing that produces a confusing first compile error.
