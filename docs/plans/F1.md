**Spec:** *F1 — Skeleton.* SwiftUI app, SwiftData store, settings model, SwiftLint, GitHub Actions CI

app launches to an empty timer.

## Summary

There is no Xcode project in this repository. F1 creates one and everything that will police it: the
lint gate, the test gate, the secret scan, and the no-Todoist-writes grep. Nothing user-facing ships
beyond an empty timer screen.

The important thing about F1 is that it is where the hooks are built. `CLAUDE.md` says the deterministic
hooks are what actually protect the non-negotiables and that "prose is advisory" — which means until F1
merges, every rule in this repo is enforced by nothing but my good behaviour. That makes F1 the highest-
leverage feature in the project even though it is the least interesting.

**Proposed spec delta:** D1 (minimum iOS 26.0) and D6 (secrets in `.env`) — see `00-deltas.md`. F1 is
blocked on both.

### F1-T3 — SwiftData store and settings model

```swift
@Model final class AppSettings {
    var workMinutes: Int          // 25
    var shortBreakMinutes: Int    // 5
    var longBreakMinutes: Int     // 15
    var pomodorosPerSprint: Int   // 4
    var soundEnabled: Bool        // true
    var autoStartNextBlock: Bool  // false
}
```

Exactly the six fields `SPEC.md` permits under *Timer customization* — "Nothing else." Note what is
deliberately **absent**: there is no `musicEnabled` here. The spec's music on/off is described as a
toggle "before a sprint," which makes it session state owned by F4, not a timer customization. Putting
it in this model would be the kind of small, reasonable-looking scope creep the reviewer is told to fail.

`ModelContainer` is built in the app entry point. `AppSettings` is a single-row model reached through a
`current(in:)` accessor that creates the row with defaults on first launch — documented as a deliberate
singleton-row choice so a future reader does not "fix" it into a collection.

Settings live in SwiftData rather than `@AppStorage` so there is one store to reason about, one
migration story, and one thing to back up — rather than settings in `UserDefaults` and everything the
app is actually for in SwiftData.

### F1-T5 — Secrets pipeline (D6)

- `.env` — git-ignored, already present, holds `TODOIST_CLIENT_ID`, `TODOIST_CLIENT_SECRET`,
  `TODOIST_OAUTH_CALLBACK_SCHEME`.
- `.env.example` — committed, same keys, empty values. The repo documents what is required without
  holding one.
- `scripts/gen-secrets.sh` — reads `.env`, writes git-ignored `Secrets.xcconfig`. Runs as a build phase
  ahead of compile. Fails the build with a readable message if `.env` is missing or a key is empty,
  rather than producing an app that fails mysteriously at the OAuth callback in F3.
- CI has no `.env`; the workflow writes one from GitHub Actions encrypted secrets before building.

Nothing reads `.env` at runtime. The generated `Secrets.xcconfig` is disposable — deleting it and
rebuilding must reproduce it exactly, and the plan's test list includes that.

### F1-T7 — The four hooks

`CLAUDE.md` names four. All four run in **both** pre-commit and CI — pre-commit for fast feedback,
CI because a pre-commit hook is trivially bypassed with `--no-verify` and branch protection is the only
gate that actually holds.

| Hook | Script | Fails when |
|---|---|---|
| Lint | `swiftlint --strict` | any warning |
| Tests | `xcodebuild test` | any failure (CI only — too slow for pre-commit) |
| No Todoist writes | `scripts/check-todoist-writes.sh` | see below |
| No secrets | `gitleaks detect` + `scripts/check-secrets.sh` | any match |

**The no-writes hook is the one that needs care.** A naive grep for `POST` fails instantly and
uselessly, because F3's own OAuth token exchange is a POST and completing a task is a POST. The rule
is not "no POST" — it is "the only mutating Todoist request is task completion."

Implementation: grep the tree for string literals containing `api.todoist.com` or a Todoist path, and
assert every one appears in the allowlist in `scripts/todoist-allowed-endpoints.txt`. Any Todoist URL
that is not on the list fails the build, so the failure mode is a *new endpoint appearing* rather than
a guess about which HTTP verb was used. The allowlist is committed, so adding to it is a visible diff
that shows up in review and in the reviewer agent's scope check — which is exactly the property we
want. F1 seeds it with the read endpoints and `/tasks/{id}/close`; F3 is where it earns its keep.

Pre-commit hooks live in `.githooks/` and are activated with `git config core.hooksPath .githooks`. That
one command is the only manual step and it goes in the README, because a hook nobody enabled is prose.

## Tests

| Test | Asserts |
|---|---|
| `settingsDefaultsOnFirstLaunch` | fresh container yields 25/5/15/4, sound on, auto-start off |
| `settingsRoundTrip` | change, re-open container, values persist |
| `settingsSingletonRow` | `current(in:)` twice yields one row, not two |
| `genSecretsIsReproducible` | delete `Secrets.xcconfig`, regenerate, byte-identical |
| `genSecretsFailsLoudly` | missing key ⇒ non-zero exit and a message naming the key |
| `noWritesHookCatchesNewEndpoint` | fixture with an unlisted Todoist URL ⇒ hook exits non-zero |
| `noWritesHookAllowsClose` | fixture with `/tasks/{id}/close` ⇒ hook exits zero |

The last two matter more than they look. A hook that has never been shown to fail is not known to work,
and this one guards a non-negotiable.
