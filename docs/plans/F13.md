# F13 — Todoist, with Todoist's flair

**Status:** plan written, awaiting the gate. No code has been written.
**Spec:** `docs/specs/zenpom-v1.5.md`, item 4 in the ratified order, *"Lets you recognise your own
projects at a glance."*
**Baseline:** `docs/specs/SPEC.md` (v0.1) and `docs/specs/definitions.md`, both still binding.
**Build contract touched:** `docs/plans/F3-contract.md` §3.2 — and that is the whole argument of this
plan, so it is stated at the top rather than discovered at the review.

---

## Paraphrasing it back

The picker is a list of grey names. Todoist's own app is not: a project called *Dissertation* is olive
there and *Household* is berry red, and after a fortnight you stop reading those two words and start
recognising two colours. A task Todoist shows as P1 is flagged, and the flag is why you can find it in
a list of forty.

F13 puts those two facts on this app's picker rows, so that choosing what to work on is recognition
rather than reading. Nothing else changes: the same projects, the same sections, the same tasks, in
the same order Todoist put them in, chosen the same way, writing nothing anywhere.

It is a small feature with one genuinely awkward corner, and the corner is not the colour — it is
where the colour is allowed to live. This app's design system says a screen may name a *role* and
never an appearance, and a SwiftLint rule fails the build on the attempt. A Todoist project colour is
not a role. "Berry red" does not mean *the page background* or *the ink on a button*; it means
*this project, the one you chose that colour for*. Section 3 is about how to hold both of those true
at once without pretending Todoist's palette is our design system.

---

## 1. The fact this plan turns on, established before anything was decided

**The v1.5 spec's earned-entry line says the colours and flags are *"already fetched and cached, and
currently thrown away."* That is half right, and the wrong half changes the plan.**

They are **not cached**. They are not decoded either. They are discarded at the DTO boundary, one
layer earlier than the spec's sentence implies, and nothing downstream has ever seen them.

What the code actually says, read rather than assumed:

- **`ZenTomato/Todoist/TodoistDTO.swift`.** `TodoistProjectDTO` decodes exactly three fields — `id`,
  `name`, `child_order` — under a comment that ends *"**Do not add a field here.**"* `TodoistTaskDTO`
  decodes `id`, `content`, `project_id`, `section_id`, `child_order` and a `due` object read for one
  boolean. Neither type mentions `color` or `priority`. Swift's `Codable` silently ignores keys a type
  does not declare, so both values arrive in the response body and are dropped on the floor at decode.
- **`ZenTomato/Models/CachedProject.swift` / `CachedTask.swift`.** No colour column, no priority
  column. `CachedProject` holds `id`, `name`, `childOrder`, `syncedAt` and nothing else.
- **`ZenTomato/Todoist/TodoistCacheStore.swift`.** The private
  `replaceEverything(projects:sections:tasks:syncedAt:)` constructs each row from the DTO's fields. It cannot write a column that does not exist and cannot
  read a field that was never decoded.
- **`ZenTomato/Todoist/TodoistClient.swift`** attaches only `limit` and `cursor` to a GET. There is no
  field-selection parameter, so the *wire* half of the spec's sentence is right: Todoist sends the
  whole object and this app pays for the bytes already.

So the honest version of the spec's line is: **fetched over the wire, never decoded, never stored.**

**Why the distinction is the plan and not pedantry.** Had they been cached, F13 would be one task —
draw what is already in the database — with no schema change, no decoder risk, and no argument with
the build contract. Because they are discarded at the boundary, F13 must cross four layers: the
decoder, the SwiftData model, the cache writer, and the view. It needs a foundational group, it needs
a SwiftData schema change, and it needs to answer §3.2 in writing. That is the difference between a
one-task feature and a five-task one, and it was worth twenty minutes of reading to find out which
this was.

### What §3.2 says, by name

`docs/plans/F3-contract.md` §3.2, *"What is deliberately not mirrored"*, lists both fields in its
table — `priority` and `color` are there in the same sentence — under a rule that adding one *"is a
visible argument with this table rather than a small reasonable commit."* It then spells out the
reason for one of them:

> **`color`** — F1's rule is that views may only name semantic roles. A Todoist colour could never be
> drawn even if it were stored.

**That sentence is now false, and F13 is the reason.** It was true when it was written, and it was
true because nobody had built the bridge in section 3. This plan's job is to build the bridge and then
retire the sentence honestly rather than quietly.

`priority` gets no individual paragraph in §3.2; it sits in the undifferentiated list. That matters a
little: the table's blanket reason is *nothing reads it*, and F13 gives it a reader.

There is a second place the same claim is made, in shipped source rather than in a contract.
`ZenTomato/Views/TaskPickerView.swift` opens with:

> A TASK ROW CARRIES ONLY ITS TITLE — No due date, no priority, no labels, no flag, and above all no
> checkbox that writes anything. The mirror does not hold those fields, which is deliberate: **a
> column that cannot be stored cannot be drawn, and a column that cannot be drawn cannot start an
> argument about sorting by it.**

The last clause is the sharpest thing anybody has written about this feature, and it is a warning
aimed squarely at F13. Section 6 answers it: the column gets stored and drawn, and the argument about
sorting is refused explicitly rather than left to be had later.

### The precedent, and it is exact

**`D21` is this feature with one boolean instead of two fields.** On 2026-08-23 the same table gave up
`due`, in part, so that `CachedTask.isRecurring` could exist — and it took a numbered, ratified
decision to do it, not a paragraph in a plan. The delta's own text is the model for what this plan
owes: it names precisely what crossed (one derived boolean), names precisely what did not (no date, no
schedule string, no time zone, nothing from which a recurrence rule could be reconstructed), and says
in as many words *"this paragraph is the visible argument with this table that the paragraph above
demands."*

D21 also carries the warning this feature has to heed twice over: *"a boolean read from the wrong key
is silently always false."* Section 5 is that warning applied to an integer, where it is worse.

## 3. The design tension: a role is ours, a tint is Todoist's

This is the part worth arguing.

### What the rule actually is

`.swiftlint.yml` lines 143–153, `palette_outside_token_layer` (the rule key is at 143; the three lines
quoted below are 150–153):

```
included: "(ZenTomato/(App|Views|Models|Timer|Alarm|Shared|Stats|Export|Sprint|Todoist|Plan|Music)|ZenTomatoActivity|ZenTomatoWatch)/.*\\.swift"
regex:    "\\bPalette\\."
message:  "Screens may only name a ColorRole, never a raw Palette step."
severity: error
```

Two things follow that the plan depends on. **`ZenTomato/DesignSystem/` is not in that list** — the
token layer is where palette steps are allowed to be named, and the rule is drawn around everything
else. And **the rule is a name check, not a colour check**: it forbids the token `Palette.` appearing
outside the token layer. It knows nothing about hex literals, and it would not see a new primitive
table under a different name.

`ColorRole` itself is a closed enum whose `pair` property is one `switch` over every case returning
both appearances, so the compiler refuses a role that has a light value and no dark one. That is a
construction guarantee and it is worth having; section 7 is explicit that it is *not* evidence, because
a compiler guarantee cannot be shown to fail.

### Why the obvious answers lose

**Option A — give Todoist's colours their own `ColorRole` cases.** `case todoistBerryRed`, twenty-odd
of them. It would satisfy the lint rule outright, with no new machinery.

It loses on what a role *means*. `ColorRole`'s own documentation is unusually clear: *"A screen asks
for 'the page', 'the ink on an action button', 'the boundary of a control'. It never asks for 'the
sixth warm grey'."* A role is a statement about **purpose**, and its whole value is that the purpose
survives when the colour changes. `todoistBerryRed` is a statement about **appearance** with a role's
syntax — it is the sixth warm grey wearing a badge.

It also breaks the accessibility instrument, and breaks it quietly. `DesignTokenTests`'s
`everyForegroundRoleIsAudited` requires every role that can be drawn on something to appear in a
hand-written contrast pairing, and its own comment warns that the failure mode is *"papering over with
a lowered threshold."* Twenty roles whose values were chosen by the user and cannot be audited would
have to be added to the exemption set — which is that paper, applied to two-thirds of the table.

And it would be untrue in a way that matters later. The role table is the thing `F12` swaps to make a
theme. A theme that swapped berry red would be changing Todoist's data, not the app's appearance.

**Option B — let the view hold the hex.** `Color(red:green:blue:)` in `ProjectPickerView`. It loses
immediately: it is precisely what the two-layer system exists to prevent, it puts appearance decisions
in the file that draws, and the only reason the lint rule would not catch it is that the rule matches
a token name rather than a colour — so option B is not permitted-and-unenforced, it is
forbidden-and-invisible, which is worse.

**Option C — map Todoist's colours onto the nearest step of our palette.** Superficially the tidiest:
one palette, no second table, the design system stays the single source of colour.

It loses on arithmetic. Our palette has five ramps — stone, slate, sage, amber, red. Todoist's colour
set is roughly twenty hues including teal, sky, lavender, olive, salmon, taupe and grape, most of which
have no nearest step in our palette worth the name. Mapping them would collapse distinct projects onto
the same swatch, which destroys the exact affordance the feature exists for: the spec's earned entry is
*"recognise your own projects at a glance"*, and two projects the same colour is not recognition. It is
also dishonest in the direction the gate brief warned about — it asserts that Todoist's berry red *is*
our red, which is the pretence that Todoist's palette is our design system.

### Option D — the bridge, which is what this plan proposes

**Two vocabularies, two types, one rule, and the rule is unchanged in substance: a screen never
chooses an appearance.**

- **`ZenTomato/DesignSystem/Primitives/TodoistPalette.swift`** — Todoist's own colour values,
  transcribed as `RGBColor` hex literals, one per Todoist colour name, sitting beside
  `Palette.swift` and never mixing with it. It is a second *primitive* table, and its separateness is
  the point: a reader can see at a glance which colours this app chose and which it is merely
  reporting. `RGBColor` already exists for exactly this — a Foundation-only value with no UI framework
  in it, so the table stays readable from a test.
- **`ZenTomato/DesignSystem/Semantic/TodoistTint.swift`** — a closed enum over Todoist's colour names,
  constructed **only** from what Todoist sent (`init(todoistName: String?)`), with an `unknown` case
  because Todoist may add a colour tomorrow and a mirror must never fail on a value it has not seen.
  It resolves to a light/dark pair through a single `switch`, the same construction `ColorRole.pair`
  uses, so a tint cannot exist with only one appearance.
- **`ZenTomato/DesignSystem/SwiftUI/Color+TodoistTint.swift`** — one initialiser, `Color(_ tint:)`,
  mirroring the existing `Color(_ role:)`. It is the only file in the bridge that knows iOS exists,
  which is the arrangement `Color+ColorRole.swift` already documents and defends.

**Why this honours the rule rather than evading it.** The rule's purpose is that a screen may not
decide what something looks like. Under the bridge a screen still decides nothing: it names a piece of
Todoist data — *this project's tint* — and the token layer decides what that data looks like, in both
appearances, in one place, changeable in one place, readable by a test with no screen behind it. Every
property the role system was built to guarantee still holds.

**Why it is two types and not one enum.** So that "berry red" is never available where a role is
expected, and a role is never usable to mean a project. A single enum with both kinds of case in it
would make `ColorRole.todoistOlive` assignable to a page background, and would make the sentence *"the
only colour vocabulary the app is allowed to speak"* stop being true of anything in particular. Two
types keep the sentence true twice: **roles are ours and mean a purpose; tints are Todoist's and mean
a project.**

**And the hole this opens, which `F13-T1` closes in the same task.** A second primitive table is a
second thing a view could name directly, and `palette_outside_token_layer` matches the literal string
`Palette.` — so `TodoistPalette.` in a view would pass the existing rule. Building the bridge without
widening the rule would leave a guard with a hole, which the rule's own comment in `.swiftlint.yml`
already calls out as the thing worth avoiding: *"nothing violated the rule, but the guard had a hole,
and a guard with a hole is one that gets believed when it should not be."* So `F13-T1` extends the
regex to `\b(Palette|TodoistPalette)\.` and proves it by breaking it.

### What a tint is allowed to be drawn as, and what it is never allowed to be

**A tint is a fill, never an ink.** It is drawn as a small swatch beside the project name; the name
stays `textPrimary` exactly as it is today. The reason is not taste: these colours are chosen by the
user in another app, this app cannot influence them, and therefore **no contrast floor can be
guaranteed for any pairing involving one.** Todoist's charcoal on our `slate900` page in dark is a
genuinely invisible combination and there is nothing we can do about it from here.

**So every swatch carries a `borderStrong` ring, unconditionally.** `borderStrong` is the role
documented as *"the boundary that tells you something is a control"* and is measured at 3.12:1 or
better on every ground in both appearances. The ring is what makes the swatch a visible object
regardless of its fill, which is what WCAG 1.4.11 is actually asking for, and it costs one modifier.
The alternative — a per-tint contrast test that passes for eighteen colours and fails for two — would
force us either to alter somebody's project colour or to ship a known-invisible mark, and both are
worse than a ring.

**And colour is never the only signal.** The project name is still there, in full, in the same ink as
today. This is the doctrine `PickerRowView` already states — *"Selection never relies on colour
alone"* — applied to the one new mark on the row. For VoiceOver the swatch is hidden: it duplicates the
project name and offers a reader nothing to act on. **Priority is the opposite case and is treated as
the opposite case**, because a priority flag is information rather than decoration; section 5 puts it
into the spoken label as words.

## 4. The two constraints the gate named, confirmed

**No Todoist endpoint outside the allowlist, and none added.**
`scripts/todoist-allowed-endpoints.txt` holds four lines: `GET /projects`, `GET /sections`,
`GET /tasks`, `POST /tasks/{id}/close` — read off the file, not from memory.

**The next sentence is a prediction and is written as one; nothing here ratifies it.** Todoist is
*expected* to return a project's `color` on `GET /projects` and a task's `priority` on `GET /tasks`,
both of which are already on that list — in which case F13 adds **no line to the allowlist and no
`Endpoint` to `TodoistAPI.swift`**. `TodoistEndpointTests`'s
`endpointTableMirrorsTheAllowlist` reads the committed file and fails in either direction, and
`thisFeatureAddsNoWriteToTodoist` is already there; both should be green on this branch without
modification, and a diff that touches either file is the signal that something has gone wrong.

**That last claim is about somebody else's system, so it is not ratified by this paragraph.** The
conventions are explicit that a decision asserting what an external system can do is not ratifiable
until a command has run and its output is recorded. `F13-T5` runs it, against the owner's real token,
using the existing read-only instrument `scripts/check-todoist-facts.sh` — which already exists for
precisely this class of question and already carries `O12`'s three unsettled Todoist facts.
**If the fields are not on those two responses, F13 is dropped, not widened.** Adding a fifth endpoint
to reach a project colour would be trading the app's hardest structural guarantee for a decoration,
and the allowlist's own header says it in as many words: *"Do not add a line to this file to make a
build pass."*

**No local model beyond a cache of Todoist's.**
F13 adds two columns to two existing mirror tables and creates no table. Both are verbatim copies of a
field Todoist sent, written by exactly one thing — `TodoistCacheStore.replaceEverything` — read by the
picker, and destroyed and rewritten on every refresh along with every other column, which is what
`CachedProject`'s own documentation says makes the mirror a mirror: *"there is no local version of a
project that could disagree with Todoist's."* Nothing in the app ever writes a colour or a priority,
there is no local override, no per-project preference, and no default for a project that has none —
absent means absent, and draws no swatch.

**And no capture surface.** F13 adds no control of any kind. Every row it touches keeps exactly the
tap targets it has today: the toggle that puts an item in the plan and, on a project row, the way in.
No new button, no disabled button, no long-press menu, no context menu, no swipe action. The two marks
it adds are non-interactive. `NoCaptureSurfaceTests` exists and must stay green untouched;
`F13-T3` and `F13-T4` each state it as an acceptance condition rather than assuming it.

## 5. The correctness hazard, named before it is built

**Todoist's `priority` is reported to run backwards from its own user interface, and an integer read
the wrong way round is silently plausible.** *That first clause is a prediction, recorded as one:*
the reported behaviour is that the wire value is an integer where the *largest* number is the *most*
urgent while Todoist's UI labels the most urgent one **P1** — which would mean the flag the user calls
P1 is not the number 1. **`F13-T5` step 1 is what turns that into a fact, and no line of `F13-T4` is
written before it has.** The hazard below holds whichever direction the run reports, and it is the
reason the run comes first: a mapping written from memory has a fifty-fifty chance of being exactly inverted, and an
inverted mapping does not crash, does not warn, and looks entirely reasonable on screen — every task
has a flag, the flags differ, the list looks right. It would be found by the owner, on their own
account, wondering why the urgent things are unflagged.

This is D21's warning — *"a boolean read from the wrong key is silently always false"* — with the
volume up, because a boolean read wrongly is constant and therefore noticeable, while an integer read
backwards is varied and therefore convincing.

**So the mapping is not written from memory, and this plan does not state it as a fact.** It is
established before the row is written, by the two means D21 itself used and the conventions require:
against Doist's own published API v1 client library, and against a real response from the owner's
account captured in `F13-T5`. The fixture the test asserts on is **the captured response**, not a
hand-built DTO — because an assertion that re-derives its own expected value cannot see the path that
produces the real one, which is the trap this project has already been bitten by five times.

**A second hazard, in the decoder, and it is the one that would hurt a real person.**
`TodoistProjectDTO`'s "do not add a field here" comment is not superstition; it gives a reason.
Todoist's answer for projects is a **union of two shapes** — a personal project and a workspace
project — and a type that requires a field belonging to only one of them fails to decode the *whole
response*, on an account with a workspace, presenting as an **empty picker on a real phone and in
nobody's test.**

So both new fields are decoded exactly the way `due` already is: **optional, `decodeIfPresent`, with
a defined meaning for absence.** A project with no `color` key gets `TodoistTint.unknown` and draws no
swatch. A task with no `priority` key gets no flag. Absence is an ordinary project and an ordinary
task, not a failure — the same sentence `TodoistTaskDTO.due` already carries, for the same reason. The
mutation in section 7 makes either field required and watches the workspace fixture fail.

**The SwiftData change, and what I could not verify by reading.** `AppModelContainer.make` builds one
`Schema` from a flat list of model types; there is no `VersionedSchema` and no `SchemaMigrationPlan`
anywhere in the tree, so F13's two columns rely on SwiftData's automatic lightweight migration, both
declared with defaults, exactly as `CachedTask.isRecurring: Bool = false` was under D21. **The
precedent is strong and I am not treating it as proof:** I have read that D21 did this and shipped, and
I have not seen a store that predates F13 open after it. The risk is also bounded by the mirror's own
design — all three tables are deleted and rewritten in full on the next refresh, so even a column that
migrated to a default corrects itself within one foreground. The check is opening the app on the
owner's phone against their existing store, and it belongs to `F13-T5` because only the owner has that
store.

## 6. Tasks

Five. Two deliver **nothing user-visible** and are labelled so.

| Task | What it delivers | Owner |
|---|---|---|
| `F13-T1` | The tint vocabulary, and the widened lint rule that guards it | **agent** |
| `F13-T2` | The two fields cross the DTO boundary and reach the mirror | **agent** |
| `F13-T3` | Project colour on the picker | **agent** |
| `F13-T4` | Priority on a task row, in ink and in speech | **agent** |
| `F13-T5` | The live-token facts and the device check | **human** |

**The table is not the running order, and one dependency runs backwards through it.** `F13-T5`'s
**step 1** — the read-only fact check against the live token — produces the two things `F13-T2` and
`F13-T4` are written against: whether the fields are on the allowlisted responses at all, and which
direction `priority` runs. It therefore runs **before** `F13-T2`, and `F13-T4` cannot begin until its
output is recorded. Steps 2 and 3 of `F13-T5` are the device check and stay at the end. The task is
one unit because it is one sitting of the owner's, but it is entered twice.

### Foundational — nothing user-visible changes

#### `F13-T1` — The tint vocabulary · owner: **agent**

Three small files under `ZenTomato/DesignSystem/`, described in section 3: `TodoistPalette.swift`
beside `Palette.swift`, `TodoistTint.swift` beside `ColorRole.swift`, and
`Color+TodoistTint.swift` beside `Color+ColorRole.swift`. Plus one line of `.swiftlint.yml`: the
regex becomes `\b(Palette|TodoistPalette)\.` so the new table is fenced the moment it exists rather
than in a retrofit after somebody names it from a view.

It is first because it is the whole of the design argument, and a design argument can be settled
before anything is fetched or drawn. It is also the piece the owner might rule differently on, and it
is cheapest to rule on when nothing depends on it yet.

**Nothing imports it yet.** No view changes, no decoder changes, and the app on the phone is
byte-for-byte what it was. That is what makes this safe to land first.

*Checkpoint:* `make lint` **fails** with the documented message when a single throwaway line naming
`TodoistPalette.` is put into `ZenTomato/Views/ProjectPickerView.swift`, and passes when it is taken
out — run in that order, with both outputs in the PR. Every tint resolves in both appearances (the
compiler proves it; see section 7 for why that is not counted as evidence) and no two tints resolve
to the same `RGBColor`.

**One caution about that last clause, because it is an assertion about somebody else's palette.** That
no two of Todoist's published colours share a hex value is *expected*, not established — and it is
being written into a test, which is the worst place for an unchecked assumption about an external
system: if two of Todoist's names genuinely share a value, a faithful transcription fails
`everyTodoistTintIsDistinct` and the honest fix is to change the test, not the table. So the table is
transcribed from **one cited source, named in the file's header**, and if that source shows a
collision the test becomes *no two tints resolve to the same value except the pair Todoist itself
duplicates*, named and quoted. The mutation in section 7 is unaffected either way: it is a
copy-paste error introduced on top of a correct table.

#### `F13-T2` — The two fields reach the mirror · owner: **agent**

`TodoistProjectDTO` gains an optional `color`; `TodoistTaskDTO` gains an optional `priority`.
`CachedProject` and `CachedTask` gain one stored column each, both defaulted.
`TodoistCacheStore.replaceEverything` copies them across — three or four lines in a method that
already does exactly this for six other fields. §3.2 and `TaskPickerView.swift`'s header comment are

## 7. Mutations — the tests, shown to fail before they are believed

At least one per behaviour these tests protect. Each is applied to the shipped code, the suite is run,
the named test is **seen** to fail, and the count is recorded as an `M<n>` before the task is called
done. A test that has never been shown to fail is not evidence.

**`M` has nowhere to be written down today, and F13 is not the place to fix that.**
`docs/plans/00-register.md` carries `## Owner items (O)`, `## Decisions (D)` and `## Chores (C)` and
**has no Mutations section**; the file is regenerated by `scripts/extract_zenpom.py`, which merges,
so a section hand-added to it is a change to that script's contract rather than a heading. Until the
owner rules otherwise, the seven rows below are recorded **in this plan and in `docs/reviews/F13.md`**
with their counts, and the register section is a chore somebody opens — not something this feature
invents on its way past. See Open Question F.

| # | The mutation | The test that must fail |
|---|---|---|
| 1 | Make `TodoistProjectDTO.color` **required** rather than `decodeIfPresent` | `aWorkspaceProjectWithNoColourKeyStillDecodes` — the whole page must survive, not just the row (`F13-T2`) |
| 2 | Make `TodoistTaskDTO.priority` required | `aTaskWithNoPriorityKeyStillDecodes` (`F13-T2`) |
| 3 | **Invert the priority mapping** — return the top level for the wire's lowest number | `priorityIsReadInTodoistsDirection`, asserting on the **captured response** from `F13-T5`, never on a hand-built DTO (`F13-T4`) |
| 4 | Give two Todoist colour names the same `RGBColor` in `TodoistPalette` | `everyTodoistTintIsDistinct` — a copy-paste in a twenty-row hex table is the realistic defect here, and two projects the same colour is the feature failing silently (`F13-T1`) |

## 9. Scope fence

Not in F13. Each needs its own gate.

**Sorting or filtering by priority — and this is the one that will be asked for mid-build**, because
once the column exists it costs about four lines and it is genuinely useful. It is out, and the reason
is already written in the file it would change. `TaskPickerView.swift`: *"a column that cannot be drawn
cannot start an argument about sorting by it."* `CachedProject.childOrder`: the order is copied from
Todoist *"because inventing an order is exactly the local state this app is not allowed to have."*
`SPEC.md` locks that **all** projects, sections and tasks are visible in the picker. A priority sort is
this app forming an opinion about somebody else's Todoist, and a priority filter is this app hiding
part of it. F13 reports two facts and reorders nothing. If the owner wants a sort, it is a delta with
that paragraph to answer.

**Colour on the session plan row.** The next most likely ask, and it has a harder refusal than the
first. `PlanRowView` holds only what a `SessionPlanItem` stores — an id and a title snapshot — and its
header says why: *"anything else here would have to be fetched from the mirror, and would therefore
vanish the day the task did, which is the D17 fence made visible rather than merely obeyed."*
`SessionPlanStore` says the same of the item itself: *"no date, no priority, no notes."* A colour on a
plan row is a live lookup wearing a decoration.

**Todoist labels, due dates, deadlines, descriptions, durations, parent tasks.** Every one is still in
§3.2 with its reason intact, and F13's crossing is narrow on purpose: two fields, both drawn, neither
sorted on. A feature that admitted two fields is not a precedent for admitting the table.

**Themes, and any use of a project colour as the app's accent.** That is `F12`, it owes its own delta
against `SPEC.md`'s out-of-scope list, and mixing the two would import Todoist's data into the role
table — the exact confusion section 3 exists to prevent.

**Colour or priority on the timer screen, the Live Activity, the watch, the stats or the export.** The
export in particular: it is the one artefact that must stay readable across time, and `O1` — the
export read beside the Rhodia — has still never been run. Nothing in F13 may change what a past export
means.

**A setting to turn the colours off.** `SPEC.md`'s *"Timer customization: … Nothing else"* closes the
settings list, and `F8`'s Ruling D is the precedent for why a new settings row owes a `D<n>` while a
control on the thing being edited does not. There is nothing being edited here, so there is nowhere
legitimate to put it. If the swatches turn out to be noise, the answer is to remove them, not to add a
switch.

## 10. Open questions for the gate

Batched. Only the owner can settle these; I have not invented answers.

**A. Does the §3.2 crossing want a number?** Section 2 in full. The ratified v1.5 spec names both
fields and says no delta is owed; `D21` set the precedent that crossing this exact table takes a
ratified decision. **I would say no `D<n>`** — the v1.5 entry is the ratified authority D21 lacked —
**and write the §3.2 argument into this plan and the PR instead.** If you would rather the crossing be
greppable from the register, it is the Todoist-tint delta and I will write it before `F13-T2`.

**B. Priority: how many levels are drawn, and in what weight?** Todoist has four. The design system's
own discipline is that amber marks one thing per screen, and a picker where half the rows are amber has
spent that budget on somebody else's data. Three candidates: draw only the top level; draw the top two,
the higher in `danger` and the lower in `warning`; or draw all three non-default levels in one quiet
weight. **I would draw the top two**, because that is the distinction people actually act on, but this
is a judgement about your account and I would rather look at it in `F13-T5` than assert it now.

**C. Does the project colour follow the project into the task picker?** `TaskPickerView`'s heading is
the project's own name, so a swatch there is consistent and costs nothing. The argument against is that
it is the one screen where the project is not in question — you are already inside it — so the mark
carries no information. **I would put it there anyway**, for continuity, but it is a taste call and it
is yours.

**D. Is `F13-T5`'s live-token run acceptable as a third claim on
`scripts/check-todoist-facts.sh`, or would you rather it stayed a one-off?** That script exists for
this class of question and already carries `O12`'s three unsettled facts, so adding a fourth read-only
claim seems right — but it is your token and your script, it needs a live credential to run, and the
conventions are explicit that a claim about another system is not ratified until something has run.

**E. And the disagreement worth naming**, in the form the conventions ask for. **The rule** is that
views may only name a role, and it exists because appearance decisions scattered through screens cannot
be changed or measured. **The need** is that Todoist's colours are data, they are not roles, they never
will be, and a rule applied literally would either forbid the feature the spec ratified or force twenty
lies into the role table. **I would build the bridge in section 3** — it keeps every property the rule
was written to protect, widens the guard rather than weakening it, and keeps the two vocabularies
visibly separate. But it does add a second colour vocabulary to a design system that has deliberately
had exactly one, and that is a real cost that will still be there when `F12` and `F15` arrive. If you
would rather this feature ship without colour at all — priority flags only, no second table, no new
type — **say so at this gate and it is a smaller feature by half.** That refusal is cheap now and
expensive after `F13-T1`.

**F. Where does an `M<n>` row live?** The conventions put the mutation register in
`docs/plans/00-register.md`, and that file has no Mutations section — it is generated by
`scripts/extract_zenpom.py` and carries `O`, `D` and `C` only. F13 will produce seven mutation
results and needs somewhere to put them. **I have not invented an answer and have not touched that
file.** The two candidates are a `## Mutations (M)` section taught to the extractor, or the counts
living in `docs/reviews/F13.md` with the register unchanged. Either is a chore of its own; F13 records
them in this plan and in its review log meanwhile.
