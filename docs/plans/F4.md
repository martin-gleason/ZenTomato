# F4 — Apple Music

**Gate:** requires F3 merged and your yes. C2 is done — the App ID carries the MusicKit capability.
**Branch:** `F4/apple-music`
**Spec:** MusicKit authorization; library playlist/song picker; play, loop, skip; on/off toggle; pause on
breaks. *Done when:* a playlist plays through a full sprint on a device with the screen locked.

## Summary

Audio that gets out of the way. The spec is unusually prescriptive here and the prescriptions are all
subtractive: skip-forward is the *only* control during a sprint, music pauses on breaks, the toggle is
set before a sprint and not during. The design work is mostly in not building things.

One honesty item up front, because the reviewer agent asks "is any other control reachable" and the
answer is yes: **we cannot suppress the system's own transport controls.** Control Center, the Lock
Screen, AirPods, and CarPlay will all offer play/pause/back for whatever is playing, because that is
iOS's contract with the user and no app can opt out. What we control is our own UI. Documented rather
than discovered in review.

## Tasks

### F4-T1 — Authorization and subscription

- `MusicAuthorization.request()`, asked when the user first enables music, not at launch.
- `NSAppleMusicUsageDescription` in Info.plist.
- Check `MusicSubscription.current`. Playing library content through `ApplicationMusicPlayer` requires
  an active Apple Music subscription; without one, the music toggle is disabled with a plain
  explanation. The timer is entirely unaffected — music is an accessory to this app, and every failure
  mode in F4 must degrade to a silent working timer rather than a broken one.
- Denied authorization behaves the same way: toggle off, explanation, timer unaffected. Note the
  contrast with F2, where denied authorization is blocking — there, the permission *is* the feature.

### F4-T2 — Picker

`MusicLibraryRequest<Playlist>` and `MusicLibraryRequest<Song>` over the user's own library, per the
spec's "an existing playlist or song from their library."

Explicitly **not** the Apple Music catalogue, and explicitly **no playlist creation** — creating a
default focus playlist is named in the spec's out-of-scope list. The picker reads the library and
selects from it; that is its entire job.

The selection persists across launches as an identifier plus a title snapshot, for the same reason F5
snapshots task titles: a playlist can be renamed or deleted in the Music app, and a stale identifier
should produce "that playlist is gone, pick another" rather than a blank row or a crash.

### F4-T3 — Playback

- `ApplicationMusicPlayer.shared`, not `SystemMusicPlayer`. The application player is scoped to us and
  does not commandeer the user's Music app queue; the system player would mean starting a pomodoro
  wipes out whatever you had queued elsewhere.
- Queue from the chosen playlist with `repeatMode = .all`, which is the spec's "playlist loops when it
  ends." A single chosen song loops the same way.
- **Skip-forward only.** One button in our UI. No previous, no scrubber, no shuffle toggle, no queue
  view. Absent, not disabled-and-greyed — a greyed control still says "this is something we do."
- Background audio: `UIBackgroundModes: audio`, and an `AVAudioSession` configured `.playback`. This is
  the entitlement the spec asks me to verify at build time; the verification is the device check, not a
  claim in this document.

### F4-T4 — Toggle and the break behaviour

- On/off toggle on the timer screen, **enabled only when the timer is idle** — the spec says music is
  toggled before a sprint, so mid-sprint it is not interactive.
- The toggle's state persists across launches but is **not** an `AppSettings` field. `SPEC.md`'s
  customization list is closed ("Nothing else"), so this is session state owned by F4, stored in F4's
  own small state row. Called out because putting it in `AppSettings` is the obvious move and it would
  be a scope violation.
- Break behaviour, driven by the F2 engine's block transitions:

```
WORK  ─────────▶ play (resume where it left off)
SHORT BREAK ───▶ pause
WORK  ─────────▶ resume, same position in the same track
LONG BREAK ────▶ pause
sprint ends ───▶ pause
```

Resume means resume, not restart — mid-track position is preserved across the break. The engine already
publishes block transitions for the Live Activity; F4 subscribes to the same signal rather than
inventing a second notion of "the block changed."

Interruptions (a phone call, another app taking the session) are handled through
`AVAudioSession.interruptionNotification`: pause on interruption, resume on end **only if** we are in a
work block and music is enabled. Resuming into a break would be an audible bug.

## Tests

Playback itself is not unit-testable — there is no simulator for "sound came out of the phone." So the
player sits behind a `MusicPlaying` protocol and the tests cover our logic against a spy, while the
device check covers the reality. That split is stated so the PR does not look over-claimed.

| Test | Asserts |
|---|---|
| `pausesOnBreakResumesOnWork` | transition sequence ⇒ pause/play calls in the right order |
| `resumePreservesPosition` | resume does not re-queue or seek to zero |
| `sprintEndPauses` | long break ⇒ paused, and stays paused |
| `toggleOffStopsPlayback` | disabling with the timer idle ⇒ no playback next block |
| `toggleLockedDuringSprint` | toggle not interactive while running |
| `skipIsTheOnlyControl` | the view exposes exactly one transport action |
| `noSubscriptionDisablesMusicOnly` | timer still starts, runs, and completes normally |
| `deniedAuthDisablesMusicOnly` | same |
| `missingPlaylistPromptsReselect` | stale identifier ⇒ explanatory state, no crash |
| `interruptionDuringBreakDoesNotResume` | interruption ends during a break ⇒ still paused |

## Device check (gated on C4)

The spec's own: a playlist plays through a **full sprint** — four pomodoros and three short breaks into
the long break — with the screen locked. Confirm music pauses at each break and resumes mid-track,
loops when the playlist ends, and that skip works from the Lock Screen Live Activity's app. Do it with
headphones and once without.

This is a ~2 hour device test and it cannot be shortened, which is worth knowing before scheduling it.

## Evidence for the PR

`xcodebuild test`, `swiftlint --strict`, and the device result narrated block by block — what played,
what paused, where it resumed. A screen recording of one break transition is worth more than a paragraph.

## Risks

- **The full-sprint device test is long** and it is the only thing that can validate the feature. If C4
  is still outstanding, F4's gate cannot close no matter how green the tests are.
- **`ApplicationMusicPlayer` in the background** — behaviour when the app is suspended for a long
  stretch mid-break, and whether resuming after a 15-minute pause reliably works, is the thing most
  likely to disappoint. It is exactly what the spec's "verify at build time" clause is pointing at.
- **Subscription state changes mid-sprint** — lapsed subscription should silence the music and leave the
  timer running. Cheap to handle, easy to forget.
- **Scope pressure.** Once music works, adding a volume slider or a "what's playing" row will feel
  natural and both are out of scope. Skip-forward only.
