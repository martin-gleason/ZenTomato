# Handoff — solidifying the development process

**Written 2026-08-24, for a fresh agent in a chat window with no access to the repository.**
Everything needed is in this file. Where it quotes a document, the quote is verbatim.

**What is being asked of you:** not to write code. To look at how this project *develops software* —
a solo owner who does not write Swift, directing an agent that writes all of it — and make that
process harder to get wrong. The failures below are real and specific; treat them as the evidence.

---

## 1. The project, in a paragraph

**ZenTomato** — an iOS 26 Pomodoro timer, public, GPL-3.0. Todoist is the only task store (read-only
except "complete task"), Apple Music is the audio, and **the distraction log is the point**: two
buttons, internal and external, tapped during a block, and a fortnightly Markdown export read beside
a paper notebook. Swift 6, SwiftUI, SwiftData, local-only, no accounts, no analytics.

Six features (F1–F6) are shipped and merged. A seventh, a watch companion, is planned and blocked.
**A hard stop falls on 13 September 2026**; unmerged work is abandoned cleanly rather than rushed.

Two constraints shape everything:

- **Learning level 5%.** The owner reviews every pull request and does not write Swift. Every PR
  description is therefore written for someone who can read code but not this language: what changed,
  why, what to test on the device, what could break.
- **The agent never edits the contract.** `SPEC.md` is the spec; the agent proposes amendments and the
  owner ratifies them. This rule is load-bearing and is *not* up for revision.

## 2. The process as it stands

From `CLAUDE.md`:

> 1. **Gate → plan.** Before any feature: Ultrathink. Re-read `SPEC.md`, batch clarifying questions,
>    paraphrase the feature back, write `docs/plans/F<N>.md`. Wait for the owner's yes.
> 2. **Build.** ultracode unless the plan says otherwise. One feature branch `F<N>/<slug>`. Small
>    commits, conventional-commit format, feature ID in scope.
> 3. **Adversarial review — mandatory.** Fire the adversarial reviewer at the end of every feature and
>    at the start of every session. Never resume blind.
> 4. **Verify with evidence.** A feature is done when a command returns pass and the output is in the
>    PR. **Assertions are not evidence.**
> 5. **PR.** Open it, link the plan, log the review result in `docs/reviews/F<N>.md`. Rebase-and-merge
>    only.

And a principle that matters more than any of them:

> **Hooks (deterministic; prose is advisory.)**

There are five enforcement points: `swiftlint --strict`, `xcodebuild test`, a grep that fails the
build if any Todoist create/update/comment endpoint appears, a secret scan, and branch protection
requiring PR + CI + rebase-merge.

### Where authority lives — and this is the root of most of what follows

| Document | Holds |
|---|---|
| `docs/specs/SPEC.md` | the contract. Features, locked decisions, out-of-scope list. |
| `docs/plans/00-deltas.md` | every proposed and ratified **amendment** to the contract (24 of them). |
| `docs/plans/F<N>.md` | the decisions taken at each feature's gate. Written for **all seven features at F1**. |
| `docs/reviews/F<N>.md` | the adversarial review log per feature. |

**No single read gives you the truth.** That is the structural problem.

## 3. What has actually gone wrong

Not hypotheticals. Each was found in the repository, most of them within one week.

### 3.1 The contract drifted out of date and nothing noticed

Twenty-two deltas were ratified between 21 and 23 August. **None was ever applied to `SPEC.md`.** As
of today the contract still says minimum iOS 18.0 (raised to 26 by D1), still says OAuth sign-in
(replaced by a pasted token in D18), still says the Live Activity is optional (made mandatory by D3),
still lists watchOS as out of scope (moved in by D2), and its status line still reads
`DRAFT for ratification` six shipped features later.

Meanwhile step 1 of the process says **"Re-read `SPEC.md`."** An agent following the instructions
exactly gets answers that are two months stale. That is not a discipline failure — it is an
instruction pointing at a document nobody was keeping current.

### 3.2 A decision was cited by name in five production files and existed nowhere

`D14` — the rule that stopping mid-block shows one sheet rather than two — was decided in
conversation, built, and never written down. A source file opened with *"Ratified decision D14 is
that…"* against a decision that did not exist in any document.

The deltas file itself contains this sentence, about a *different* decision that suffered the same
fate a day earlier:

> **Ratified 2026-08-22 at the F6 gate. Written down 2026-08-23** — it was decided, described in
> conversation, and never recorded, which is how a decision becomes a thing nobody can check.

So the failure mode was known, named, and recurred anyway. **Knowing about a failure mode does not
prevent it.**

### 3.3 A plan was destroyed by writing to a path nobody had read

The agent ran `cat > docs/plans/F7.md` on a file it had never opened, destroying 153 lines written
months earlier — including decisions it then failed to reproduce, one of which (deduplicating watch
taps by UUID) prevents silent inflation of the very counts the app exists to produce.

The mechanism is worth understanding precisely: **the agent's file-writing tool refuses to overwrite a
file that has not been read in the session. Shell redirection has no such guard.** The protection
existed and was walked around by using a different tool for the same job.

This was the second such incident. An earlier one destroyed 350 of 377 lines of a source file via a
runaway `git checkout`.

### 3.4 Settled decisions were sent back to be re-decided

A pull request asked the owner to rule on five formatting questions. **Four had already been ratified**
in that feature's own plan, months before, complete with a worked example. The owner's review slot —
the scarcest resource in this project — was spent re-deciding decided things.

### 3.5 Tests that could not fail

Three separate cases, each found by *deliberately breaking the code and watching the suite stay
green*:

- Rewiring the export to the wrong date range: **all 407 tests passed.** The test seam handed the same
  value to both sides of the comparison, so it was a tautology in exactly the direction that mattered.
- Deleting a rule's only write path: **green.**
- Deleting its only read path: **green.**

The project's own process says *"Assertions are not evidence."* These were assertions.

### 3.6 Verifications given aloud and never recorded

The owner performed a device check and reported the results in conversation. They were acted on and
never written into the review log, though three other features had that section. The record now says
nothing happened.

### 3.7 The taxonomy had no slot for a whole class of work

`conventions.md` defined a chore as *"an operational task the human performs"* and a feature as *"a
deliverable unit of user value."* Agent-authored work that delivers no user value — documentation
corrections, tooling, process — fitted neither, so it was filed as a feature and numbered as though it
were one. **A classification scheme with a gap does not produce an error; it produces a wrong answer
that looks right.**

## 4. What has already been hardened — do not re-propose these

Three checks now run automatically. All three were proved by breaking them first.

1. **Delta integrity.** Every `D<n>` cited anywhere in the app, the tests or the docs must have an
   entry in the deltas file; every delta must state its status; the numeric sequence must have no
   holes; an index must list them all. Removing D14's entry fails this and names all ten citing files.
2. **An amendment ratchet.** The agent may not edit the contract, so the check cannot close the gap —
   it refuses to let it grow. A delta owes an amendment when the text it says the spec *currently*
   says is still in the spec; applying the amendment removes that text and the delta stops counting
   itself. Seven are outstanding. The count may shrink or hold, never grow.
   **It is a ratchet rather than an assertion of zero on purpose:** a permanently red test under
   branch protection blocks every merge, and a gate that cannot be met is a gate somebody deletes.
3. **An overwrite guard.** Any commit removing more than 60% of an existing document is refused,
   unless the message declares `Rewrites: <path> — <why>`. It caught a legitimate rewrite by the agent
   within an hour of being written, which is the intended behaviour.

A register of every outstanding item from every review now exists in one table, split by who can close
it. Before that, an item left open in one feature was invisible from the next.

## 5. What is worth your attention

These are open, and they are process questions rather than code ones.

1. **How should a decision get from conversation into the record, reliably?** Three decisions were
   made aloud and lost or nearly lost. The gap is between "the owner says yes in chat" and "it exists
   in a file". Note the constraint: the owner is on a phone much of the time, reviewing in the
   afternoon, and any ceremony that costs them more than a sentence will not survive.

2. **Step 1 says "re-read `SPEC.md`" and that is now known to be insufficient.** What should the
   pre-flight for a gate actually be, given authority is split four ways? Note that the plans were all
   written at F1, so *the answer to a gate question often already exists* — the failure is not
   thinking too little but reading too little.

3. **What is the smallest thing that makes "assertions are not evidence" enforceable?** Mutation
   testing caught three green-but-worthless tests here. Requiring every new test to be demonstrated
   failing is one answer, but it is prose again unless something checks it.

4. **The review-slot economy.** Four demands are made on the owner's attention. **Three are
   irreducible:** reviewing every PR (they do not write Swift, so every unautomated judgement routes
   through them), device verification (no test here can hear a sound leave a phone or answer a
   permission prompt — twelve open items are this), and ratifying every spec amendment (the agent may
   not edit the contract). The fourth — **arbitrating questions the agent asks** — is the only one
   that compresses, and it is the one being spent carelessly.

   **The asymmetry that causes it:** a question costs the agent a sentence and costs the owner a
   context switch, a re-read, and a decision, in a review slot pinned to a fixed afternoon window.
   Nothing in the loop makes the agent pay for asking, so nothing stops it asking too often, too
   vaguely, or about things already settled. Note the shape of the waste — the problem is not *hard*
   questions, which are exactly what should reach a human. It is **already-answered** ones, which cost
   the same to receive and yield nothing.

   Three instances from one week, all the agent's:

   - A pull request asked the owner to rule on five formatting decisions. **Four were already
     ratified** in that feature's own plan, with a worked example, before a line was built.
   - The agent offered the owner a watch-complication option that `SPEC.md` had already excluded
     (*"widgets beyond the Lock Screen Live Activity"*) and that the feature's own plan named as out
     of scope. The owner chose it. That is worse than waste: attention spent, and an answer that
     cannot be honoured as given.
   - The agent put three options for a bug fix to the owner and asked them to arbitrate. The owner
     redirected it to research the question first — and the research collapsed it entirely: the fix
     needed no schema change and none of the three framings was the right shape.

   ### Proposal, from the session that found all this — critique it rather than adopting it

   **A question earns the owner's attention only if it passes all three tests:**

   1. **It is not already answered** in `SPEC.md`, `00-deltas.md`, or the feature's own plan. This is
      the test the agent keeps failing, and it is checkable *before* asking rather than discovered
      after.
   2. **The answer changes what gets built.** Not a preference between options the agent could pick
      and note.
   3. **It cannot be resolved by investigation.** The third instance above failed this: the research
      existed, it simply had not been done.

   Anything failing those, the agent decides, states plainly, and lets the owner overturn — which is
   cheaper for a reviewer than deciding from scratch.

   **What is unresolved, and why this is still an open question rather than a rule:** all three tests
   are prose, and section 6 below says what this project thinks of prose. Test 1 is the only one that
   looks mechanisable — something could plausibly check whether a question's subject already appears
   in the ratified documents before it is asked. Tests 2 and 3 are judgement, and judgement is what
   failed. **Is there a version of this with teeth, or is the honest answer that the owner should
   simply reject already-answered questions out of hand and make the agent pay the cost of a second
   pass?**

5. **The agent works in long autonomous sessions.** Context is summarised and re-summarised; earlier
   decisions fade. Several failures above are recall failures rather than judgement failures. What
   survives a context boundary, and what must be re-read rather than remembered?

6. **Twenty days remain.** Whatever you propose has to be worth its cost against a hard stop, with one
   feature unstarted and blocked. Cheap and partial beats thorough and unfinished.

## 6. Things to know before proposing

- **The agent never edits `SPEC.md`.** Any proposal requiring it to is out.
- **No third-party dependencies without a ratified amendment.**
- **Prose is advisory; hooks are deterministic.** Every failure in section 3 happened under prose that
  already asked for the opposite. `CLAUDE.md` literally says *"Before deleting or overwriting, look at
  the target"*, and the overwrite happened anyway. **A proposal that amounts to "be more careful" has
  already been tried.**
- **`CLAUDE.md` is meant to be lean** — its own instruction is to *"prune anything the agent wouldn't
  get wrong without it."* Adding to it has a cost.
- The owner's stated aim for v1.1/v1.5 includes bi-directional Todoist sync, a local task model,
  calendar integration and gamification. None of that is in scope now, and one ratified decision
  exists specifically to stop the code being "prepared" for it.
