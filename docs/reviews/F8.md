## Blocking — the uncommitted change, and what closed it

1. **The `openShape` guard defended an unreachable harm and installed a reachable lockout.**
   `ZenTomato/Views/TimerView.swift:1036` gained `guard shapes.runningShape() == nil else { return }`,
   with a comment claiming it stopped a saved shape from rewriting a sprint in flight.

   **That harm has no trigger today.** `ShapeStore.start(_:)` has zero shipped callers —
   `ZenTomato/Views/ShapeSheetActions.swift:16` says so in its own words: *"It never calls
   `ShapeStore.start(_:)`. Nothing on this screen runs a sprint — `F8-T4` owns…"*. `F8-T4` is unbuilt,
   so `runningShape()` is always `nil` and the guard is dead code asserting a mechanism that cannot
   fire.

   **What it creates the moment `F8-T4` lands is worse than what it prevents.**
   `ZenTomato/Views/TimerView.swift:530` sets `controls = .start` whenever `!engine.isRunning`, and
   `ZenTomato/Views/TimerScreen.swift:563` renders `shapeControl` on `case .start`. So through every
   idle gap of a shaped sprint with auto-start off — most of its wall-clock life — the button is
   **visible, enabled and VoiceOver-labelled** and silently does nothing. That is the state
   `TimerScreen.swift:543-551` forbids in its own doctrine: *"ABSENT WHILE A BLOCK RUNS, RATHER THAN
   DISABLED… A greyed-out button is still in the accessibility tree."* The guard side was changed; the
   control side was not.

   **And there is no way out.** `TimerEngine.stop(reason:)` (`ZenTomato/Timer/TimerEngine.swift:349`)
   guards on `isRunning`, and `abandonShape()` is reachable only through `stop`. Reachable trigger:
   start a shaped sprint with auto-start off, finish block 1, kill the app, relaunch the next day. The
   shape is still in `UserDefaults`, `isRunning` is false, the button is inert, and the stale-shape
   discard that `docs/plans/F8.md:566-568` assigns to `F8-T4` does not exist yet.

   **Closed by reverting it.** The change belongs in `F8-T4`, alongside the stale-shape discard and an
   *absent* rather than inert control. The reverted diff is preserved as a patch for that task.

## `critical` — the 36-hour grace left the app holding two accounts of one sprint

`ShapeStore.load()` applied the owner's grace period by rewinding a stale cursor to zero **on every
read**, and nothing anywhere put `TimerState.completedInSprint` back. `TimerEngine.synchronize()`'s
idle path deliberately preserves that tally — correctly, for every other reason it runs — so two
pomodoros into a shaped sprint, left for a day and a half, the app came back with the shape at block
**0** and the cycle still saying **one pomodoro banked**.

**That is the exact state `ShapeStore.rewindRun()`'s own doc comment refuses by name** — *"a shape
held at block four against a cycle at pomodoro zero is two accounts of the same sprint, which is the
thing `SessionPlan` refuses by name"* — and it explains that a **stop** costs the position *because*
`stop(reason:)` zeroes the tally. The grace path had no such pairing. The invariant was written down
and then broken by the rule written to serve it.

**Nothing on screen looked wrong**, which is what earns the severity. The readout said twenty-two
minutes and `.work`, both correct. The damage lands three blocks later: with `pomodorosPerSprint`
overridden to the shape's four and the tally starting at one, `TimerCycle` ends the sprint at cursor
six, leaving a 22-minute pomodoro and the 17-minute long break unrun — a 120-minute budget that does
not fill its budget, which is the one thing this feature exists to prevent, arriving by a third door
that no mutation covered.

**Verified independently before acting on it**, and the first probe was wrong in an instructive way:
it let `positionedAt` be stamped by the real clock while comparing against a `TestClock` instant —
mixed clocks — and reported no defect. Pinned to one clock:

```
PROBE cursorBefore=2 tallyBefore=1 cursorAfter=0 tallyAfter=1
```

## `major` — `advance()` incremented off the filtered copy

`advance()` reads through `load()`, so it saw the *rewound* value and incremented from there. An
overdue block that had been the shape's block two was charged against block zero:

```
PROBE advanceGives=false cursorNow=1
```

**And the suite pinned it as correct.** `ShapeStoreTests.advancingARewoundStaleShapeMakesThePositionFreshAgain`
asserted `cursor == 1` with the comment *"and it stays where the advance put it"*. One was the number
the code produced, not the number the rule wants; the assertion was written from the output rather
than from the claim. Its stated purpose — proving the grace runs from the last move and not the
fitting — is served by the new **timestamp**, not by the cursor. Renamed and rewritten.

## The fix

**The grace is now a decision made once, not a filter applied on every read.**

- `load()` is a pure read.
- `ShapeStore.rewindRunIfStale() -> Bool` performs the rewind, **writes** it, and reports whether it
  did. Its doc comment says in as many words that a caller ignoring the answer reintroduces the
  defect.
- `TimerEngine.synchronize()` is the one caller, because it is the one place both records are in hand,
  and it pairs the rewind with `goIdle(kind: .work, completedInSprint: 0)` exactly as `stop(reason:)`
  does. Only while idle: a running block's frozen columns are authoritative, and the reconciliation
  path advances the shape through `end()`, which re-stamps the position and so needs no check.
- It is in `synchronize()` and not `init` on this engine's own stated division of labour: the
  initialiser *"adopts whatever the database already says"* and `synchronize()` *"works out whether it
  is still true"*, at launch and on every return to the foreground — every moment a 36-hour gap can
  have opened in.
