## What was built, and the one fact that shaped it

**The v1.5 spec says the colours and flags are *"already fetched and cached, and currently thrown
away."* That is half right, and the wrong half was worth twenty minutes of reading.** They are fetched
and they are thrown away — at the DTO boundary, one layer earlier than the sentence implies. They were
never decoded and never stored, which is the difference between a one-task feature and a five-task
one. `docs/plans/F13.md` §1 has the evidence, file by file.

### `F13-T1` — the tint vocabulary

Three files under `DesignSystem/` and one line of `.swiftlint.yml`. **Nothing imported them**, so the
app on the phone was byte-for-byte unchanged and the design argument could be settled before anything
was fetched or drawn.

**The table is transcribed from one cited source, named in the file header** — `src/utils/colors.ts`
in Doist's own TypeScript SDK at commit `19798a37`, read 2026-09-24. The plan warned that *"no two of
Todoist's published colours share a hex value"* was **expected, not established**, and that writing an
unchecked assumption about an external system into a test is the worst place for one. It was checked
against the source before the test was written: twenty colours, no two sharing a value. Had two
collided, `everyTodoistTintIsDistinct` would have been the wrong artefact and the table the right one.

**Light and dark are the same value for every tint, deliberately.** These colours are chosen by the
user in another app; lightening one for dark mode would be this app editing somebody else's project
colour so that our page looks better. Visibility is bought by the unconditional `borderStrong` ring
instead — measured at 3.12:1 or better on every ground in both appearances — which is what WCAG 1.4.11
is actually asking for.

**The lint rule was widened in the commit that created the second table.** The old regex matched the
literal `Palette.`, so `TodoistPalette.` in a view would have passed it — a guard with a hole, which
that rule's own comment already names as the thing worth avoiding.

### `F13-T2` — the two fields reach the mirror

`TodoistProjectDTO` gained an optional `color`; `TodoistTaskDTO` an optional `priority`.
`CachedProject.colorName` and `CachedTask.priority` are the two new columns, both optional with
defaults, following `CachedTask.isRecurring`'s precedent exactly so an existing store migrates
lightweight. `TodoistCacheStore.replaceEverything` copies both across.

**`colorName` and not `color`, because it is not a colour** — it holds the key from Todoist's palette,
and a column called `color` holding the seven characters `berry_red` is the kind of name that sends
the next reader looking for a hex.

**Neither field is interpreted, and that is what keeps `T2` free of predictions.** The colour stays
the name Todoist sent; the priority stays the number on the wire. Which end of Todoist's range is
urgent is not settled by reading, `F13-T5` step 1 settles it against a real account, and `F13-T4` maps
it for the screen. A column holding an already-interpreted level would have to be rewritten if that
reading turned out backwards. The wire value never needs rewriting.

**Both contract corrections are in `T2`'s own commit, not a later tidy-up.** `F3-contract.md` §3.2
struck both fields, recorded the authority (`zenpom-v1.5.md` lists `F13` as owing no delta — the
ratified authority `D21` had to be written to supply), and kept the old `color` reasoning on the page
with an explanation of why it no longer holds rather than deleting it. `TaskPickerView`'s header said
*"no priority"* and gave a two-part reason; the first half stopped being true, so the second half —
**nothing sorts by priority** — is now stated on its own as the live guarantee.

### `F13-T3` — the swatch

A rounded 12pt square, filled with the project's tint and **unconditionally ringed in
`borderStrong`**, sitting between the plan toggle and the title. Three placements: the root project
list, a project row in search results, and `TaskPickerView`'s heading.

**The ring is not decoration and it removes an argument rather than adding one.** No contrast floor
can be guaranteed for any pairing involving a colour somebody chose in another app — Todoist's
charcoal on our dark page is genuinely invisible and cannot be fixed from here. `borderStrong` is
measured at 3.12:1 or better on every ground in both appearances, so the ring makes the swatch a
visible object whatever its fill, which is what WCAG 1.4.11 actually asks for. The alternative was a
per-tint contrast test that passes for eighteen colours and fails for two, forcing us either to alter
somebody's project colour or to ship a known-invisible mark.

**The view does not do the lookup.** `PickerScreenModel.Project.tint` is a `TodoistTint`, converted
once where the model is built, so no screen ever calls `TodoistTint(todoistName:)` itself — a screen
doing that would be a screen deciding what a piece of data looks like. `TaskPickerView` knows an id
and a name because that is what its route carries, so the lookup is `PickerScreenModel.tint(ofProject:)`,
a plain function read by a test with no screen behind it. Adding a third payload to the route would
have put presentation into navigation.

**`nil` and `.unknown` mean different things, deliberately.** A project whose colour Todoist never
sent is `.unknown` and draws Todoist's own default. An id the mirror does not hold — a project deleted
while its task list was open — is `nil` and draws nothing, because a swatch there would claim the
project still exists.

**The heading keeps `navigationTitle` as well as the principal toolbar item.** The modifier supplies
the screen's semantic title, which is what VoiceOver's screen announcement and a back button read;
dropping it to draw a swatch would have traded an accessibility fact for a decoration. This placement
is `T3`'s one taste call and the plan argued it both ways — the project is not in question on a screen
you are already inside — and it is one modifier to remove.

`PlanBuilderView` is at exactly the 400-line cap, which is why the tint arrives through the model
rather than through a new parameter, and why an explanatory comment there was cut in favour of the doc
comment on the property.

## A defect found in the instrument, not in the feature

`F13-T5` step 1 needs a fourth claim on `scripts/check-todoist-facts.sh` (gate answer `D`). Writing it
turned up something worse than the thing it was for.

**`CLAIM 2`'s phase-2 verdict block had never compiled.** It used a backslash-escaped quote inside an
f-string expression, which no Python accepts at any version — PEP 701 permits quote *reuse* inside
f-strings, never a backslash escape. And the helper was
`json() { python3 -c "$1" 2>/dev/null; }`, so the `SyntaxError` went to a discarded stream: running
`--phase2` printed its heading and then nothing at all.

**An instrument that reports *no evidence* in exactly the way it reports *no finding* is the worst
failure mode there is.** This script exists to settle questions that cannot be settled by reading, and
`O12`'s tombstone claim — does incremental sync report a removed project as a tombstone, or by
silence? — could never have been settled by it.

Fixed three ways, because one would have been the same bet again:

1. The block is rewritten without backslash escapes, and so is the new `CLAIM 4` block.
2. `json()` no longer discards stderr.
3. **`scripts/check_embedded_python.py`** compiles every Python program embedded in every
   `scripts/*.sh` — eleven of them — and is in `make checks`, in CI, and proven by `F13-M10`, which
   puts the original defect back and watches the check go red.

## What the owner's run settled, and what it found

The owner ran `scripts/check-todoist-facts.sh` on 2026-09-24. **`CLAIM 4` — the one written for
`F13-T5` — failed on their machine**, and two of `O12`'s three long-open facts were settled on the way.

### `CLAIM 4` shipped broken, and the check I had just written could not see it

```
CLAIM 4 — are colour and priority on the responses, and which way does priority run?
sed: 1: "\$d
": unterminated regular expression
...
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

Two of the seven `printf | sed '$d'` splits shipped as `sed '\$d'` — a stray backslash that survived
into the file. `sed` rejected it, the body came back **empty**, and Python was handed nothing.

**`scripts/check_embedded_python.py` reported OK throughout, because the embedded Python was never the
problem.** I had written that check an hour earlier, for this exact script, and it validated the
program and not the shell feeding it. That is `D46`'s second-artefact rule one layer down: the thing a
human is told to run was still not run by anything.

Three fixes, because the typo alone would have been the same bet again:

1. **The split is one definition.** `body()` and `code()`, used at all seven sites, so there is one
   place to get wrong instead of seven. `factsScriptSplitsBodyFromStatus` drives the real functions out
   of the shipped file against a fixture and asserts both halves — including that the body is still
   parseable, because an empty string is a perfectly good string and a useless one.
2. **`CLAIM 4` is run, not merely compiled.** `scripts/tests/probe_facts_claim4.py` lifts the claim's
   own code out of the script, stubs `api_get` with a fixture, and runs it with no token.
   `factsClaim4ReportsFromAFixture` asserts the colour half, the priority half, and the absence of a
   traceback.
3. **`json()` no longer discards stderr** — which is the only reason the owner saw a traceback instead
   of silence.

`F13-M11` and `F13-M12` put the stray backslash back; both tests go red. **And the first version of
`F13-M11`'s test killed the runner instead of failing** — under `set -e` a failing command substitution
in an assignment aborts the shell. That is the third instance of that pattern in one day, after
`gen_or_fail` and `expect_validator_catches`.

### Two of `O12`'s three facts are settled

- **An archived project DOES resolve by id.** 19 archived projects; `GET /projects/{id}` returned
  HTTP 200 with `is_archived=True`. **So the mirror must read both `/projects` and
  `/projects/archived` or it loses the name — and `/projects/archived` is not on the allowlist.**
  Adding it is a decision, not a tidy-up, and it is not `F13`'s.
- **No all-numeric task id is in active use.** 50 active tasks, 50 alphanumeric, 0 numeric. That does
  not prove old ids are dead, only that none is live, and the row says so.
- **Tombstones are still open.** Phase 1 took a token; phase 2 needs the create–token–delete sequence.
  And it could not have been settled before today regardless, because that verdict block had never
  compiled.

### The backfill diff caught me while I recorded it

Writing those results onto `O12` grew the row from 250 characters to 1100, and
`make check-open-backfill` reported it **GONE**. It was not — every original word was still there.

The first report was a true catch: my rewrite had dropped `O12`'s original sentence naming the three
facts, and I restored it. **The second was the check's own defect**: it paired rows by
`SequenceMatcher.ratio()`, which is a *similarity* and therefore falls when a row grows. Appending to a
row cannot mean the row is missing. It pairs on **coverage** now — what fraction of the old row's words
still align — which appending cannot lower and deleting does. All five triggers still fail, including a
new one: deleting the grown row outright.
