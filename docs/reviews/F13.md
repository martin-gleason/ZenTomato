## What was built, and the one fact that shaped it

**The v1.5 spec says the colours and flags are *"already fetched and cached, and currently thrown
away."* That is half right, and the wrong half was worth twenty minutes of reading.** They are fetched
and they are thrown away — at the DTO boundary, one layer earlier than the sentence implies. They were
never decoded and never stored, which is the difference between a one-task feature and a five-task
one. `docs/plans/F13.md` §1 has the evidence, file by file.

### `F13-T1` — the tint vocabulary

Three files under `DesignSystem/` and one line of `.swiftlint.yml`. **Nothing imported them**, so the
app on the phone was byte-for-byte unchanged and the design argument could be settled before anything
was fetched or drawn.

**The table is transcribed from one cited source, named in the file header** — `src/utils/colors.ts`
in Doist's own TypeScript SDK at commit `19798a37`, read 2026-09-24. The plan warned that *"no two of
Todoist's published colours share a hex value"* was **expected, not established**, and that writing an
unchecked assumption about an external system into a test is the worst place for one. It was checked
against the source before the test was written: twenty colours, no two sharing a value. Had two
collided, `everyTodoistTintIsDistinct` would have been the wrong artefact and the table the right one.

**Light and dark are the same value for every tint, deliberately.** These colours are chosen by the
user in another app; lightening one for dark mode would be this app editing somebody else's project
colour so that our page looks better. Visibility is bought by the unconditional `borderStrong` ring
instead — measured at 3.12:1 or better on every ground in both appearances — which is what WCAG 1.4.11
is actually asking for.

**The lint rule was widened in the commit that created the second table.** The old regex matched the
literal `Palette.`, so `TodoistPalette.` in a view would have passed it — a guard with a hole, which
that rule's own comment already names as the thing worth avoiding.

### `F13-T2` — the two fields reach the mirror

`TodoistProjectDTO` gained an optional `color`; `TodoistTaskDTO` an optional `priority`.
`CachedProject.colorName` and `CachedTask.priority` are the two new columns, both optional with
defaults, following `CachedTask.isRecurring`'s precedent exactly so an existing store migrates
lightweight. `TodoistCacheStore.replaceEverything` copies both across.

**`colorName` and not `color`, because it is not a colour** — it holds the key from Todoist's palette,
and a column called `color` holding the seven characters `berry_red` is the kind of name that sends
the next reader looking for a hex.

**Neither field is interpreted, and that is what keeps `T2` free of predictions.** The colour stays
the name Todoist sent; the priority stays the number on the wire. Which end of Todoist's range is
urgent is not settled by reading, `F13-T5` step 1 settles it against a real account, and `F13-T4` maps
it for the screen. A column holding an already-interpreted level would have to be rewritten if that
reading turned out backwards. The wire value never needs rewriting.

**Both contract corrections are in `T2`'s own commit, not a later tidy-up.** `F3-contract.md` §3.2
struck both fields, recorded the authority (`zenpom-v1.5.md` lists `F13` as owing no delta — the
ratified authority `D21` had to be written to supply), and kept the old `color` reasoning on the page
with an explanation of why it no longer holds rather than deleting it. `TaskPickerView`'s header said
*"no priority"* and gave a two-part reason; the first half stopped being true, so the second half —
**nothing sorts by priority** — is now stated on its own as the live guarantee.

## Tests added

| Suite | Test | What it protects |
|---|---|---|
| `TodoistTintTests` | `theTableIsTheSizeOfTodoistsPalette` | Todoist adding a colour is noticed, not guessed at |
| | `everyTodoistTintIsDistinct` | a copy-paste in a twenty-row hex table, in both appearances |
| | `everyTintRoundTripsThroughItsTodoistName` | the seam between Todoist's spelling and ours |
| | `theNamesAreTheSpellingTodoistUses` | `berry_red`, and a single word gaining no underscore |
| | `anUnrecognisedColourFallsBackRatherThanFailing` | a colour from the future is drawn, not dropped |
| | `camelCaseIsNotATodoistName` | the direction that would otherwise pass by accident |
| | `aTintIsNotReinterpretedForDarkMode` | the light/dark decision is a record, not an omission |
| `TodoistFlairCacheTests` | `aProjectColourReachesTheMirroredRow` | the field is copied, not merely decoded |
| | `aWorkspaceProjectWithNoColourKeyStillDecodes` | **the whole page**, not the row |
| | `aTaskPriorityReachesTheMirroredRow` | the wire value arrives verbatim |
| | `aTaskWithNoPriorityKeyStillDecodes` | **the whole page**, not the row |

**`TodoistFlairCacheTests` is a file of its own and not by preference.** These tests belong beside
`TodoistCacheTests`, where the same boundary is tested for every other field, and they were written
there first. The 400-line cap in `.swiftlint.yml` is what moved them.

**Every absent-field test asserts on the page, and that is the whole design of those two fixtures.** A
required field does not fail one row: the decoder fails the element, `TodoistPage` fails with it, and
the refresh returns nothing at all — an empty picker on somebody's phone and a green suite everywhere
else. So each fixture puts a populated row *after* an empty one, which is a case a row-shaped
assertion cannot tell apart from a correct one.

## Mutations

Recorded as `F13-M1`–`F13-M8` in `docs/plans/00-register.md`. **Open Question F is closed and not by
this feature**: the plan said `M` had nowhere to live and that the register had no Mutations section.
`D38` opened one, `C33` backfilled it with 119 rows, and `scripts/extract_zenpom.py` — the script the
question was about — no longer exists. The chore that paragraph said somebody should open was opened
and closed while `F13` waited.

| ID | mutation | result |
|---|---|---|
| `F13-M1` | `TodoistProjectDTO.color` required | caught — 3 issues, all `.malformedResponse`: **the page**, not the row. The row-shaped test stayed green |
| `F13-M2` | `TodoistTaskDTO.priority` required | caught — 1 issue on the page. Most tasks carry no `priority`, so this is the one that empties a real picker |
| `F13-M4` | two colour names share a hex | caught — 4 issues, the clash named in both appearances |
| `F13-M5` | `TodoistPalette.` in a view | caught — `make lint` exit 2 with the widened message, then exit 0 |
| `F13-M7` | the writer drops the colour | caught — 4 issues, including that two projects resolve to **different** colours |
| `F13-M8` | the lookup built from `rawValue` | caught — 6 issues, one per multi-word colour |

`F13-M3` and `F13-M6` belong to `F13-T4` and are not yet run.

**`F13-M1` produced the run's most useful result, and it was not the one it was written for.** It was
expected to fail one test. It failed three, across two fixtures — and `aProjectColourReachesTheMirroredRow`,
whose projects all carry a colour, **passed throughout**. That is the row-versus-page distinction
demonstrated rather than argued: a suite made only of rows that happen to set the field would have
called a required `color` correct.

`F13-M8` is not in the plan's table and needed to be. The plan covers the hex values and the lint rule
but not the name lookup, and that seam is where a real response goes wrong: every multi-word colour
arrives as `unknown` while every single-word colour keeps working, so the feature half-fails on an
account and passes on a fixture.
