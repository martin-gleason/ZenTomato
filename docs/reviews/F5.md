## Blocking findings, and what closed them

1. **Two of F3's columns shipped in F5 with no ratified authority.** `Distraction` carried
   `taskTitle: String?` and `projectTitle: String?`. The committed record says the opposite in two
   places: `docs/plans/F5.md:33` writes `// F3 adds taskTitle / projectTitle snapshots`, and
   `docs/plans/F2-contract.md:565` fences a field of exactly this shape by name — "A field named
   `taskTitle` that is always `nil` is F3 starting early, and it is worse than absent because it
   looks finished." The only document authorising them was `docs/plans/F5-contract.md`, which is
   **untracked**, appealing to a brief that is not in the tree. `docs/plans/00-deltas.md` ends at D13.

   Closed by **deleting both stored properties and both initialiser parameters**, and deleting
   `titleSnapshotsAreNilForEverythingF5Captures`. CLAUDE.md's non-negotiable prescribes the mechanism
   for the other route and the remediation pass cannot ratify a delta on the owner's behalf:
   *"Do not build it, stub it, or 'prepare for it.' If it seems necessary, write `Proposed spec
   delta:` in the plan summary and stop."* The proposal is in the PR description as **D15** for the
   owner to accept or refuse. There is no durability cost to waiting: a SwiftData optional column
   added later needs no migration, which the store dump below demonstrates — the table now has no
   `ZTASKTITLE` and adding one is a schema change SwiftData performs on its own.

2. **The disabled "Stop the timer" button was drawn identically to the live one.**
   `SecondaryButtonStyle.Content` never read `@Environment(\.isEnabled)`. It painted one ink, one
   1pt outline and one pressed fill unconditionally, while `StartButtonStyle.Content` two screens up
   reads it at line 92 and its own doc says why it must: *"A custom style receives no automatic
   dimming, so the treatment below is the whole treatment."* This is the only `.disabled(...)` on a
   `SecondaryButtonStyle` in the tree and no preview showed it, which is why nobody looked.

   The consequence is specific to this feature. The design spec's fifth signal for telling the
   required field from the optional ones is *"'Stop the timer' is visibly switched off until a reason
   exists"*, and `StopReasonSheet` repeats that claim in its own shipped doc comment. It was false.
   Combined with the ratified prohibition — nothing appears, moves or changes colour if the
   switched-off button is tapped — a person with no reason written tapped an ordinary-looking
   control and got nothing at all. D14 makes it worse than F2 did, because the "Required" marker is
   now separated from the button by up to six new fields.

   Closed by giving `SecondaryButtonStyle.Content` the `isEnabled` branch its sibling already has:
   `textSubtle` ink over a resting `surfaceInset` fill, the pairing `ColorRole.swift:98-101`
   documents as legal precisely and only inside a disabled control. No new role, no new token. A
   `.disabled(true)` quiet-button row was added to `ButtonStylePreviewRows` so the branch is looked
   at, and the two zero-tap previews now differ in the footer, which is the point of having both.

3. **The store-level proof of the two facts only the store can prove had never been run, and the
   query published for it does not execute.** `docs/plans/F5-contract.md:624` selects `ZKIND FROM
   ZDISTRACTION`. `DistractionKind` is a `Codable` enum with no `String` raw value, so SwiftData
   splits it into two marker columns and that column does not exist.

   Closed **at the store level** — see *Evidence* — and **not** at the device level. The corrected
   query is recorded below and in the PR. `DistractionKind` must not gain a raw value to make the
   published query work: that file is fenced and owner-written.

4. **No device check, no review log.** `docs/reviews/F5.md` did not exist. **The device check itself
   is still not closed** — see *Still open*. This is the same finding that blocked F2, where it also
   remains open.

## Non-blocking findings acted on

- **A refused tap poisoned the rest of the block, and lied while doing it.** `recordDistraction` set
  `lastFailure = .persistenceFailed` — "This block couldn't be saved and may be lost if you close the
  app" — and nothing clears `lastFailure` until the next boundary. So tapping again, which is exactly
  what the screen's own amber line instructs, replaced the correct message with a block-loss warning
  at the instant of the tap that *worked*, and left it up. `TimerScreen` announces every change of
  that line, so a VoiceOver reader heard the warning on top of the "Internal, 2" receipt. The engine
  no longer records a failure for a refused tap at all: the screen owns that wording, and `false` is
  the whole message. New test `aRefusedTapLeavesNoWarningAboutTheBlock`.
- **`attachNotes` inherited the same wrong sentence, and read the whole log to do it.** It fetched
  `FetchDescriptor<Distraction>()` with no predicate — the app's entire distraction table, on the
  main actor, every time either sheet closes, which by D4 is the instant a break has started behind
  it. That table is the one thing in this app designed to grow for its whole life. It is now bounded
  by date exactly as `rehydrateDistractions` twenty lines below already was, with the identifier
  match still done in Swift, and it returns `Bool` so the screen can word its own failure
  ("Those sentences weren't saved. The taps themselves are safe.") instead of borrowing one about the
  block.
- **A backward clock jump silently hid every tap that followed it.** `correctForClockSkew` rewrote
  `state.endsAt` and never touched `state.startedAt`, so after a timezone change or an NTP correction
  the block claimed to have started after it would finish — and `rehydrateDistractions` bounds its
  query at `startedAt`, so every later tap fell below the bound and vanished from the count and from
  the end-of-block sheet. The rows stayed on disk; the receipt lied, which the design spec argues is
  worse than absent. `startedAt` now moves by the same delta as `endsAt`, which also stops a finished
  block being written with `startedAt` after `endedAt`. New test
  `aBackwardClockJumpDoesNotHideTheTapsThatFollowIt`, **verified to fail without the fix**.
- **A stop confirmed inside the transition still produced a reflection sheet.** On the auto-start
  path `publishReflection` runs after `await begin(...)`, and `begin` genuinely suspends. `stop()` is
  reached from its own task, so it could complete in that window — clearing `pendingReflection`,
  going idle — and then `end()` resumed and assigned the offer anyway, putting a sheet over an idle
  screen at the moment somebody confirmed they wanted to quit. The engine now freezes an
  `abandonGeneration` counter alongside the ended block's other facts and refuses to publish if it
  has moved. New test `stoppingInsideTheTransitionStillDoesNotPresentTheSheet`, with a control half,
  **verified to fail without the fix**.
- **The settings sheet silently swallowed the end-of-block prompt.** The guard excluded the stop
  sheet and not `showingSettings`. SwiftUI will not present a second sheet from the same view while
  one is up, so a work block with taps ending while settings was open consumed the offer, cleared it
  and drew nothing — no error, no amber row, just a prompt that did not happen. The clause is now in
  the guard, so the offer stays on the engine exactly as the stop-sheet case already behaves.
- **A test claimed to cover a branch it cannot reach.**
  `aRefusedTapLeavesNothingBehindToBeSavedLater` described the `catch` that deletes a half-made row,
  but the refusal it produces is the *guard* firing while idle, which returns before a `Distraction`
  is ever built. Renamed `aTapRefusedByTheGuardInsertsNothing`, doc rewritten to describe the guard,
  and the genuinely uncovered branch is now stated in the test's own comment, here, and in the PR.
- **Every tap row was spoken twice.** The caption `Text("Internal · 14:32")` was its own accessibility
  element beside a field whose label repeats it word for word — twelve elements to swipe through
  instead of six at AX5, on the list a person has to traverse to reach the stop sheet's buttons. The
  caption is now `.accessibilityHidden(true)`; it stays drawn.
- **The requirement level was spoken only in hints, which can be switched off.** The reason field's
  label is now "Reason for stopping, required" and the tap fields' labels end "Optional", with the
  consequence left in the hint. `DistractionButtons.swift:206` already argued this principle and it
  had not been carried across.
- **The haptic was never prepared.** `CaptureHaptic` kept one long-lived generator and its comment
  claimed that was what made the buzz land while the finger was down. It is not — `prepare()` is, and
  it was absent, so with taps minutes apart essentially every first tap of a block paid the wake
  cost. Warmed when the buttons appear and again after each tap; the comment now says what the code
  does and admits what the old one got wrong.
- **`BlockReflection.kind` had no reader and its comment named one.** Deleted, along with its
  parameter on both initialisers. It was also the only thing coupling this type to `BlockKind`, which
  is compiled into the Live Activity's bundle.
- **Three doc comments claimed the zero-tap stop sheet was byte-identical to F2's.** It is not: the
  reason field's outline went 1pt → 2pt, it gained an uppercase "Required" marker and a spoken
  requirement level, and the buttons moved out of the scrolling content. All four are correct under
  D14; the claim of identity was the sentence that would stop the next reader checking. Reworded to
  say what is true. Same class of finding F2's review closed three times.
- **The D14 mock preview showed two internal taps.** Now one internal and one external, which is the
  case the row label has to distinguish.

## Findings rejected, or whose proposed fix was rejected

- **"Drop `.disabled(isWritten == false)` from 'Stop the timer' and scroll the person back to the
  required field on a failed confirm."** Rejected, because it contradicts the blocking finding above
  and cannot coexist with it: a disabled button never delivers the tap that would trigger the scroll.
  Between the two, the blocking one is right — the design spec ratifies the switched-off confirm as
  one of its five signals, and the real defect was that the state was invisible, not that it existed.
  With the fix the button now visibly changes at AX5 too, which is the signal the finding said was
  missing. The underlying observation stands and is recorded: at AX5 with six rows, the *explanation*
  is scrolled off the top even though the signal is not.
- **"Fix the Skip residue in `TimerControls.swift`."** The residue is real — `Button("Skip") { }` in
  preview scaffolding, plus five doc comments describing Skip as shipping, after D13 removed it — but
  two lenses independently said not to fix it inside F5, and they are right. It is F2's file, F2 is
  still in review, and a comment-and-preview edit here would collide on rebase. F5 touches that file
  for one reason only (the disabled branch above). Named in the PR description with file and line,
  and proposed as an `F2b` retrofit.
- **"D4's break must start even with auto-start off."** No code change. With auto-start off, a
  finished focus block goes idle and no break clock runs; `promptWithAutoStartOffLeavesTheTimerIdle`
  locks that in, and the sheet honestly drops its "Your break is already running" line rather than
  lying. The transition rule is F2's and outside F5's fence. If the owner reads D4 as requiring the
  break regardless of the setting, that is a delta and an F2 retrofit, not an F5 edit. Stated in the
  PR so a reviewer reading D4 is not left guessing whether it is a bug.
- **"Add `: String` to `DistractionKind` so the published query runs."** Rejected outright. That file
  is fenced and owner-written, and it is unnecessary — the corrected query below reads the two marker
  columns SwiftData already creates.
- **"Commit the feature in task-scoped commits."** The finding is correct and the branch genuinely
  cannot merge without it, but the remediation brief forbids committing, branching or pushing.
  Recorded in *Still open* with the commit sequence.

### The store-level check — the feature's *Done when*, read off disk

F5 ships no way to read the log back; that is F6's, and it is deliberate. So the only place the
spec's *"three records with the right timestamps"* and the plan's `skippingLeavesNilNotNotEmpty` can
be checked outside the test process is the SQLite file itself. Full output in
`build/f5-evidence/r2/store-check.txt`.

**The published query fails, exactly as predicted:**

```
$ sqlite3 default.store "SELECT ZKIND FROM ZDISTRACTION;"
Error: in prepare, no such column: ZKIND
```

**The real schema** — dumped from the running app's own container, and identical in the store the
engine wrote for this check:

```
CREATE TABLE ZDISTRACTION ( Z_PK INTEGER PRIMARY KEY, Z_ENT INTEGER, Z_OPT INTEGER,
  ZTIMESTAMP TIMESTAMP, ZINTERNALINTERRUPTION VARCHAR, ZEXTERNALINTERRUPTION VARCHAR,
  ZNOTE VARCHAR, ZID BLOB, ZSESSIONID BLOB );
```

**The corrected query, and its output.** One pomodoro, three taps at 4, 10 and 13 minutes in, one
sentence written and two fields skipped — one omitted entirely, one left as whitespace:

```
$ sqlite3 -header -column default.store \
    "SELECT datetime(ZTIMESTAMP + 978307200, 'unixepoch') AS tapped_at_utc,
            ZINTERNALINTERRUPTION AS internal, ZEXTERNALINTERRUPTION AS external,
            typeof(ZNOTE) AS note_type, ZNOTE AS note
       FROM ZDISTRACTION ORDER BY ZTIMESTAMP;"

tapped_at_utc        internal              external              note_type  note
-------------------  --------------------  --------------------  ---------  ----------------------------------------
2026-08-17 20:57:20  internalInterruption                        null
2026-08-17 21:03:20                        externalInterruption  text       Colleague came over about the release notes.
2026-08-17 21:06:20  internalInterruption                        null

$ sqlite3 default.store "SELECT typeof(ZNOTE) || ' | ' || quote(ZNOTE) FROM ZDISTRACTION ORDER BY ZTIMESTAMP;"
null | NULL
text | 'Colleague came over about the release notes.'
null | NULL
```

`typeof` and `quote` are in the query for one reason: an empty string prints as nothing in a column
listing and would be indistinguishable from a NULL. It is not. **A skipped sentence is a genuine SQL
NULL, and the whitespace-only field became NULL too** — which is the contract the whole feature is
said to rest on, checked outside the process that wrote it.

Three rows, one distinct `ZSESSIONID`, and each of those sessions matches a row in
`ZPOMODOROSESSION` — so the taps and the finished-block row agree about which pomodoro this was,
with no database relationship maintaining it. `SELECT ZTASKTITLE` errors with `no such column`,
confirming blocking finding 1 is closed in the schema and not only in the source.

**How this store was produced, and what it is not.** The rows were written by the shipping
`TimerEngine.recordDistraction(_:)` and `attachNotes(_:notEarlierThan:)` against a real on-disk
`AppModelContainer`, driven from a temporary test that was deleted afterwards; the schema was
cross-checked against the store the installed app creates for itself on the simulator. It is real
SQL over real rows written by the real code. **It is not a person tapping a phone**, and the
distinction matters for everything below.
