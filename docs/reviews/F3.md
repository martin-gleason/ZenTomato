## Blocking findings, and what closed them

1. **A rate-limited Complete sent the close command twice.** `TodoistClient.perform` retried any 429
   once. That is right for a read — the answer is the same list either way — and it applied to the
   one address that writes. One tap on Complete could therefore produce two
   `POST /tasks/{id}/close` against somebody's real account, automatically and unwatched, which is
   the thing the ratified design forbids in its own words: *"No automatic retry, no backoff timer on
   this control, and above all no queue."*

   It is not harmless duplication. `TodoistAPI.swift` quotes Todoist's own documentation for this
   address: *"Tasks with recurring due dates will be scheduled to their next occurrence."* Closing
   twice advances a recurring task **two** occurrences. The person sees one tap, one "Completed in
   Todoist · 14:57", one local record, and a task that has silently skipped a day — a corrupted row
   in the one dataset this app exists to produce.

   No test covered it: every rate-limit test went through `fetchProjects`, and every
   "exactly one close" assertion used a non-429 answer, so the feature's headline claim was
   unexercised on the one path that broke it.

   Closed by binding the retry to the method — `if endpoint.method == .get, response.statusCode ==
   429, …` — so a rate-limited close falls straight through to `TodoistError.rateLimited` and the
   retry is a person tapping the button again. New test
   `oneTapOnCompleteIsOneCloseEvenWhenRateLimited`, **verified to fail without the fix** (see
   *Evidence*). `TaskCompletion.Outcome` gained `case rateLimited(retryAfter:)` so that fall-through
   has somewhere honest to land, with the wording the design spec already specified.

2. **The one write read its subject live, so it could retarget itself between the tap and the
   bytes.** `TimerView.completionSubject` was a computed property calling
   `plan.attachmentForTheBlockJustWorked()`, which returns the *currently running* work block's
   attachment. By D4 the end-of-block sheet sits over a break that is already running, and nothing
   in `TimerView` closes it at a boundary. With `autoStartNextBlock` on, the break ends behind the
   open sheet, the next focus block auto-starts, takes the next plan item, and the sheet's Complete
   button now points at it.

   The concrete failure: plan is [A, B], auto-start on. Block one works A. The reflection sheet opens
   showing A. Five minutes of writing later, block two takes B. Tapping "Complete in Todoist" closes
   **B**, which was never worked, and leaves A open — and writes a `CompletedTaskRecord` for B, so
   the log says the person worked A and completed B. The control's own copy says "This can only be
   undone in Todoist", and reopening a task is not on the allowlist. The same file already freezes
   `stopPrompts` and `reflectionBreakIsRunning` at presentation, with a comment explaining why a live
   read is wrong; the one value driving a network write was the one left live.

   Closed twice over. The subject is now `@State` frozen at the two moments a sheet is presented
   (`onChange(of: engine.pendingReflection)` and `stopBlock()`) and cleared when either sheet
   closes — and the tap carries the task **with the request**, through a small `CompletionRequest`
   value, so there is no window at all in which a lookup could disagree. New suite
   `CompletionSubjectTests`, which asserts the hazard exists (after the next block starts, the plan's
   answer really has changed to B) and that a frozen subject still closes A and records A. **Its
   limits are stated honestly below in *Still open*.**

3. **The branch as committed does not pass `make ci`.** Reported by all three lenses.
   `scripts/check-secrets.sh` exited 1 at `HEAD` (`12ea4e2`) with 14 findings across four test files.
   The green run everybody reported was the working tree: four modified test files were sitting
   unstaged. The pre-commit hook scans staged files only, which is exactly why three commits went
   through clean and the full-tree scan did not.

   The cause is a genuine false positive with a documented remedy. Check 2 looks for a
   credential-shaped name beside sixteen or more opaque characters, and
   `tokens: InMemoryTokenStore()` is eighteen. The script publishes the convention for this case:
   *"If you need a fake credential anywhere in this repository, name it that way."*

   Closed by taking the script at its word rather than working around it: the stub is now
   **`FakeTokenStore`** (file renamed with it), which is both shorter than the threshold and
   obviously a stand-in, and the reason is written into the type's own doc comment. One further
   local, `let token = "not-a-real-token"` in `tokenNeverAppearsInErrors`, is now `let fixture` —
   the literal value is deliberately unchanged, because it is the value the whole suite proves never
   comes back out. The rejected alternative was a five-line apology at nine call sites explaining
   why a check the whole project relies on is wrong about them, which is how a check ends up
   switched off. `scripts/` is untouched. **The remediation brief forbids committing, so the branch
   still fails at `HEAD` — see *Still open* for the exact commit.**

4. **No device check and no review log.** `docs/reviews/F3.md` did not exist; this file is it.
   **The device check itself is still not closed** — see *Still open*. It is the third feature
   running with this outstanding, and for F3 it is the whole point: the Todoist activity log showing
   a lone completion is the only evidence outside a closed loop of stubs.

## Non-blocking findings acted on

- **A failed Connect destroyed a working credential.** The Settings row reaches the token screen
  while a perfectly good token is stored. `connect()` wrote the pasted value, tried it, and cleared
  it on any failure — so a stale paste, or simply tapping Connect on a train, signed somebody out
  with no dialog while the screen said "Nothing has been saved". True of the new token; false of the
  old one, which is the one they were relying on. The previous value is now read before the
  overwrite and restored on any refusal. It cannot resurrect a revoked token: the only way somebody
  reaches this screen because a stored token stopped working is a refusal that has already removed
  it. Three new tests in `SignInScreenModelTests`.
- **Two amber rows could be on one screen at once.** The revoked banner never cleared, so a revoked
  token followed by one fumbled paste drew a warning triangle for each — and the file states the
  one-amber rule against itself. `banner` is now cleared the moment a fresh attempt begins, so the
  refusal replaces it. The "Largest text" preview was deliberately rendering that unreachable state;
  it now shows one row. `aFreshAttemptClearsTheBannerSoThereIsOnlyEverOneAmberRow`.
- **A refused token left the Complete button live, and the second tap said nothing.** `.tokenRejected`
  mapped back to `.ready`, but by then the credential is out of the Keychain, so tapping again
  reached a client with nothing to send and came back as a nameless `.failed` — "try again in a
  moment", for something that can never succeed. The control now goes to `.unavailable` with its own
  sentence naming Settings, `restingControl` checks the credential first and separately (so it never
  blames the network for a revoked token), and `TaskCompletion` maps `notSignedIn` to `.tokenRejected`
  so both paths agree. `aRefusedTokenSwitchesTheButtonOffRatherThanLeavingItLive`.
- **Signing out could leave the credential and the whole mirror on the phone.** The three clears were
  in one `do`, so a Keychain that refused to delete skipped the rest — the credential still there, a
  full copy of somebody's Todoist still there, the plan gone anyway, and a row reading "Couldn't sign
  out". Of the three, the one with a security meaning was the one left. Each store is attempted
  independently now, credential last, and the failure is still reported.
  `aKeychainThatRefusesToDeleteStillEmptiesTheCopyAndThePlan`, using a stub that refuses.
- **A failed save threw away the completion record.** `recordLocally` inserted the record, deleted
  the cached row and saved; a refusal rolled back *both*, and the sheet still drew "Completed in
  Todoist · 14:57" with nothing behind it. The record is the artefact; the cached delete is
  housekeeping the next refresh does anyway. A refusal is now followed by one more attempt at the
  record alone. **No test** — SwiftData offers no supported way to make a save fail in-process; the
  same limitation `F5.md` recorded.
- **Empty sections were hidden.** `SPEC.md:23` is unconditional — *"All projects, sections, and tasks
  are visible in the picker"* — and both `PickerScreenModel` and `TaskPickerView` quoted that
  sentence while filtering one of the three. An emptied section is still a section, and dropping it
  is this app making an editorial judgement about somebody else's Todoist. It is now drawn as a
  heading with nothing under it, which adds no control anywhere. A project with nothing to work on
  still gets its one sentence. `anEmptySectionIsStillDrawn`,
  `anEmptySectionIsAHeadingAndNotAnInvitation`.
- **The screen drew grouping code the tests never saw.** `TaskPickerView.groups` reimplemented
  `PickerScreenModel.rows(inProject:)` — same iteration, same guard, same fallback — so the tested
  implementation was not the shipped one and the two could drift with the suite still green.
  `PickerScreenModel` now owns `groups(inProject:)`, `rows(inProject:)` is derived from it, and the
  view calls the model. `theRowsAreTheGroupsFlattened` locks the two together.
- **The plan bar lied about an existing plan, and was a dead end.** It was driven from the
  uncommitted picker selection only, which starts empty every time the sheet opens — so with a
  three-item plan stored it read "Nothing planned yet" and was inert. Back out of the session plan
  and there was no way back to it, and therefore no way to reach Skip or Remove without destroying
  the plan to get there. It now reports the stored plan when nothing new has been chosen, and names
  the plan's *current* item rather than its first. `PlanBar` moved to its own file with the change.
- **A revoked token could be pushed past.** Opening the sheet from a timer that already had a plan
  pushed the session plan on top of the token screen, hiding the single most important sentence this
  feature can say. The push is now gated on the banner, and `refresh()` sets `hasToken = false`
  alongside it, as the timer screen already did.
- **The 429 banner promised a retry that never happened.** "Trying again in 30 seconds" with no
  countdown and no scheduled attempt — and a pull during the stated wait went straight out to
  Todoist, which is the one thing a rate limit asks you not to do. The copy now says *"Pull down to
  try again in 30 seconds"*, and a pull inside the window re-shows and re-announces the banner with
  the time actually remaining and sends nothing.
- **Three triggers refreshed the mirror and the comment claimed one.** `TimerView` said the mirror is
  filled "on the way in, and nowhere else except a pull", while it was filled on every foreground
  *and* on every sheet opening, with no floor and no re-entrancy guard. On a five-thousand-task
  account one sweep is roughly 27 requests; a phone picked up forty times in a quarter of an hour was
  over a thousand — past the strictest number Todoist publishes anywhere, for addresses it publishes
  no ceiling for at all. `refresh` now takes `force:`, defaulting to `true` because most callers are
  somebody asking; the two automatic triggers pass `false` and skip if the copy is under a minute
  old, and a sweep already in flight is never doubled. A pull is never held back.
  `anAutomaticRefreshRightAfterAnotherAsksForNothing`, `aPullToRefreshIsNeverHeldBack`.
- **VoiceOver never heard a row's second line.** `spokenToggleLabel` was built from the title and the

  identically-titled rows apart, which is why it exists — and the label carrying it is hidden from
  VoiceOver on task rows, so it reached no reader at all. It also dropped "3 tasks" from project
  rows. Both are spoken now. `aRowSpeaksItsSecondLine`.
- **The Settings route rebuilt the token screen's state.** The destination was constructed inline in
  a `NavigationLink`, and `TodoistSignInView` holds its model in a `@Bindable` rather than a
  `@State` — so a break ending flipped `isRunning`, the parent body re-ran, and a half-pasted
  credential vanished with no explanation. A `TodoistSignInRoute` wrapper owns the model in `@State`.

- **`everySentenceThePickerCanSay` covered five sentences of about fifteen** and its name claimed
  otherwise, sitting beside a test that really is mechanical. The ten it missed were the empty
  states, which is precisely where a create affordance gets added. Every user-facing string in the

  them; the array is built from all of them.
- **The one runtime-assembled part of an address is now checked.** `closeTask(id:)` interpolated an
  unvalidated identifier. It could not reach a write — every path this app can produce ends in
  `/close` — but that is the shape being lucky rather than a guarantee, and it opens the day a fifth

### The scare, and what it actually was

The owner reported that a completed task and **an entire project** had disappeared from Todoist. That
is data loss, and it was investigated as such rather than reassured away.

It was not data loss. The evidence that settled it came from Todoist's own API: the cache is a
**full replace** on refresh, and a refresh at 16:52:09 — *after* both completions — returned
`9/19 House Party`. A project Todoist had deleted could not have appeared in that response.

What had happened is that `Create flyers` was the project's only task. Completing it left the project
empty, and an empty project is easy to scroll past. The task itself was under **Completed tasks**,
where the owner then found it.

Worth stating plainly for the next person who gets this fright: **the app is structurally incapable of
deleting anything in Todoist.** Its HTTP client has exactly two cases, `get` and `post`; there is no
`DELETE`. Its entire allowlist is four lines. There is no project endpoint beyond `GET /projects`.
Every `delete` in the codebase is `context.delete` against the local SwiftData mirror.

### A real finding: recurring tasks do not complete, they advance

`Budget with YNAB by 7:30 AM` appeared in Todoist's activity log as completed at 16:48 **and was still
returned as an active task** by the 16:52 refresh. That is not a bug. In Todoist, closing a recurring
task advances it to its next occurrence rather than finishing it.

This matters beyond F3, and F6 should decide it deliberately rather than discover it:

- A `CompletedTaskRecord` for a recurring task is accurate — you *did* complete today's occurrence —
  but the task still exists and will be completable again tomorrow.
- So the export's Completed section will legitimately list the same task title on many days. That is
  probably what a person wants from a daily habit, but it is a different thing from finishing a piece
  of work, and a reader glancing at the list should not have to work out which.
- F3 stores the id and a title snapshot and nothing else, so it cannot currently tell the two apart.
  Deciding whether it should is F6's, and it is recorded here so the question arrives with evidence
  behind it rather than as a surprise.
